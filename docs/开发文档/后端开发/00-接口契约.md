# 后端接口契约（v0.1.0 冻结版）

> 版本: v0.1.0
> 最后更新: 2026-09-21
> 范围: 后端 Repository / Service / Handler 三层的类型与方法签名、全部路由与响应类型

---

## 1. 契约用途

本文档冻结 v0.1.0 的分层接口命名与签名。`internal/repository`、`internal/service`、
`internal/api/handler/web`、`internal/api/handler/app` 四层的实现必须与本文档**逐字一致**，
否则 `internal/api/router/web.go` 无法完成装配。

配套约定：

- 所有 Handler 构造函数命名为 `NewXxxHandler()`，方法接收者为 `(h *XxxHandler)`。
- 所有 Service 构造函数命名为 `NewXxxService()`，无参。
- 所有 Repository 构造函数命名为 `NewXxxRepo()`，无参。
- Repository 与 Service 的方法首参统一为 `ctx context.Context`。
- 分层调用：Handler → Service → Repository。**Handler 不得直接调用 Repository。**

## 2. 通用约定

### 2.1 响应类型命名

| 类型 | 结构 | 用途 |
|---|---|---|
| `RXxxList` | `Data []model.Xxx` 或 `[]XxxOption` | 简单列表（无分页） |
| `RPageXxx` | `Data PageXxxResp{Items, Total, Page, PageSize}` | 分页列表 |
| `RXxx` | `Data model.Xxx` | 单条详情 |
| `ROptionList` | `Data []OptionItem{ID, Name, Code}` | 下拉选项 |

全部响应包装类型继承 `response.BaseResponse`，定义在 `internal/dto/response/<domain>.go`。

### 2.2 分页请求参数

统一查询参数：`page`（默认 1）、`page_size`（默认 20）。

### 2.3 数据权限

列表类 Repository 方法通过 `utils.NewDataScope(c).ApplyToQuery(q, "<alias>.dept_id")` 施加行级过滤。
`dept_id` 为空的表不做行级过滤（如 `ac_menu`、`ac_role`）。

## 4. Handler 清单（router 装配契约）

profileH := handler.NewProfileHandler()

## 6. Repository 层方法命名

Repository 方法与 Service 方法同名同参（去掉 `ds` 参数，数据权限在 Service 层组装查询条件）。
唯一要求：构造函数 `NewXxxRepo()`，方法首参 `ctx context.Context`，返回 `(*model.T, error)` 或
`([]model.T, int64, error)`（列表返回 items + total）。

## 9. 约束与注意事项

1. **静态路径统一写在 `:id` 之前**（书写约定，非框架硬约束）。
   > **实测修正（v0.1.0）**：gin v1.12 的路由树会把同级静态子节点**规范化到 `:param` 之前，与注册先后无关**。
   > 实测：先注册 `/probe/:id` 再注册 `/probe/modes`，请求 `/probe/modes` 仍命中静态 handler，
   > 且 `Routes()` 输出中 `modes` 排在 `:id` 前。因此「不按顺序就会被吞掉」的旧说法不成立。
   > 本项目仍保持静态在前的书写顺序（可读性更好），真正的防线是回归测试
   > `backend/tests/api/route_test.go` 的 `TestRoutePriority_StaticWinsOverParam` —— 它以**发起真实请求、
   > 按响应特征判定命中的 handler** 来断言优先级（已实证非空转：移除 `/web/devices/modes` 注册后该测试立即报
   > `期望 200，实际 status=400 message="无效的设备ID"`，正是路由被参数分支吞掉的症状）。
2. **所有分页端点必须返回类型化的 `RPageXxx`**，Swagger `@Success 200 {object} response.RPageXxx`。
3. **`@ID` 取方法名首字母小写**；分页方法统一命名为 `pageXxxx`（如 `Page` → `pageUsers` 需按语义命名，
   本契约允许 `@ID` 直接使用方法名小写，如 `userH.Page` → `@ID Page` 不合规，应写 `@ID pageUsers`）。
   实际执行时以 handler 语义命名：`Page` → `pageUsers` / `pageRoles` / `pageRegions` …
4. **列表涉及多表关联时必须返回关联名称字段**（如风险列表返回 `risk_type.name`、`device.name`、`region.name`），
   通过 GORM `Preload` 实现。
5. **角色授权变更后必须调用 Casbin 同步**：`internal/service/system/role_service.go` 内的
   `syncCasbinForRole(ctx, roleID)` 负责重建 p/g/g2/g3 策略并 `ReloadPolicy()`。
6. **告警设置只能操作当前登录用户的数据**（`user_id = ctx 中的 user_id`）。

### 10.15 IOT 设备端（前缀 `/iot`）★ 无 JWT / 无 Casbin

> 实现：`internal/api/handler/iot/ota_handler.go` + `internal/api/router/device.go`
> 鉴权：请求头 `X-Device-Code`（`ac_device.device_code`）
> 与 `X-Device-Secret`（`ac_device.device_secret`）。

| 方法 | 路径 | Handler | 方法 | 鉴权 |
|---|---|---|---|---|
| POST | `/iot/ota` | iotDeviceH（handler/iot） | `OTA` | X-Device-* |
| POST | `/iot/activate` | iotDeviceH（handler/iot） | `Activate` | X-Device-* |

- **为什么不用 JWT**：设备无人值守、无用户会话；JWT 需要在设备上长期保存
  且泄露后无法按设备吊销。`device_secret` 一机一份，可单独轮换。
- **为什么 OTA 返回明文组凭据**：设备已用 `device_secret` 完成身份确认，
  脱敏会使其无法登录服务组；Web 读接口仍然脱敏。
- `POST /iot/ota`：body 可选 `{client_version}`，返回
  `{product, device, service_groups:[{code,name,type,username,password,items:[]}],
  server_time}`。服务组 = 该设备产品绑定的、`active` 的组；服务项只返回 `active` 的。
  每次调用写一条 `ac_iot_device_event(event='ota')`。
- `POST /iot/activate`：body `{owner_name?, owner_phone?, nickname?}`，
  返回 `{username, password, device_code, activated_at}`；
  **重复激活返回 409**「设备已激活，请勿重复激活」。
- `device_secret` 为空 → 401「设备未配置接入密钥，请先在平台重置」；
  密钥不匹配 → 401「设备接入密钥无效」。

## 14. v0.2.0 约束与注意事项

1. **国标 ID ≠ 设备编号**。`gb_device_id`（20 位）与 `device_code`（业务编号）是**两个命名空间**，
   不要复用、不要互转（设计 §4.1）。
2. **`ac_gb_sip_log` 不嵌 `BaseModel`**，无 `deleted_at` / `dept_id`，**不做软删除、不走 DataScope**。
3. **四个敏感字段必须脱敏**：`ac_device.sip_password`、`ac_gb_media_server.secret`、
   `ac_gb_platform.password`、`ac_gb_channel.password`。读返 `****`，写遇空值或含 `****` 时跳过。
4. **`/media/hook/*` 是独立中间件组**，不挂 `authMW` / `casbinMW`，用 ZLM `secret` 校验。
5. **`on_publish` 拒绝用 `{"code":-1}`**（HTTP 200），不是 HTTP 401（设计 §7.3）。
6. **流名规则**：`stream = %08X(ssrc)` 大写（**两种端口模式都是**，设计 §2.2 实测）。`{deviceId}_{channelId}` 只作鉴权映射键，不是流名。
   前端播放器用 `app` / `stream` 拼 ZLM 播放地址。
7. **分页一律用 `RPageXxx`**，禁止 `PageResp`；`@ID` 用方法名首字母小写，分页方法命名 `pageXxxx`。
8. **列表涉及关联表必须返回名称字段**（`region.name`、`group.name`、`media_server.name` 等），
   通过 GORM `Preload` 实现。
9. **`ac_gb_platform_group` / `ac_gb_platform_region` 是纯关联表**（无 `dept_id`），
   随主表 `ac_gb_platform` 过滤，不单独施加 DataScope。
10. **权限码**：本期的菜单与按钮权限行必须在 `sql/init/01-初始数据.sql` 中真实存在，
    否则前端 `permCodes.includes()` 会对**超管也静默失效**（`CLAUDE.md` 有此踩坑记录）。

## 15. 关键端点的字段级定义

> 本轮实现（Web 播放器）时发现：§10 只给了路由，**字段没定义**会导致前端与后端各自猜，
> 猜错时表现为「按钮点了没反应」而不是报错。本节把最容易猜错的几处钉死。

### 15.1 `POST /web/gb/play/:channelId` —— 播放

**请求** `GbPlayReq`：

```go
type GbPlayReq struct {
    Protocol string `json:"protocol"` // webrtc | flv | hls，缺省 webrtc
    StreamID string `json:"stream_id"` // 可选，重用已有流
}
```

**响应** `RGbPlayResp`：

```go
type GbPlayResp struct {
    App      string `json:"app"`       // 恒为 "rtp"
    Stream   string `json:"stream"`    // = %08X(ssrc) 大写（设计 §2.2 实测）
    SSRC     string `json:"ssrc"`      // 10 位，供排障
    HTTPBase string `json:"http_base"` // ★ ZLM 的 HTTP 基址，如 http://10.0.0.5:8082
    WebRTC   string `json:"webrtc"`    // 完整 WHEP URL
    FLV      string `json:"flv"`       // 完整 HTTP-FLV URL
    HLS      string `json:"hls"`       // 完整 HLS URL
    MediaServerID string `json:"media_server_id"`
    StreamID string `json:"stream_id"` // 会话标识，停止时回传
}
```

> **前端二选一即可**：用 `webrtc`/`flv`/`hls` 整串地址最省事；要给 `mpegts.js` 自己拼则用
> `http_base` + `app` + `stream`。**两个都返回**，避免前端为了拿 `http_base` 再去查媒体节点列表。
> 已实现的 `LivePlayer` 组件同时支持 `url`（整串）与 `app/stream/httpBase`（三件套）两种入参。

### 15.2 `POST /web/gb/ptz/:channelId` —— 云台控制

**请求** `GbPtzReq`：

```go
type GbPtzReq struct {
    // 方向：八方向 + 停止。★ 命名必须与前端 PtzControl 组件一致，否则按钮静默失效
    Direction string `json:"direction"` // up|down|left|right|up-left|up-right|down-left|down-right|stop
    // ★ 速度量纲：1–8（1 最慢、8 最快）。后端负责映射到 PTZCmd 的 0x00–0xFF 字节
    Speed     int    `json:"speed"`     // 1–8，缺省 5
    // 变焦/光圈/聚焦为独立动作，与 direction 互斥
    Action    string `json:"action"`    // "" | zoom-in | zoom-out | zoom-stop
                                       //   | iris-in | iris-out | iris-stop
                                       //   | focus-near | focus-far | focus-stop
}
```

> ⚠️ **速度量纲（1–8）与方向枚举是本契约钉死的**。前端 `PtzControl` 组件已按此实现
> （`defaultSpeed=5`、`presetCount=8`）。后端若按 0–255 解释会**静默错位**（速度不对但不报错）。
> 映射关系写进 `internal/gb28181/protocol/manscdp` 的 PTZCmd 构造函数。

**预置位** `POST /web/gb/ptz/:channelId/presets`（`GbPresetReq`）：
`PresetID int`（1–255）、`Name string`、`Action string`（`set`）。

**巡航/扫描**（`GbPtzCruiseReq` / `GbPtzScanReq`）：
`Action string`（`start` | `stop`）、`GroupID int`（巡航组号）。

### 15.3 `POST /web/gb/playback/control` —— 回放控制

```go
type GbPlaybackControlReq struct {
    StreamID string `json:"stream_id"`
    Action   string `json:"action"` // pause | resume | seek | speed
    // Action=seek 时必填，取值范围为本次回放的时间窗
    SeekTime string `json:"seek_time"` // 格式 "2006-01-02T15:04:05"
    // Action=speed 时必填，1.0 为原速
    Scale    float64 `json:"scale"`
}
```

> **回放控制走带内 SIP `INFO` + MANSRTSP，云台走带外 `MESSAGE`** —— 两者的发送路径完全不同
> （设计 §2.5）。实现时不要复用同一个发送函数。

### 15.5b 设备侧 SDP 的 `o=` 用户名必须是设备编码（★ 实施提醒）

平台的 **ACK 目的地址取自 SDP 的 `o=` 用户名**，不是 Contact 头
（WVP `InviteResponseProcessor` 的实现即如此）。

**因此设备回 200 OK 时，SDP 必须是 `o=<设备国标编码> ...`。**
写错的表现是：**INVITE 成功、200 OK 也收到了，但 ACK 打不到设备 → 推流永不开始**，
且没有任何报错。这是模拟器实现阶段实测踩到的坑，已在其测试里钉住。

### 15.5c 语音对讲的 `startSendRtp` 与 ZLM 端口分配

语音对讲回推音频走 ZLM 的 `startSendRtp`（向设备发 RTP）。**该接口的发送端口同样由
ZLM 内部的 `PortManager` 分配**，与 `openRtpServer` 共用同一套端口资源。

> ⚠️ 因此**不要**为了让某个误用「响亮失败」而把 `deploy/zlm/config.ini` 的
> `rtp_proxy.port_range` 设成非法值（实测会触发 `Rtsp.cpp makeSockPair`
> 断言失败并重试，波及 ZLM 内部 socket 分配，最终影响对讲）。
> 防误用改用纪律：**sipsvc 不得调用 `openRtpServer`**（设计 §2.2）。

## 16. 内部服务间 RPC（`/rpc`）

> 不是给浏览器/App 用的接口，**不挂 JWT / Casbin / OperationLog**。
> 调用方是内部进程（MQTT broker、其他服务），用共享 token 鉴权；
> 生产必须用 NetworkPolicy / 内网限制来源。

### 16.1 MQTT 鉴权（broker → 后端）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/rpc/mqtt/auth` | 连接鉴权 |
| POST | `/rpc/mqtt/acl` | 发布/订阅 ACL |

请求头：`X-RPC-Token: <MQTT_RPC_TOKEN>`

```json
// /rpc/mqtt/auth
{"username":"iot_xxx","password":"...","client_id":"...","remote_addr":"10.0.0.9:50123"}
// 响应：allow=false 时 broker 拒绝连接
{"allow":true,"group_code":"iot-webrtc-01","reason":""}

// /rpc/mqtt/acl
{"username":"iot_xxx","client_id":"...","topic":"iot/iot-webrtc-01/data","action":"publish"}
{"allow":true,"reason":""}
```

**鉴权规则**：用户名匹配 `ac_iot_service_group.username`，组必须启用、`type=webrtc`、
且存在启用的 `MQTT` 服务项；密码做 constant-time 比较。
**ACL 规则**：只允许 `iot/<group_code>` 及其子路径；跨组话题一律拒绝。

**失败语义**：后端不可达 / 超时 / token 错误 / 非 2xx / 未配置 `MQTT_RPC_TOKEN`
→ broker 与后端**双层 fail-closed**，绝不放行。

### 16.2 TURN 凭据签发

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/rpc/turn/credentials` | 签发 coturn 短期凭据 |

请求头：`X-RPC-Token: <TURN_RPC_TOKEN>`

```json
{"subject":"device-001","ttl":3600}
→ {"code":200,"data":{
     "username":"1700000000:device-001",
     "password":"Base64(HMAC-SHA1(secret, username))",
     "ttl":3600,"expires_at":1700000000,
     "realm":"ai-camera","urls":["stun:...","turn:..."]
   }}
```

**为什么不是 coturn 回调后端**：coturn **没有** HTTP 鉴权回调，唯一的外部授权方式是
TURN REST API（`use-auth-secret`）。后端负责「授权 + 签发」，coturn 只验签与过期时间。
详见 `docs/部署文档/01-部署与运维.md` 的 TURN 一节。

`POST /iot/ota` 在配置了 TURN 时会附带 `turn` 字段（subject 为设备编码），
设备可直接用其 `username`/`credential` 配置 ICE；未配置时字段省略。
