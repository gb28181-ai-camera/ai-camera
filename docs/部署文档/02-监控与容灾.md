## 1. 监控体系架构

AI Camera 的监控对象比其他业务系统多一层：除了「服务是否可用」，还要监控**设备是否在
上报**。设备离线不会触发任何 HTTP 请求，服务端指标全绿但业务已经停摆 —— 因此监控体系必须
把「设备心跳静默」作为一等公民信号。

> **注意**：第 4 层是本项目区别于普通 Web 系统的关键。第 1~3 层全绿但第 4 层为 0，
> 说明「平台活着但设备没在干活」，业务上等价于故障。

## 2. Prometheus 监控配置

### 2.1 服务发现与采集配置

采用 K8s Pod 注解自动发现，避免每次扩缩容都改配置。

```yaml
# k8s-apply-gitops/ai-camera-monitor/prometheus/prometheus.yml
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    cluster: ai-camera-prod
    env: prod

rule_files:
  - /etc/prometheus/rules/*.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]

scrape_configs:
  # ── 1. 后端服务（Pod 注解发现）──
  - job_name: ai-camera-backend
    kubernetes_sd_configs:
      - role: pod
        namespaces:
          names: [ai-camera-prod]
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_path]
        action: replace
        target_label: __metrics_path__
        regex: (.+)
      - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        regex: ([^:]+)(?::\d+)?;(\d+)
        replacement: $1:$2
        target_label: __address__
      - source_labels: [__meta_kubernetes_pod_name]
        action: replace
        target_label: pod
      - source_labels: [__meta_kubernetes_pod_label_app]
        action: replace
        target_label: service

  # ── 2. Node Exporter（节点资源）──
  - job_name: node-exporter
    kubernetes_sd_configs:
      - role: node
    relabel_configs:
      - source_labels: [__address__]
        regex: (.+):(\d+)
        replacement: $1:9100
        target_label: __address__

  # ── 3. PostgreSQL Exporter ──
  - job_name: postgres-exporter
    static_configs:
      - targets: ["postgres-exporter.ai-camera-monitor.svc.cluster.local:9187"]
    metrics_path: /metrics

  # ── 4. Redis Exporter ──
  - job_name: redis-exporter
    static_configs:
      - targets: ["redis-exporter.ai-camera-monitor.svc.cluster.local:9121"]

  # ── 5. 设备心跳探针（本项目特有）──
  # 由 ai-camera-beat-probe 定时调用后端统计接口，把「离线设备数」暴露为指标
  - job_name: ai-camera-beat-probe
    static_configs:
      - targets: ["ai-camera-beat-probe.ai-camera-monitor.svc.cluster.local:9273"]
    scrape_interval: 60s
```

设备心跳探针的定位：Prometheus 无法感知「设备没有发请求」这件事，所以用一个 sidecar
定期查询 `ac_device` 的 `status='offline'` 与 `last_beat_dt` 分布，转成 Gauge 指标。

```yaml
# k8s-apply-gitops/ai-camera-monitor/deployments/ai-camera-beat-probe.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai-camera-beat-probe
  namespace: ai-camera-monitor
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ai-camera-beat-probe
  template:
    metadata:
      labels:
        app: ai-camera-beat-probe
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "9273"
    spec:
      containers:
        - name: probe
          image: registry.boticz.cn:5000/boticz/ai-camera-beat-probe:latest
          env:
            - name: METRICS_ADDR
              value: ":9273"
            - name: QUERY_INTERVAL
              value: "60s"
            # 直接读库统计，避免依赖后端接口的鉴权
            - name: DB_DSN
              valueFrom:
                secretKeyRef:
                  name: ai-camera-probe-secret
                  key: dsn
```

埋点接入示例（在 handler 中记录风险上报与心跳）：

```go
// internal/api/handler/web/risk_handler.go（节选）
func (h *RiskHandler) Report(c *gin.Context) {
	var req request.ReportRiskReq
	if err := c.ShouldBindJSON(&req); err != nil {
		utils.BadRequest(c, "参数错误")
		return
	}

	rec, err := h.svc.Report(c.Request.Context(), &req)
	if err != nil {
		metrics.RiskReportedTotal.WithLabelValues(req.RiskTypeCode, "", "error").Inc()
		utils.ServerError(c, "风险上报失败")
		return
	}

	metrics.RiskReportedTotal.WithLabelValues(
		req.RiskTypeCode, rec.DeviceCode, rec.RiskLevel,
	).Inc()

	utils.Success(c, rec)
}
```

### 2.3 告警规则

```yaml
# k8s-apply-gitops/ai-camera-monitor/prometheus/rules/ai-camera.yml
groups:
  - name: ai-camera-service
    interval: 30s
    rules:
      - alert: BackendDown
        expr: up{job="ai-camera-backend"} == 0
        for: 1m
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "ai-camera-backend 实例 {{ $labels.pod }} 离线"
          description: "已持续 1 分钟未采集到指标，检查 Pod 状态与数据库连通性。"

      - alert: BackendHighErrorRate
        expr: |
          sum(rate(ai_camera_http_requests_total{status=~"5.."}[5m]))
          / sum(rate(ai_camera_http_requests_total[5m])) > 0.01
        for: 5m
        labels:
          severity: critical
          team: platform
        annotations:
          summary: "5xx 错误率超过 1%（当前 {{ $value | humanizePercentage }}）"

      - alert: BackendSlowP95
        expr: |
          histogram_quantile(0.95,
            sum(rate(ai_camera_http_duration_seconds_bucket[5m])) by (le, path)
          ) > 1.5
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "接口 {{ $labels.path }} P95 超过 1.5s（需求上限）"

      - alert: CasbinDenySpike
        expr: sum(rate(ai_camera_casbin_deny_total[5m])) > 5
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Casbin 鉴权拒绝速率异常，可能为权限误配或凭据泄露探测"

      - alert: CasbinEnforceSlow
        expr: |
          histogram_quantile(0.99,
            sum(rate(ai_camera_casbin_enforce_duration_seconds_bucket[10m])) by (le)
          ) > 0.01
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: "Casbin 校验 P99 超过 10ms，策略表可能膨胀"

  - name: ai-camera-device
    interval: 60s
    rules:
      # ── 设备心跳中断（本项目最关键的告警）──
      - alert: DeviceHeartbeatStopped
        expr: sum(rate(ai_camera_device_heartbeat_total[10m])) < 0.1
        for: 10m
        labels:
          severity: critical
          team: ops
        annotations:
          summary: "全平台心跳上报速率低于 0.1/s，疑似上报链路中断"
          description: "设备侧或网络侧异常。先确认是否为设备批量离线，再排查 ApiKey 与限流配置。"

      - alert: DeviceHeartbeatErrorsHigh
```

### 2.4 GB28181 指标（`/metrics`）

> 实现：`backend/internal/gb28181/metrics/`。
> **不引入 `prometheus/client_golang`**：只有 counter/gauge 两种类型，
> 手写 Prometheus 文本格式（0.0.4）即可，避免新增供应链依赖。

#### 2.4.1 端点与安全

```http
GET /metrics
```

- 不挂 JWT / Casbin：Prometheus 没有用户会话，且指标不含业务数据。
- **生产必须限制来源**：用 NetworkPolicy 只允许 `ai-camera-monitor` 命名空间的
  Prometheus 访问 8080，或经 Ingress 白名单。禁止暴露到公网 —— 指标会泄露
  设备规模、注册失败率与故障形态。
- Content-Type：`text/plain; version=0.0.4; charset=utf-8`。

```bash
curl -s http://localhost:8080/metrics | grep '^aicamera_gb_'
```

#### 2.4.2 指标清单

| 指标 | 类型 | 标签 | 含义 |
|:---|:---:|:---|:---|
| `aicamera_gb_sip_registers_total` | counter | `result=success/failed/rejected` | 注册成功 / 网络失败 / 鉴权拒绝 |
| `aicamera_gb_sip_messages_total` | counter | `direction=in/out` | SIP 入向 / 出向报文数 |
| `aicamera_gb_active_streams` | gauge | — | 当前活跃国标流数 |
| `aicamera_gb_hook_callbacks_total` | counter | `event=...` | ZLM 回调事件数（server_keepalive、publish、stream_changed…） |
| `aicamera_gb_voice_sessions` | gauge | — | 活跃语音广播/对讲/Agent 会话数 |
| `aicamera_gb_process_start_time_seconds` | gauge | — | 进程启动时间（Unix 秒），用于 uptime/重启识别 |
| `aicamera_gb_diagnoses_total` | counter | `result=ok/warning/failed/skipped` | 设备诊断接口调用结论分布 |
| `aicamera_gb_sip_log_deleted_total` | counter | — | janitor 累计物理删除的信令日志行数 |
| `aicamera_gb_sip_log_dropped` | gauge | — | 信令日志异步队列累计丢弃条数（应长期为 0） |

#### 2.4.3 打点状态（重要）

本轮只在**可修改的文件**里完成了打点；信令/媒体核心文件属于其他并行任务，
以下位置需要在主会话合入后接线（API 已就绪，直接调用即可）：

| 指标 | 待接线位置 | 建议调用 |
|:---|:---|:---|
| 注册成功 | `internal/gb28181/sipserver/handlers.go` → REGISTER 成功分支 | `metrics.IncSipRegister("success")` |
| 注册失败 | 同文件 → 发送失败/非法报文分支 | `metrics.IncSipRegister("failed")` |
| 注册拒绝 | 同文件 → Digest 鉴权失败/设备未建档（403） | `metrics.IncSipRegister("rejected")` |
| 入向报文 | 同文件 → 每个 SIP 请求入口 | `metrics.IncSipMessage("in")` |
| 出向报文 | `internal/gb28181/sipserver/service.go` → `send()` | `metrics.IncSipMessage("out")` |
| ZLM hook | `internal/gb28181/hook/*` → 各回调入口 | `metrics.IncHookCallback("server_keepalive")` 等 |
| 活跃流 | `on_stream_changed` 回调 | `metrics.SetActiveStreams(n)` 或 `AddActiveStreams(±1)` |
| 语音会话 | `internal/service/gb28181/voice_service.go` → 建/停会话 | `metrics.AddVoiceSessions(+1/-1)` |
| 日志丢弃 | 信令进程退出前或周期任务 | `metrics.SetSipLogDropped(mgr.DroppedLogs())` |

已接线：

- `aicamera_gb_diagnoses_total`：`internal/gb28181/diagnostics/diagnostics.go`；
- `aicamera_gb_sip_log_deleted_total`：`internal/service/gb28181/sip_log_service.go`；
- `aicamera_gb_process_start_time_seconds`：metrics 包 `init()`。

> 标签纪律：只允许固定枚举值。**禁止**把设备国标编码、Call-ID、远端 IP 当标签，
> 否则时序数量随设备数线性膨胀。按设备排障请查 `ac_gb_sip_log` 表。

#### 2.4.4 建议告警规则

```yaml
# 追加到 k8s-apply-gitops/ai-camera-monitor/prometheus/rules/ai-camera.yml
- alert: GbSipRegisterRejected
  expr: sum(rate(aicamera_gb_sip_registers_total{result="rejected"}[5m])) > 0
  for: 5m
  labels: { severity: warning }
  annotations:
    summary: "国标设备 REGISTER 持续被拒，检查 sip_password / realm / gb_device_id 建档"

- alert: GbSipNoInbound
  expr: |
    sum(rate(aicamera_gb_sip_messages_total{direction="in"}[10m])) == 0
    and on() (sum(aicamera_gb_sip_registers_total) > 0)
  for: 10m
  labels: { severity: critical }
  annotations:
    summary: "平台已接入国标设备，但 10 分钟无任何入向 SIP 报文，疑似 5060 链路中断"

- alert: GbZlmHookStopped
  expr: sum(rate(aicamera_gb_hook_callbacks_total{event="server_keepalive"}[5m])) == 0
  for: 5m
  labels: { severity: critical }
  annotations:
    summary: "ZLM 心跳回调中断，检查 ZLM_HOOK_BASE / NetworkPolicy / backend 8080"

- alert: GbSipLogDropped
  expr: aicamera_gb_sip_log_dropped > 0
  for: 5m
  labels: { severity: warning }
  annotations:
    summary: "信令日志写入队列出现丢弃，数据库写入能力跟不上信令速率"

- alert: GbDiagnoseFailureSpike
  expr: |
    sum(rate(aicamera_gb_diagnoses_total{result="failed"}[15m]))
    / sum(rate(aicamera_gb_diagnoses_total[15m])) > 0.5
  for: 15m
  labels: { severity: warning }
  annotations:
    summary: "设备诊断失败率超过 50%，现场网络/NAT 可能存在系统性问题"
```

> 说明：`GbSipNoInbound` 只在「历史上有过注册」时触发（`sum(registers) > 0`），
> 避免全新部署、尚未接入设备时产生噪音。

### 3.1 配置

```yaml
# k8s-apply-gitops/ai-camera-monitor/alertmanager/alertmanager.yml
global:
  resolve_timeout: 5m
  smtp_smarthost: "smtp.exmail.qq.com:465"
  smtp_from: "alert@boticz.com"
  smtp_auth_username: "alert@boticz.com"
  smtp_auth_password_file: /etc/alertmanager/secrets/smtp_password

route:
  receiver: default
  group_by: [alertname, cluster, service]
  group_wait: 30s            # 首次告警等待 30 秒，聚合同批告警
  group_interval: 5m         # 同组新增告警的推送间隔
  repeat_interval: 4h        # 未恢复告警的重复提醒间隔
  routes:
    # ── 严重告警：立即电话 + 企业微信 + 短信 ──
    - matchers:
        - severity = critical
      receiver: critical-receiver
      group_wait: 10s
      repeat_interval: 1h
      continue: true         # 继续匹配后续路由（业务负责人也要收到）

    # ── 设备类告警：只推设备运维组 ──
    - matchers:
        - team = ops
      receiver: ops-receiver
      group_by: [region, alertname]

    # ── 业务类告警：只推业务负责人 ──
    - matchers:
        - team = biz
      receiver: biz-receiver

    # ── 已知维护窗口静默 ──
    - matchers:
        - alertname =~ "BackendDown|BackendHighErrorRate"
      receiver: platform-receiver
      mute_time_intervals: [maintenance-window]

receivers:
  - name: default
    webhook_configs:
      - url: "http://ai-camera-alert-bridge.ai-camera-monitor.svc.cluster.local:8080/alert"

  - name: critical-receiver
    webhook_configs:
      - url: "http://ai-camera-alert-bridge.ai-camera-monitor.svc.cluster.local:8080/alert?level=critical"
    # 电话通知由 alert-bridge 对接语音网关
    email_configs:
      - to: "oncall@boticz.com"
        send_resolved: true
        headers:
          Subject: "[CRITICAL] {{ .CommonLabels.alertname }}"

  - name: platform-receiver
    webhook_configs:
      - url: "http://ai-camera-alert-bridge.ai-camera-monitor.svc.cluster.local:8080/alert?group=platform"

  - name: ops-receiver
    webhook_configs:
      - url: "http://ai-camera-alert-bridge.ai-camera-monitor.svc.cluster.local:8080/alert?group=ops"

  - name: biz-receiver
    webhook_configs:
      - url: "http://ai-camera-alert-bridge.ai-camera-monitor.svc.cluster.local:8080/alert?group=biz"

inhibit_rules:
  # 后端整体不可用时，抑制派生的错误率/延迟告警，避免告警风暴
  - source_matchers: [alertname = "BackendDown"]
    target_matchers: [alertname =~ "BackendHighErrorRate|BackendSlowP95"]
    equal: [cluster, service]

  # 数据库主库故障时，抑制复制延迟告警
  - source_matchers: [alertname =~ "PostgresPrimaryDown"]
    target_matchers: [alertname = "PostgresReplicationLag"]
    equal: [cluster]

  # PVC 满时抑制上传失败告警（同一根因）
  - source_matchers: [alertname = "PVCNearlyFull"]

time_intervals:
```

### 3.2 告警分级与升级机制

| 级别 | 触发条件 | 通知方式 | 首次响应 | 升级时限 | 接收人 |
|:---:|:---|:---|:---:|:---:|:---|
| **P0 致命** | 后端全实例不可用、数据库主库故障、全平台设备心跳中断 | 电话 + 短信 + 企业微信 + 邮件 | 5 分钟 | 15 分钟未响应 → 主管 | 值班工程师 → 平台负责人 |
| **P1 严重** | 5xx > 1%、复制延迟 > 30s、区域设备全离线、PVC > 85% | 企业微信 + 短信 + 邮件 | 15 分钟 | 30 分钟未响应 → 主管 | 值班工程师 |
| **P2 警告** | P95 超限、Casbin 拒绝激增、设备在线率 < 80%、第三方失败率 > 20% | 企业微信 + 邮件 | 1 小时 | 4 小时未处理 → 升级 P1 | 值班工程师 |
| **P3 提示** | 风险积压、误报率上升、物联网卡流量 > 90%、升级失败率 > 30% | 企业微信（工作时段） | 1 工作日 | 3 工作日未处理 → 升级 P2 | 对应业务负责人 |

```
告警升级链路：

  ┌──────────────┐        ┌──────────────┐        ┌──────────────┐
  │  值班工程师   │ ──15m─▶│  平台负责人   │ ──30m─▶│  技术总监     │
  │  (第一响应)   │  未响应 │  (升级响应)   │  未响应 │  (兜底)       │
  └──────────────┘        └──────────────┘        └──────────────┘
         │                        │                        │
         └────────────────────────┴────────────────────────┘
                                  │
                                  ▼
                        ┌──────────────────┐
                        │  事故复盘与改进    │
                        │  24h 内出初步结论  │
                        └──────────────────┘
```

值班与静默约定：

- 值班表按月轮换，值班人当日必须保持电话可达。
- 计划内维护（每次生产发布、数据库升级）提前在 AlertManager 配置 `mute_time_intervals`，
  静默窗口结束后必须确认告警恢复正常。
- 同一根因的多条告警通过 `inhibit_rules` 抑制，禁止让值班人在 5 分钟内收到 20 条同源告警。
- **P0 告警不允许静默处理** —— 只能显式标记为「已确认」并在事后补充复盘记录。

## 5. 容灾架构设计

### 5.1 容灾目标

| 系统/数据 | RTO（恢复时间目标） | RPO（恢复点目标） | 容灾等级 |
|:---|:---:|:---:|:---|
| 后端 API 服务 | ≤ 5 分钟 | — | 同城双活（多副本 + HPA） |
| PostgreSQL 业务库 | ≤ 15 分钟 | ≤ 5 分钟（流复制） / ≤ 1 分钟（同步提交） | 主备 + 自动切换 |
| Redis 缓存（预留） | ≤ 5 分钟 | ≤ 1 分钟 | Sentinel / Cluster |
| `uploads/` 文件存储 | ≤ 30 分钟 | ≤ 24 小时 | 每日增量同步 + 对象存储迁移 |
| 管理后台 / 官网静态站 | ≤ 5 分钟 | — | 多副本，无状态 |
| 设备侧数据（断网续传） | 不适用 | ≤ 设备 `info_interval` | 设备本地缓存后补传 |

> **注意**：RPO 为「≤ 5 分钟」是以**异步流复制**为前提。若业务要求零数据丢失，
> 需将 `synchronous_commit` 调整为 `on` + `synchronous_standby_names`，代价是写入延迟上升
> —— 设备心跳这类高频写入接口会明显变慢，需按接口分级（见 5.3.1）。

### 5.2 多活架构

AI Camera 当前阶段不追求跨城多活，采用**同城多副本 + 主备数据库**，在成本与可用性之间取平衡。

```

                                   │
        ┌──────────────────────────┼──────────────────────────┐

┌───────────────┐          ┌───────────────┐          ┌───────────────┐
```

无状态设计约束（保证多副本可随时替换）：

| 约束 | 说明 |
|:---|:---|
| 会话不落本地内存 | JWT 为无状态令牌；Casbin 策略存库 + 定时重载 |
| 上传文件不落本地盘 | 生产环境 `uploads` 挂载共享 PVC；迁移目标为对象存储 |
| 定时任务不并发重复执行 | 多副本下 cron 任务必须加分布式锁（数据库行锁或 Redis 锁） |
| 日志不落本地盘 | 生产环境日志走 stdout → Promtail → Loki；本地文件仅兜底 |

> **注意**：`internal/bootstrap` 中的 `casbin.StartAutoReload(interval)` 是多副本权限一致的
> 基础。若去掉该机制，会出现「A Pod 已放行新接口、B Pod 仍拒绝」的诡异现象。

### 5.3 数据库容灾方案

#### 5.3.1 PostgreSQL 流复制

```bash
# ── 主库配置（postgresql.conf）──
# k8s-apply-gitops/ai-camera-prod/configmaps/postgresql-primary.conf
listen_addresses = '*'
wal_level = replica
max_wal_senders = 10
wal_keep_size = 1GB
archive_mode = on
archive_command = 'wal-g wal-push %p'      # 归档到对象存储
archive_timeout = 60
hot_standby = on

# 提交策略：默认异步（性能优先）
synchronous_commit = local
# 若业务要求零丢失，改为：
# synchronous_commit = on
# synchronous_standby_names = 'ANY 1 (ai-camera-replica-*)'
```

```bash
# ── 从库基础备份（pg_basebackup）──
kubectl -n ai-camera-prod exec -it statefulset/postgresql -- \
  pg_basebackup -h postgresql-primary -U replicator -D /var/lib/postgresql/data \
    -Fp -Xs -P -R

# ── 检查复制状态（主库）──
psql -c "SELECT client_addr, state, sync_state,
                pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
         FROM pg_stat_replication;"

# ── 检查回放延迟（从库，单位秒）──
psql -c "SELECT now() - pg_last_xact_replay_timestamp() AS replay_lag;"
```

接口写入分级（决定哪些写入可以使用同步提交）：

| 接口 | 数据重要性 | 建议提交模式 |
|:---|:---|:---|
| `POST /web/risks/report` | 高（业务证据，含图片/录像 URL） | 同步提交 |
| `POST /web/alarms/report` | 高 | 同步提交 |
| `POST /web/devices/:id/heartbeat` | 低（可丢，下一次心跳即覆盖） | 异步提交 |
| `GET /web/devices/history` | 无写入 | — |
| 配置类写入（用户/角色/菜单） | 高但低频 | 同步提交 |

#### 5.3.2 自动故障切换（Patroni）

> 「设备上报中断」比「极小概率丢最后几秒数据」的业务影响更大。

### 5.4 Redis 高可用方案

Redis 当前为**预留组件**（`config/config.yaml` 已配置但业务未接入），高可用方案按后续接入
场景（验证码、令牌黑名单、WebSocket 会话、分布式锁）预设计。

```
方案选型（按规模）：

  单实例 ──────▶ 开发/测试环境：1 主，无副本
      │
      │ 数据量 < 10GB，可接受秒级中断
      ▼
  Sentinel ────▶ 生产推荐：1 主 2 从 + 3 Sentinel
      │           自动主从切换，客户端通过 Sentinel 发现主节点
      │
      │ 数据量 > 10GB，或需水平分片
      ▼
  Cluster ─────▶ 大规模：3 主 3 从，16384 槽位分片
```

接入后必须体现的容灾行为：

| 场景 | 期望行为 |
|:---|:---|
| Redis 完全不可用 | 后端**不崩溃**：令牌黑名单校验降级为放行（记 warn 日志），WebSocket 断开重连 |
| 主从切换（≤ 30s） | 客户端经 Sentinel 重新发现主节点，重试后恢复 |
| AOF 文件损坏 | 先 `redis-check-aof --fix`，无法修复时从最近 RDB 恢复 |

> **注意**：Redis 不可用时**必须降级而非报错**。当前后端未接入 Redis，接入时所有调用点
> 都要有 `if err != nil { log.Warn(...) ; /* 走兜底逻辑 */ }` 分支，不能直接 `return err`。

### 5.5 应用层容灾策略

| 策略 | 实现方式 | 涉及文件 |
|:---|:---|:---|
| **设备心跳中断检测** | 定时任务扫描 `ac_device.last_beat_dt`，超过 `info_interval * 3` 未上报则置 `status='offline'`、写 `ac_device_history`，并按 `ac_alarm_setting` 生成告警 | 定时任务调度器 + `internal/service/device/device_service.go` |
| **心跳上报幂等** | 心跳接口只做 UPDATE，不产生业务记录（除时序采样），重复上报无副作用 | `internal/api/handler/web/device_handler.go` |
| **风险上报重试容忍** | 设备侧网络抖动可能重复提交，`ac_risk_record` 以 `device_id + occurred_dt + risk_type_id` 去重 | `internal/service/risk/risk_service.go` |
| **Casbin 降级** | enforcer 初始化失败时路由层退化为放行并打印显著告警，不阻塞服务启动 | `internal/bootstrap/main.go`（`globalCasbin = nil` 分支） |
| **数据库连接失败** | 启动阶段 `initContainer` 等待库就绪；运行阶段 GORM 连接池自动重建连接 | `pkg/database/postgres.go` |
| **上传目录不可写** | 上传接口返回明确错误码，风险上报仍落库（`image_url` 为空），不因图片缺失丢弃风险 | `internal/api/handler/web/upload_handler.go` |
| **视频流不可达** | 实时监控页占位播放器展示「视频流不可用」，不影响页面其他区域 | 前端 `实时监控` 页面 |
| **升级下发失败** | `ac_device_upgrade_record` 记录失败原因，计划可重试或取消 | `internal/service/upgrade/upgrade_service.go` |

#### 视频流/录像存储的备份与对象存储迁移

这是本项目容灾的**重点风险项**：`uploads/` 目录当前落在 K8s PVC 上，存在三个问题：

1. **单点**：PVC 绑定的底层存储一旦损坏，风险图片与录像全部丢失（业务上等于证据丢失）。
2. **扩容僵化**：PVC 扩容通常需要重建，而风险图片是持续增长且不可压缩的数据。
3. **多副本难题**：若使用 `ReadWriteOnce` PVC，后端扩到多副本后只有一个 Pod 能挂载。

迁移方案（分三阶段）：

```
阶段一（当前）：PVC 挂载
    后端 Pod ──▶ PVC (ReadWriteMany) ──▶ 底层 NFS/块存储
    问题：单点、扩容僵化、备份靠 rsync 快照

阶段二（迁移中）：双写过渡
    后端 Pod ──┬─▶ PVC（主，读路径）
               └─▶ 对象存储（写路径镜像）
    动作：上传接口写本地 + 同步推对象存储；启动历史文件批量迁移任务；
          读路径按「对象存储优先，回退本地」策略

阶段三（目标）：对象存储为唯一真源
    后端 Pod ──▶ 对象存储（S3 兼容：MinIO / 阿里云 OSS / 腾讯云 COS）
    优势：无单点、弹性扩容、跨桶复制、版本控制、生命周期策略自动转冷归档
    配置变更：media.upload_dir 弃用，media.base_url 改指向 CDN 域名
```

迁移涉及的后端改动点：

| 改动 | 文件 | 说明 |
|:---|:---|:---|
| 存储抽象层 | `pkg/storage/`（新增） | 定义 `Put/Get/Delete/SignedURL` 接口，实现 Local 与 S3 两套 |

#### 物联网卡流量数据与第三方平台对账

`ac_iot_card` 的流量字段（`traffic_total` / `traffic_used` / `traffic_left` / `stat_dt`）由平台
侧记录，但**真实用量由运营商/第三方物联网卡管理平台统计**。两条链路不一致会造成：

- 平台显示流量充足，运营商侧已停机 → 设备静默离线，但平台无任何告警；
- 平台显示流量耗尽，实际尚有余额 → 误报，运维无效投入。

对账机制设计：

```
     ┌──────────────────────┐             ┌──────────────────────┐
     │  AI Camera 平台侧     │             │  第三方物联网卡平台    │
     │  ac_iot_card          │             │  (运营商 API)         │
     │  traffic_used (平台值)│             │  traffic_used (权威值)│
     └──────────┬───────────┘             └──────────┬───────────┘
                │                                    │
                │  定时任务 traffic_sync（每日 01:00） │
                │  ① 调用第三方 API 拉取权威用量        │
                └───────────────┬────────────────────┘
                                ▼
                  ┌─────────────────────────────┐
                  │  diff = |平台值 - 权威值|     │
                  ├─────────────────────────────┤
                  │  diff ≤ 阈值(50MB)           │
                  │    → 静默修正平台值 + 记日志   │
                  ├─────────────────────────────┤
                  │  diff > 阈值                 │
                  │    → 暴露 ai_camera_iot_card_ │
                  │      reconcile_diff_mb 指标   │
                  │    → 触发 IotCardReconcileDiff│
                  │      Large 告警（见 2.3）     │
                  │    → 写操作日志待人工核查      │
                  └─────────────────────────────┘
```

对账任务的实现要点：

| 要点 | 说明 |
|:---|:---|
| 调度时间 | 每日 01:00（第三方平台日结完成后），避开设备上报高峰 |
| 分批拉取 | 按区域分批调用第三方 API，单批 ≤ 200 张卡，避免触发限流 |
| 幂等 | 对账结果写入 `ac_operation_log`，重复执行不产生重复记录 |
| 失败重试 | 第三方 API 失败时指数退避重试 3 次；仍失败则记 `ai_camera_cron_job_errors_total{job="traffic_sync"}` |
| 停机预警 | 对账后若 `traffic_left < traffic_total * 5%`，直接生成 `ac_alarm_record` 并走 `ac_alarm_setting` 通知策略 |
| 换卡衔接 | 换卡（`POST /web/devices/iot-card-replace-logs`）后，新卡的首次对账必须在 24 小时内完成，避免新卡用量盲区 |

> **注意**：对账差异**只修正平台展示值，不反向写入第三方平台**。第三方平台是权威数据源，
> 平台侧字段仅用于本地展示与预警。

## 6. 数据备份与恢复

### 6.1 备份策略

| 备份类型 | 对象 | 频率 | 保留期 | 存储位置 | 加密 |
|:---|:---|:---|:---:|:---|:---:|
| 全量备份 | PostgreSQL 业务库 | 每日 02:00 | 30 天 | 对象存储 `backup/pg/daily/` | ✅ |
| 增量备份 | WAL 归档 | 持续（`archive_timeout=60`） | 7 天 | 对象存储 `backup/pg/wal/` | ✅ |
| 逻辑备份 | 关键表（`ac_user`/`ac_role`/`ac_menu`/`ac_role_menu_rel`） | 每日 02:30 | 90 天 | 对象存储 `backup/pg/logical/` | ✅ |
| 文件备份 | `uploads/` 目录 | 每日 03:00（增量） | 30 天 | 对象存储 `backup/uploads/` | — |
| 配置备份 | ConfigMap / Secret | 变更即提交 | 永久 | GitOps 仓库 | ✅（SOPS） |
| 版本备份 | 固件 / AI 模型原始件 | 上传即同步 | 永久 | 对象存储 `release/` | — |

> **注意**：全量备份保留 30 天与风险记录保留 3 年是两个不同概念 —— 备份用于**灾难恢复**
> （回到某个时间点），业务数据保留用于**合规审计**（查询历史记录）。后者靠数据库自身的
> 数据保留策略，不依赖备份文件。

### 6.2 备份脚本

```bash
# backend/scripts/backup.sh（生产备份入口，由 K8s CronJob 调用）
#!/bin/bash
# ================================================================
# AI Camera 生产备份脚本
# 执行环境: K8s CronJob（namespace: ai-camera-prod）
# 依赖: kubectl / pg_dump / pg_restore / mc（对象存储 CLI）
# ================================================================
set -euo pipefail

DATE=$(date +%F)
TS=$(date +%Y%m%d_%H%M%S)
NAMESPACE="ai-camera-prod"
DB_NAME="ai_camera_prod"
DB_USER="boticz"
BACKUP_BUCKET="s3://ai-camera-backup"
WORKDIR="/tmp/ai-camera-backup"

mkdir -p "${WORKDIR}"

echo "▶ [1/5] 数据库全量备份 ${DB_NAME} @ ${TS}"
kubectl -n "${NAMESPACE}" exec statefulset/postgresql -- \
  pg_dump -U "${DB_USER}" -d "${DB_NAME}" -Fc \
    -f "/tmp/${DB_NAME}_${TS}.dump"

kubectl -n "${NAMESPACE}" cp \
  "postgresql-0:/tmp/${DB_NAME}_${TS}.dump" \
  "${WORKDIR}/${DB_NAME}_${TS}.dump"

echo "▶ [2/5] 关键表逻辑备份（权限体系，恢复优先级最高）"
kubectl -n "${NAMESPACE}" exec statefulset/postgresql -- \
  pg_dump -U "${DB_USER}" -d "${DB_NAME}" \
    -t ac_user -t ac_role -t ac_menu -t ac_menu_api \
    -t ac_dept -t ac_post \
    -t ac_user_role_rel -t ac_dept_role_rel -t ac_post_role_rel \
    -t ac_role_menu_rel -t ac_api_key \
    -Fc -f "/tmp/rbac_${TS}.dump"

kubectl -n "${NAMESPACE}" cp \
  "postgresql-0:/tmp/rbac_${TS}.dump" \
  "${WORKDIR}/rbac_${TS}.dump"

echo "▶ [3/5] 上传文件增量同步（风险图片 / 录像 / 音频 / 固件 / 模型）"
rsync -az --delete \
  /mnt/ai-camera-uploads/ \
  "${WORKDIR}/uploads/"

echo "▶ [4/5] 上传对象存储（服务端加密）"
mc cp --encrypt-key "${BACKUP_ENCRYPT_KEY}" \
  "${WORKDIR}/${DB_NAME}_${TS}.dump" "${BACKUP_BUCKET}/pg/daily/${DATE}/"
mc cp --encrypt-key "${BACKUP_ENCRYPT_KEY}" \
  "${WORKDIR}/rbac_${TS}.dump" "${BACKUP_BUCKET}/pg/logical/${DATE}/"
mc mirror --overwrite \
  "${WORKDIR}/uploads/" "${BACKUP_BUCKET}/uploads/${DATE}/"

echo "▶ [5/5] 清理 30 天前的本地临时文件"
find "${WORKDIR}" -type f -mtime +30 -delete

echo "✅ 备份完成：${BACKUP_BUCKET}/pg/daily/${DATE}/${DB_NAME}_${TS}.dump"
```

### 6.4 备份验证

备份「存在」不等于备份「可用」。自动验证由每日 CronJob 在备份完成后追加执行：

```bash
# backend/scripts/verify-backup.sh（每日 04:00 执行）
#!/bin/bash
set -euo pipefail

LATEST=$(mc ls --json "s3://ai-camera-backup/pg/daily/$(date +%F)/" \
  | grep '\.dump"' | tail -1 | sed 's/.*"key":"//;s/".*//')

echo "▶ 校验备份文件: ${LATEST}"

# 1. 文件完整性：pg_restore --list 能列出内容说明归档未损坏
mc cp "s3://ai-camera-backup/${LATEST}" /tmp/verify.dump
pg_restore --list /tmp/verify.dump > /dev/null || {
  echo "❌ 备份文件损坏，归档无法解析"; exit 1;
}

# 2. 表覆盖率：备份中包含的 ac_ 表数量
TBL_CNT=$(pg_restore --list /tmp/verify.dump | grep -c 'TABLE DATA public ac_' || true)
echo "  备份包含 ${TBL_CNT} 张 ac_ 业务表"
if [ "${TBL_CNT}" -lt 35 ]; then
  echo "❌ 备份表数量不足（期望 ≥ 35）"; exit 1
fi

# 3. 真实恢复验证：恢复到临时库并抽查行数
psql -h 192.168.1.227 -U boticz -c "DROP DATABASE IF EXISTS ai_camera_verify;" postgres
psql -h 192.168.1.227 -U boticz -c "CREATE DATABASE ai_camera_verify;" postgres
pg_restore -h 192.168.1.227 -U boticz -d ai_camera_verify --no-owner /tmp/verify.dump

for t in ac_user ac_role ac_menu ac_device; do
  n=$(psql -h 192.168.1.227 -U boticz -d ai_camera_verify -tAc "SELECT count(*) FROM ${t};")
  echo "  ${t}: ${n} 行"
  [ "${n}" -gt 0 ] || { echo "❌ ${t} 为空"; exit 1; }
done

psql -h 192.168.1.227 -U boticz -c "DROP DATABASE ai_camera_verify;" postgres
rm -f /tmp/verify.dump

echo "✅ 备份验证通过"
```

## 7. 故障演练与应急预案

| 演练场景 | 注入方式 | 预期行为 | 验证点 | 频率 |
|:---|:---|:---|:---|:---|
| **后端 Pod 全部 Kill** | `kubectl delete pod -l app=ai-camera-backend` | Deployment 自动重建，2 分钟内恢复 | 设备心跳中断告警是否在 10 分钟内触发；客户端重试是否成功 | 每季度 |
| **数据库主库故障** | 删除 `postgresql-0` Pod | Patroni 在 30s 内提升备库，写入恢复 | 后端连接池自动重连；RPO 是否符合 5.1 目标 | 每季度 |
| **设备批量离线** | 在测试环境停止模拟设备上报 | `DeviceHeartbeatStopped` 告警触发 | 告警延迟、值班响应时间 | 每半年 |
| **上传目录写满** | 用 `fallocate` 填充 PVC 至 90% | `UploadsDiskHigh` 告警触发；上传失败但风险仍落库 | 风险记录是否因图片失败而丢失 | 每半年 |
| **第三方推送不可用** | 将个推 `app_key` 改为错误值 | `ThirdPartyFailure` 告警触发；站内通知仍正常 | 存在降级通道 | 每半年 |
| **Casbin 策略表损坏** | 清空 `casbin_rule` 表后重启 | 服务启动不阻塞，打印显著告警；管理接口可重新授权 | 是否有放行保护 | 每季度 |
| **网络分区（Ingress 不可达）** | 修改 Traefik Service selector | 客户端报错但服务端无异常日志 | 区分「业务故障」与「入口故障」 | 每半年 |

应急预案关键条目：

| 故障现象 | 首要排查 | 应急动作 | 回滚方式 |
|:---|:---|:---|:---|
| 全平台无数据（设备不在线） | 后端 `/health` 与 `up` 指标 | ① 确认服务是否存活 ② 确认数据库连通 ③ 确认 Traefik 路由 | `kubectl rollout undo` |
| 心跳接口大量 401 | `ai_camera_device_heartbeat_errors_total{reason="invalid_key"}` | 检查 `ac_api_key` 是否被误停用；重新生成并下发 Key | 启用历史 Key |
| 风险列表为空但设备在上报 | 风险上报接口日志与 `ai_camera_risk_reported_total` | 检查 `risk_type_id` 外键是否存在、数据权限是否过滤掉全部数据 | 修复数据权限配置 |
| 接口整体变慢 | Casbin 校验耗时、慢查询日志 | 检查策略表行数是否膨胀；检查数据库索引与连接数 | 缩短 `auto_load_interval` 无效，需重建策略 |
| 上传全部失败 | PVC 状态与 `ai_camera_uploads_disk_used_ratio` | 扩容 PVC 或清理过期录像 | 恢复上一版本镜像 |
| 权限变更不生效 | Casbin 策略是否已 `ReloadPolicy()` | 手动调用重载或等待 `auto_load_interval` 到期 | 重启 Pod 强制重载 |

## 10. 附录

### 10.1 关键告警检查清单

值班工程师收到告警后的标准排查顺序：

```
【P0】BackendDown / 全平台设备心跳中断
  □ 1. kubectl -n ai-camera-prod get pods -l app=ai-camera-backend    → Pod 是否 Running
  □ 2. kubectl -n ai-camera-prod logs --tail=100 deploy/ai-camera-backend  → 启动报错内容
  □ 3. kubectl -n ai-camera-prod exec deploy/ai-camera-backend -- wget -qO- localhost:8080/health
  □ 4. 数据库是否可连（initContainer 是否卡在 wait-for-db）
  □ 5. ConfigMap 是否被误改（CONFIG_PATH 指向的文件是否存在）
  □ 6. 指标 up{job="ai-camera-backend"} 是否为 0（确认是服务问题还是采集问题）

【P0】PostgresPrimaryDown
  □ 1. patronictl list 查看集群状态与 Leader
  □ 2. 是否已自动切换（备库变主库，约 30s）
  □ 3. 后端连接池是否自动重连（观察错误日志是否停止）
  □ 4. 复制延迟是否在切换后快速收敛
  □ 5. 记录 RPO（最后一条成功写入的时间）

【P1】DeviceOnlineRateLow / DeviceRegionAllOffline
  □ 1. 是平台问题还是设备问题？（看心跳接口 QPS 是否也下跌）
  □ 2. 心跳接口 QPS 正常但在线率低 → 设备侧或网络侧问题
  □ 3. 心跳接口 QPS 也下跌 → 平台侧问题（限流、ApiKey、路由）
  □ 4. 检查 ai_camera_device_heartbeat_errors_total 的 reason 分布
  □ 5. 联系现场确认设备电源与网络状态

【P1】UploadsDiskHigh / PVCNearlyFull
  □ 1. 确认增长来源（风险图片 vs 录像 vs 固件）
  □ 2. 清理超过 90 天的录像文件（风险图片不清理，保留 3 年）
  □ 3. 扩容 PVC（注意 ReadWriteMany 底层存储是否支持在线扩容）
  □ 4. 加速对象存储迁移（见 5.5 节）

【P2】CasbinDenySpike
  □ 1. 按 user_name 聚合，确认是单用户还是多用户
  □ 2. 单用户 → 权限配置问题（角色菜单未授权该接口）
  □ 3. 多用户集中同一 path → 接口路径未登记到 ac_menu_api，正常用户被拒
  □ 4. 来源 IP 分散且用户不存在 → 凭据泄露探测，检查访问日志

【P2】ThirdPartyFailure
  □ 1. 确认 provider（getui / sms）与失败错误码
  □ 2. 个推：检查 app_key / master_secret 是否过期
  □ 3. 短信：检查腾讯云账户余额与签名审核状态
  □ 4. 站内通知（ac_notification）是否仍正常写入（降级通道是否可用）
```

### 10.3 灾难恢复场景时间线

**场景 A：后端服务全量故障（Pod 全部异常）**

```
T+0min    监控告警 BackendDown 触发（Prometheus 采集到 up==0，持续 1 分钟）
T+1min    AlertManager 按 critical 路由推送：电话 + 短信 + 企业微信
T+3min    值班工程师确认告警，开始排查（get pods / logs）
T+5min    定位根因（示例：ConfigMap 被误改导致启动失败）
T+6min    修复 ConfigMap，kubectl rollout restart deploy/ai-camera-backend
T+8min    新 Pod Running，readinessProbe 通过，Service 开始转发流量
T+9min    /health 返回 200，up 指标恢复为 1
T+10min   设备心跳恢复上报，ai_camera_device_heartbeat_total 速率回升
T+12min   设备在线率回到 90% 以上（含设备重连与心跳周期等待）
T+15min   告警自动恢复（resolve），监控面板全绿
T+30min   补充事故记录，评估设备侧缓存数据是否补传成功
T+24h     输出复盘报告，明确「ConfigMap 变更需双人复核」的改进项

实际 RTO ≈ 9 分钟（服务恢复） / 12 分钟（业务恢复）
```

**场景 B：数据库主库故障（Patroni 自动切换）**

```
T+0s      主库 Pod 异常，PostgreSQL 进程不可达
T+10s     Patroni 检测到主库失去锁租约（ttl=30s 的探测周期）
T+20s     etcd 中 Leader key 过期
T+25s     Patroni 触发选举，备库（maximum_lag_on_failover=1MB 内）被提升为新主库
T+30s     新主库完成提升，开始接受写入
T+35s     后端 GORM 连接池检测到旧连接失效，自动重连到新的 Service 端点
T+40s     写入恢复正常，ai_camera_http_requests_total{status=~"5.."} 停止增长
T+45s     告警 BackendHighErrorRate 自动恢复
T+2min    旧主库 Pod 重建，作为新备库加入并开始追平（pg_rewind）
T+3min    复制延迟收敛到 0，pg_replication_lag_seconds 恢复正常
T+15min   完成 RPO 评估：确认丢失的数据窗口
T+1h      检查是否有业务数据需要人工补录（风险上报通常由设备侧重传）

实际 RTO ≈ 40 秒（数据库层面） / 45 秒（应用层面）
实际 RPO ≈ 0 秒（synchronous_mode: true 下无数据丢失；降级为异步时可能丢失最后几秒）
```

**场景 C：上传存储写满（影响风险图片与录像）**

```
T+0h      存储增长超过 85%，UploadsDiskHigh 告警触发（critical）
T+5min    值班工程师确认告警，查询各类型文件占用
T+10min   发现录像文件占比 78%
T+15min   暂停录像写入（前端提示「录像暂不可用，图片正常」），损失面收敛到录像
T+30min   清理超过 90 天保留期的录像，释放空间至 60% 以下
T+45min   恢复录像写入
T+1h      告警自动恢复
T+1d      启动对象存储迁移（见 5.5 节），该类问题不再复现
T+3d      完成历史文件批量迁移，PVC 使用率降至 20% 以下

实际 RTO ≈ 45 分钟（录像功能恢复）
业务影响：约 30 分钟的录像缺失窗口；风险图片不受影响（保留期 3 年，不参与清理）
```

**场景 D：AII 设备批量离线（现场网络中断）**

```
T+0min    某区域现场网络中断，该区域设备全部停止心跳上报
T+3min    (窗口期内) 平台无任何异常告警 —— 设备不上报不产生任何 HTTP 请求
T+10min   Prometheus 规则 DeviceRegionAllOffline 满足 for: 10m 条件，告警触发
          （若为全平台离线，DeviceHeartbeatStopped 在 10 分钟后触发）
T+11min   AlertManager 按 team=ops 路由推送至设备运维组
T+15min   值班工程师确认为某区域集中离线（而非全平台），判定为现场网络问题
T+16min   联系现场确认网络中断，通知客户
T+35min   现场网络恢复，设备按 info_interval 周期陆续恢复心跳
T+40min   区域在线率回到 90%，告警自动恢复
T+1h      检查设备侧缓存的风险数据是否补传成功（设备断网期间识别到的风险）

关键点：检测延迟 = 规则 for 时长（10 分钟）+ 心跳周期（默认 60 秒）
        若需更快发现，可对高价值区域单独配置更短的 for 时长（如 5 分钟）
        但需同步收紧 ai_camera_device_online_count 的判定窗口，避免频繁误报
```
