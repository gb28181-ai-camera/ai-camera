## 1. 部署架构

AI Camera 平台采用「单后端服务 + 三前端入口」的部署形态：后端 `ai-camera-backend` 一个
Deployment 承载 `/web/*`（管理后台 + 官网）与 `/app/*`（移动端）两套路由；前端拆分为
管理后台静态站、官网静态站两个 Nginx 容器；移动端 App 与桌面端 Desktop 不进集群，走
文件分发（应用市场 / 安装包下载）。

v0.2.0 接入国标视频后，另有两个**可选**组件（仅在需要 GB/T 28181 时部署，见 §9）：

- `ai-camera-sipsvc`：SIP 信令服务，**副本固定 1**，监听 5060/udp+tcp；
- `ai-camera-zlm`（ZLMediaKit）：媒体节点，单端口 `10000/udp+tcp` 收流，对外提供
  WebRTC / HTTP-FLV / HLS。

> 当前实现中，若 `sipsvc` 与 `backend` 分进程部署，API 进程的 SIP 控制面为空，
> 播放 / 云台 / 回放等 HTTP 触发的命令不可用；单进程内嵌模式（`GB28181_EMBEDDED=true`）
> 是当前推荐形态。

### 1.1 端口与访问面

| 组件 | 集群内端口 | 对外入口 | 说明 |
|:---|:----:|:---|:---|
| `ai-camera-backend` | 8080 | `https://api.ai-camera.com` | 生产环境端口；开发 8080 / 测试 8081 |
| `ai-camera-admin` | 8080 | `https://admin.ai-camera.com` | 管理后台静态站（Vite `dist/`，base `/admin/`） |
| `ai-camera-website` | 8080 | `https://www.ai-camera.com` | 官网介绍页静态站（Vite `dist-website/`，base `/`） |

| Redis | 6379 | 集群内 | 预留：验证码、令牌黑名单、WebSocket 会话 |
| `ai-camera-sipsvc` | 5060/udp + 5060/tcp | **设备可达的网络** | 国标 SIP 信令（v0.2.0，副本固定 1） |
| ZLMediaKit（`zlm`） | 10000/udp + 10000/tcp | **设备可达的网络** | 国标单端口收流（v0.2.0） |
| ZLMediaKit（`zlm`） | 8082 → 容器 80 | 浏览器 / 后端 | HTTP-FLV / HLS / WHEP / REST |
| ZLMediaKit（`zlm`） | 8000/udp | 浏览器 | WebRTC 收流 |

> **注意**：`ai-camera-admin` 与 `ai-camera-website` 是同一份前端工程的两个构建产物，
> 通过 `npm run build:admin` 与 `npm run build:website` 分别产出，**不可混用** —— 管理后台
> 资源路径以 `/admin/` 为根，官网以 `/` 为根，混用会导致静态资源 404。

## 3. Docker镜像构建

后端与两个前端各有独立 Dockerfile。后端 Dockerfile 位于 `backend/Dockerfile`
（`--prod` 时用 `backend/Dockerfile.prod`），两个前端 Dockerfile 位于 `frontend/` 下。

### 3.1 后端Dockerfile

```dockerfile
# backend/Dockerfile
# 多阶段构建：builder 编译静态二进制 → runtime 仅保留二进制与配置模板
FROM golang:1.26-alpine AS builder

WORKDIR /build

# 先复制依赖描述文件，利用层缓存加速重复构建
COPY go.mod go.sum ./
RUN go env -w GOPROXY=https://goproxy.cn,direct && go mod download

# 复制源码并编译（CGO_ENABLED=0 保证静态链接，可在 alpine 直接运行）
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags "-s -w" \
      -o /build/server ./cmd/server/main.go

# ── 运行阶段 ──
FROM alpine:3.20

RUN apk add --no-cache ca-certificates tzdata curl && \
    cp /usr/share/zoneinfo/Asia/Shanghai /etc/localtime && \
    echo "Asia/Shanghai" > /etc/timezone

WORKDIR /app

# 二进制、Casbin 模型、Swagger 文档（Swagger 关闭时可不复制）
COPY --from=builder /build/server            /app/server
COPY --from=builder /build/config/rbac_model.conf /app/config/rbac_model.conf
COPY --from=builder /build/docs/web          /app/docs/web

# 上传目录与日志目录（生产建议挂载 PVC）
RUN mkdir -p /app/uploads /app/logs

EXPOSE 8080

# 健康检查：/health 为内联端点，不经过鉴权
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -fsS http://127.0.0.1:8080/health || exit 1

CMD ["/app/server"]
```

```dockerfile
# backend/Dockerfile.prod
# 生产镜像：与 Dockerfile 一致，差异为镜像更精简 + 关闭 Swagger 由 ConfigMap 控制
FROM golang:1.26-alpine AS builder

WORKDIR /build
COPY go.mod go.sum ./
RUN go env -w GOPROXY=https://goproxy.cn,direct && go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags "-s -w" \
      -o /build/server ./cmd/server/main.go

FROM alpine:3.20
RUN apk add --no-cache ca-certificates tzdata curl
WORKDIR /app
COPY --from=builder /build/server                 /app/server
COPY --from=builder /build/config/rbac_model.conf /app/config/rbac_model.conf
RUN mkdir -p /app/uploads /app/logs
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -fsS http://127.0.0.1:8080/health || exit 1
CMD ["/app/server"]
```

构建与推送：

```bash
# 开发镜像（推送 dev-registry.boticz.com:5000）
cd backend && bash scripts/build.sh

# 生产镜像（推送 registry.boticz.cn:5000）
cd backend && bash scripts/build.sh --prod
```

### 3.2 前端管理后台 Dockerfile

前端镜像采用**单镜像双站点**：一个 nginx 容器同时托管管理后台（`/admin/`）与官网（`/`）。
这与 K8s 清单中的两个独立 Deployment 并不冲突 —— 生产环境用同一镜像起两个 Deployment，
分别以 `Traefik` 路由到不同 Host；也可以只部署一个容器走路径区分。

```dockerfile
# frontend/Dockerfile
# ============================================================================
# AI Camera 前端镜像
# 一个 npm 工程、两个 Web 构建目标：
#   - 管理后台   index.html    → dist/          （base /admin/）
#   - 官网介绍页 website.html  → dist-website/  （base /）
# 镜像内由 nginx 同时托管两者：/admin/ → 管理后台，/ → 官网。
# ============================================================================

FROM node:22-alpine AS builder

WORKDIR /app

# 国内镜像加速
RUN sed -i 's/dl-cdn.alpinelinux.org/mirrors.aliyun.com/g' /etc/apk/repositories
RUN npm config set registry https://registry.npmmirror.com
ENV ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/

# 依赖层单独缓存
COPY package.json ./
RUN npm install

COPY . .

# build:admin 含 tsc --noEmit；build:website 仅 vite build
RUN npm run build

# ============================================================
# 生产镜像：nginx:alpine 托管静态文件
# ============================================================
FROM nginx:alpine

RUN sed -i 's/dl-cdn.alpinelinux.org/mirrors.aliyun.com/g' /etc/apk/repositories

# 官网产物放到站点根，管理后台产物放到 /admin 子目录
COPY --from=builder /app/dist-website /usr/share/nginx/html
COPY --from=builder /app/dist /usr/share/nginx/html/admin

COPY nginx.conf /etc/nginx/conf.d/default.conf

EXPOSE 8080

CMD ["nginx", "-g", "daemon off;"]
```

```nginx
# frontend/nginx.conf
server {
    listen 8080;
    server_name localhost;

    root /usr/share/nginx/html;
    index index.html;

    # Gzip 压缩
    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml application/xml image/svg+xml;
    gzip_min_length 256;

    # 管理后台（base /admin/，产物位于 /usr/share/nginx/html/admin）
    # 注意：alias 路径片段会被替换为 location 前缀，故末尾均需带 `/`
    location /admin/ {
        alias /usr/share/nginx/html/admin/;
        # SPA 路由回退；回退 URI 重新匹配本 location，alias 解析为 .../admin/index.html
        try_files $uri $uri/ /admin/index.html;
    }

    # 管理后台带 hash 的静态资源强缓存
    location /admin/assets/ {
        alias /usr/share/nginx/html/admin/assets/;
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 官网介绍页（base /，产物位于站点根）
    location / {
        try_files $uri $uri/ /index.html;
    }

    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 后端接口反向代理（如由本容器统一入口时启用，按需调整 upstream）
    # location /web/ { proxy_pass http://backend:8080; proxy_set_header Host $host; }
    # location /app/ { proxy_pass http://backend:8080; proxy_set_header Host $host; }
}
```

> **注意**：`alias` 指令的路径片段会被替换为 `location` 前缀，因此 `location /admin/` 与
> `alias` 的**末尾都必须带 `/`**。`try_files` 的兜底 URI 写 `/admin/index.html`（绝对路径）
> 而非 `index.html`，否则会解析到站点根目录的官网 `index.html`。

构建与运行：

```bash
# 单镜像双站点
cd frontend && docker build -t ai-camera-frontend .
cd frontend && docker run -p 8080:8080 ai-camera-frontend

# 验证：/ 返回官网，/admin/ 返回管理后台
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/admin/
```

### 3.3 前端官网 Dockerfile

官网也可独立打成**只含官网**的镜像（体积更小，适合官网单独部署到 CDN 边缘或独立域名）：

```dockerfile
# frontend/Dockerfile.website
# 仅构建官网入口 website.html（base /），产物 dist-website/
FROM node:22-alpine AS builder

WORKDIR /app
RUN sed -i 's/dl-cdn.alpinelinux.org/mirrors.aliyun.com/g' /etc/apk/repositories
RUN npm config set registry https://registry.npmmirror.com

COPY package.json ./
RUN npm install
COPY . .
RUN npm run build:website

FROM nginx:alpine
RUN sed -i 's/dl-cdn.alpinelinux.org/mirrors.aliyun.com/g' /etc/apk/repositories

COPY --from=builder /app/dist-website /usr/share/nginx/html
COPY nginx.website.conf /etc/nginx/conf.d/default.conf

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

```bash
cd frontend && docker build -f Dockerfile.website -t ai-camera-website .
cd frontend && docker run -p 8081:80 ai-camera-website
```

> **注意**：官网容器**不代理后端** —— 官网为纯静态展示页，不调用任何 API。
> 官网内的「登录」入口为跳转到管理后台域的绝对链接（`/admin/`）。

### 3.4 前端Desktop (Electron) 构建

桌面端与管理后台共用同一份 `frontend/` 工程，通过 Electron Forge + Vite 插件打包，
配置见 `frontend/forge.config.ts` 与 `frontend/vite.renderer.config.ts`。

```bash
# 桌面端开发模式（Electron 主进程 + 渲染进程热更新）
cd frontend && npm run dev:desktop

# 仅打包不生成安装包（产物在 out/，用于本地验证）
cd frontend && npm run package:desktop

# 生成 NSIS 安装包（Windows）
cd frontend && npm run make:win

# 生成 DMG（macOS）/ DEB+RPM（Linux）
cd frontend && npm run make:mac
cd frontend && npm run make:linux
```

```bash
# frontend/scripts/build-desktop.sh（三平台打包 + 一致性校验的推荐入口）
# 关键约束：
#   1. package.json 的 version 必须与发布版本一致，否则安装后反复提示「发现新版本」
```

## 4. Kubernetes部署清单

### 4.1 后端Deployment

```yaml
# k8s-apply-gitops/ai-camera-prod/deployments/ai-camera-backend.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai-camera-backend
  namespace: ai-camera-prod
  labels:
    app: ai-camera-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ai-camera-backend
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0          # 先起新 Pod 再停旧 Pod，保证零中断
  template:
    metadata:
      labels:
        app: ai-camera-backend
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "8080"
        prometheus.io/path: "/metrics"
    spec:
      initContainers:
        # 等待数据库就绪：AutoMigrate 在启动时执行，库不可用会导致启动失败
        - name: wait-for-db
          image: postgres:16-alpine
          command:
            - sh
            - -c
            - |
              until pg_isready -h postgresql-service.postgresql.svc.cluster.local -p 5432; do
                echo "等待 PostgreSQL 就绪..."; sleep 2
              done
      containers:
        - name: backend
          image: registry.boticz.cn:5000/boticz/ai-camera-api:latest
          imagePullPolicy: Always
          ports:
            - name: http
              containerPort: 8080
          env:
            # 切换配置文件的唯一开关：dev=config/config.yaml  test=config/config-test.yaml
            - name: CONFIG_PATH
              value: /app/config/config.yaml
            - name: TZ
              value: Asia/Shanghai
          volumeMounts:
            - name: config
              mountPath: /app/config
              readOnly: true
            - name: uploads
              mountPath: /app/uploads          # 风险图片 / 录像 / 音频 / 固件 / 模型
            - name: logs
              mountPath: /app/logs
          resources:
            requests:
              cpu: 200m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 1Gi
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 10
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 30
```

### 4.2 自动扩缩（HPA）

```yaml
# k8s-apply-gitops/ai-camera-prod/hpa/ai-camera-backend-hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: ai-camera-backend-hpa
  namespace: ai-camera-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: ai-camera-backend
  minReplicas: 2
  maxReplicas: 8
  metrics:
    # 1. CPU：通用负载信号
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    # 2. 内存：风险图片上传与统计聚合会拉高内存占用
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Percent
          value: 100
          periodSeconds: 60       # 每分钟最多翻倍
        - type: Pods
          value: 2
          periodSeconds: 60
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300   # 冷却 5 分钟，避免设备上报潮汐导致抖动
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120
```

> **注意**：设备心跳按 `info_interval`（默认 60 秒，`ac_device.info_interval`）周期到达，
> 500 台设备约 8 QPS 的稳态流量。真正的扩容触发点不是心跳，而是**风险上报后的列表刷新**
> 与**首页看板/可视化大屏的聚合查询** —— 因此 HPA 的 CPU 阈值不宜过高。

## 7. 备份策略

| 对象 | 方式 | 频率 | 保留 | 存放位置 |
|:---|:---|:---|:---|:---|
| PostgreSQL 全量 | `pg_dump -Fc` | 每日 02:00 | 30 天 | 对象存储 `backup/pg/daily/` |
| PostgreSQL 归档 | WAL 归档（`archive_mode=on`） | 持续 | 7 天 | 对象存储 `backup/pg/wal/` |
| K8s 资源清单 | `kubectl get all -o yaml` | 每次发布前 | 90 天 | GitOps 仓库 |
| `uploads/` 目录 | `rsync` 增量同步 | 每日 03:00 | 30 天 | 对象存储 `backup/uploads/` |
| ConfigMap / Secret | 加密后入 GitOps | 变更即提交 | 永久 | GitOps 仓库 |
| 固件 / AI 模型文件 | 上传时同步一份原始件 | 上传即同步 | 永久 | 对象存储 `release/firmware/` |

```bash
# 数据库备份（生产库，容器内执行）
kubectl -n ai-camera-prod exec -it statefulset/postgresql -- \
  pg_dump -U boticz -d ai_camera_prod -Fc -f /tmp/ai_camera_prod_$(date +%F).dump

kubectl -n ai-camera-prod cp \
  postgresql-0:/tmp/ai_camera_prod_$(date +%F).dump \
  /backup/pg/daily/ai_camera_prod_$(date +%F).dump

# uploads 目录增量备份（PVC 已挂载到 NFS 时可直接 rsync）
rsync -av --delete /mnt/ai-camera-uploads/ /backup/uploads/$(date +%F)/

# 恢复演练（在独立库中还原，禁止直接覆盖生产库）
createdb -h 192.168.1.227 -U boticz ai_camera_restore_drill
pg_restore -h 192.168.1.227 -U boticz -d ai_camera_restore_drill -c /backup/pg/daily/ai_camera_prod_2026-09-20.dump
```

> **注意**：`uploads/` 目录当前落在 PVC 上，备份粒度是文件级；迁移到对象存储后（见
> [02-监控与容灾.md](02-监控与容灾.md) 第 5.5 节），备份策略应改为**跨桶复制 + 版本控制**，
> 不再依赖 rsync 快照。

## 9. 国标视频（GB/T 28181）部署

> 适用版本：v0.2.0。对应实现：`backend/cmd/sipsvc`、`backend/internal/gb28181/`、
> `deploy/zlm/`、`docker-compose.yml` 的 `gb28181` profile。

### 9.1 组件与端口

| 组件 | 端口 | 关键约束 |
|:---|:---|:---|
| `sipsvc` | **5060/udp + 5060/tcp** | **副本固定 1**；默认 `transport=UDP`，需要 TCP 时设 `GB28181_SIP_TRANSPORT=BOTH` |
| `zlm`（收流） | **10000/udp + 10000/tcp** | 单端口模式，**只发布 10000**，不需要 30000–30500 端口段 |
| `zlm`（HTTP） | 8082 → 容器 80 | HTTP-FLV / HLS / WHEP / REST API |
| `zlm`（WebRTC） | 8000/udp | 浏览器 WebRTC 收流 |
| `backend` | 8080（测试 8081） | `/web/gb/*`、`/app/gb/*`、`/media/hook/*` |

启动：

```bash
# 只起基础设施
docker compose up -d

# 起 ZLM + sipsvc（需要设备接入时）
docker compose --profile gb28181 up -d

# 全量（postgres + redis + backend + frontend + zlm + sipsvc）
docker compose --profile full --profile gb28181 up -d
```

### 9.2 `sipsvc`：单副本与 SIP 通告地址

```yaml
sipsvc:
  command: ["/app/ai-camera-sipsvc"]   # 复用 backend 镜像，不单独构建
  ports:
    - "5060:5060/udp"
    - "5060:5060/tcp"
  environment:
    GB28181_ENABLED: "true"
    GB28181_SIP_LISTEN_IP: "0.0.0.0"
    GB28181_SIP_PORT: "5060"
    GB28181_SIP_ADVERTISE_IP: "<设备可达的局域网 IP>"
    GB28181_MEDIA_PUBLIC_IP: "<设备可达的局域网 IP>"
    GB28181_MEDIA_RTP_PROXY_PORT: "10000"
```

**`SIP_ADVERTISE_IP` 必须是设备可达的局域网 IP**，不能是 `127.0.0.1`、容器内网 IP
或 NAT 外网 IP（除非已做端口映射与 SIP ALG）。它同时用于：

1. SIP 报文的 Via / Contact（设备把响应与下行指令发回这里）；
2. SDP 的 `c=` / `o=`（设备往这里推 RTP）。

写错的典型表现：**设备能注册、目录也能同步，但点播黑屏** —— 信令通了，RTP 打到了错误地址。
多网卡场景可在设备上单独覆盖 `ac_device.local_ip` / `ac_device.sdp_ip`。

> **单副本原因**：SIP 事务、TCP 连接与 INVITE 会话状态都在进程内存；设备注册后绑定到具体节点。
> 横向扩容需要 Redis 注册表 + 进程间 RPC，本期不做。

> **分进程限制**：`cmd/server` 与 `cmd/sipsvc` 分开部署时，API 进程的
> `control.Default()` 为 nil，播放 / 云台 / 回放等 HTTP 触发的 SIP 命令会返回
> 「信令服务未启动」。当前可用形态是单进程内嵌（见 §9.6）。

### 9.3 ZLM 单端口收流

`deploy/zlm/config.ini` 的 `[rtp_proxy]`：

```ini
[rtp_proxy]
port=10000
; 刻意不设 port_range
```

- **只发布 10000**（udp + tcp）。设备统一向该端口打流，ZLM 按 SSRC 自动建流；
  **不需要** 30000–30500 的端口段，也不需要平台调用 `openRtpServer`。
- `port_range` 刻意留空：设了会让误用的 `openRtpServer(port=0)` 从端口段取端口，
  实测可能触发 ZLM 内部断言失败并波及 socket 分配。
- **TCP-ACTIVE 与单端口模式互斥**：单端口不创建流级 RTP server，ZLM 无法主动拨号。

### 9.4 ZLM `[hook]` 必须由渲染脚本生成

**实测结论：ZLM 不支持环境变量替换**（`${VAR}` 会原样保留在配置里）。
因此不能把 secret 与 hook 地址直接写进 `config.ini` 模板，否则会出现
「本地联调正常、容器部署全部回调 401」。

做法：

1. `deploy/zlm/config.ini` 作为**模板**，只读挂载到 `/opt/media/conf/config.tmpl`；
2. `/opt/media/render-config.sh` 用 `awk` 把 `__ZLM_SECRET__`、`__HOOK_BASE__`
   替换为环境变量值，输出到容器可写层 `/opt/media/conf/config.ini`；
3. 启动 ZLM 使用渲染后的文件。

```bash
ZLM_SECRET='<32 位以上随机串>' \
ZLM_HOOK_BASE='http://host.docker.internal:8081' \
docker compose --profile gb28181 up -d zlm
```

- 渲染脚本会校验 secret 只含 `A-Z a-z 0-9 . _ -`（避免 `awk` 替换语义与 URL 编码问题）；
- 输出**不写回**模板挂载点，避免把某次部署的密钥固化进仓库；
- `on_media_arrival` **不是** ZLM 回调，不要配置（它是 WVP 的内部事件）。

### 9.5 `ZLM_SECRET` 三处一致

以下三处必须是**同一个字符串**，否则 hook 全部被拒：

| # | 位置 | 说明 |
|:--:|:---|:---|
| 1 | `.env` 的 `ZLM_SECRET` | compose 注入 ZLM 渲染脚本 |
| 2 | `ac_gb_media_server.secret` | 平台校验 hook 的 `secret` 查询参数 |
| 3 | 渲染进 ZLM 的 `[api] secret` 与各 `on_*` URL | `render-config.sh` 写入 |

- **长度必须 ≥ 32 字符**：ZLM 启动时会校验并自动改写过短的 secret（实测 19 字符被拒）。
- seed 默认值为 `aicamera-zlm-dev-secret-0123456789`，仅用于本地开发，生产必须更换。
- 数据库里**必须存在至少一条**媒体节点记录；没有记录时，所有 hook 都会因
  「找不到匹配 secret 的节点」被拒 —— 表现为 ZLM 日志显示回调成功、平台侧一条都没收到。

### 9.6 单进程内嵌模式（推荐当前使用）

```bash
cd backend
GB28181_ENABLED=true \
GB28181_EMBEDDED=true \
GB28181_SIP_ADVERTISE_IP='<局域网 IP>' \
GB28181_MEDIA_PUBLIC_IP='<局域网 IP>' \
go run ./cmd/server/main.go
```

- SIP 监听随 API 进程启动，**不需要**单独的 `sipsvc` 容器；
- 播放 / 云台 / 回放等命令面完整可用；
- backend 必须保持**单副本**（SIP 状态在本进程）。

### 9.7 常见故障

| 现象 | 根因 | 处理 |
|:---|:---|:---|
| **能注册但黑屏** | SDP `c=` / `o=` 通告的 IP 不是设备可达地址 | 设置 `GB28181_SIP_ADVERTISE_IP` / `GB28181_MEDIA_PUBLIC_IP` 为局域网 IP；必要时覆盖设备 `sdp_ip` |
| **hook 全部 invalid secret** | `ac_gb_media_server` 表没有节点记录，或 secret 与 ZLM 不一致 | 执行 seed（默认节点 `ai-camera-zlm-01`）；核对 `.env`、表、渲染后配置三处一致 |
| **目录发不出 / 通道不出现** | UDP 下单条目录 MESSAGE 超过 MTU | 确认 gbsim 目录分片预算 700 字节；真机确认设备分片；或改用 TCP 信令 |
| **设备注册 403** | `gb_device_id` 未建档 / 为空 / 已软删除 | 在设备管理中生成激活凭证并写入设备 |
| **设备一直 401** | sip_password 与设备配置不一致；realm 不一致；`nc` 大小写处理 | 核对密码 / 域；服务端已按原样 `nc` 计算 |
| **播放返回「信令服务未启动」** | API 与 sipsvc 分进程，`control.Default()` 为 nil | 改用 `GB28181_EMBEDDED=true` 单进程 |
| **INVITE 成功但无流** | 设备 200 OK 的 SDP `o=` 用户名不是设备国标编码 | 设备侧修正；平台按 `o=` 取 ACK 目标 |
| **ZLM 重启后节点一直离线** | hook 地址不可达 | 检查 `ZLM_HOOK_BASE`（Linux 宿主需 `host.docker.internal:host-gateway`）与 backend 端口 |
| **语音回推无声** | 音频源未就绪 / `startSendRtp` 失败 | 属 best-effort 预期；检查 ZLM 源流与设备喇叭 |

### 9.8 验证命令

```bash
ss -lunpt | grep 5060

# ZLM 是否收到 hook（平台侧日志）
```

### 10.1 组件与端口

| 组件 | 端口 | 关键约束 |
|:---|:---|:---|
| `pipecat` | **8090/tcp（仅容器内网，`expose`）** | **不映射宿主机端口**；单副本（配置/会话在进程内存） |

`pipecat` 同时提供控制面与语音服务：配置下发、会话登记、pipeline 装配、
`/ws/voice`（App/Web/ESP32 小智兼容 WebSocket）。GB28181 RTP 链路的
`audio_bridge` 仍可能为 `not_connected`（取决于下行 WebRTC 是否接通），
WS 链路不受影响。

### 10.2 启动

```bash

#   openssl rand -hex 32
# PIPECAT_TOKEN=<token>

docker compose --profile voice up -d --build pipecat
```

> ⚠️ `PIPECAT_TOKEN` 未设置时容器**拒绝启动**（fail-fast），compose 变量
> `${PIPECAT_TOKEN:?...}` 也会在解析阶段报错。

### 10.3 控制面地址与令牌（三处一致）

| # | 位置 | 说明 |
|:--:|:---|:---|
| 1 | `.env` 的 `PIPECAT_TOKEN` | 注入控制面进程 |
| 2 | 后台「语音 Agent 配置 → Pipecat 控制面令牌」 | 存入 `ac_thirdparty_config`（`pipecat_token`） |
| 3 | 后台「Pipecat 控制面地址」 | 容器内网填 `http://pipecat:8090` |

点击「应用到 Pipecat」后，backend 会 `POST {endpoint}/config`，使用
`Authorization: Bearer <token>`。1 与 2 不一致时控制面返回 401。

> backend 与 pipecat 必须在同一个 docker 网络（compose 的 `ai-camera`），
> 因此地址用服务名 `pipecat`，不能用 `127.0.0.1`。

### 10.4 控制面端点

| 方法 | 路径 | 鉴权 | 说明 |
|:--|:--|:--:|:--|
| GET | `/health` | 否 | 存活、版本、provider 数量、`audio_bridge` |
| POST | `/config` | 是 | 后端 `Apply` 下发，body 为 `map[string]string` |
| GET | `/config` | 是 | 当前配置（敏感键脱敏为 `****`） |
| POST | `/session/start` | 是 | `{session_id, channel_id, mode}` |
| POST | `/session/stop` | 是 | `{session_id}` |
| GET | `/sessions` | 是 | 活跃会话 |
| POST | `/test` | 是 | `{category}`，本地导入 + DNS 检查，不发计费请求 |

配置键与后端 `voice_agent_service.go` 完全一致（`stt_* / llm_* / tts_* /
vad_* / barge_in / session_idle_timeout / max_session_sec`）。**默认半双工**
（`barge_in=false`），避免设备喇叭回声导致自激（设计 §8.1.1）。

### 10.5 可选依赖与降级

- provider 的 SDK 按可选导入处理：未安装时控制面**仍能启动**，
  `POST /test` 返回 `ok=false` 并说明缺失模块，
  `POST /session/start` 返回 400 中文原因（不会静默回退）。
- 默认方案：STT=`local_whisper`（`faster-whisper`，已列入 requirements，
  体积较大，可移除）、LLM=`anthropic`（需 `llm_api_key`）、
  TTS=`edge_tts`（免费）、VAD=`silero`（Pipecat 内置）。
- `pipecat-ai` 固定 `1.13.0`；服务类路径已按该版本核对。

### 10.11 v0.6.0：设备 MQTT 上报与离线推送

**MQTT 上报**（适老化相机）：

- 设备发布 `iot/<group>/device/<device_code>/report`，后端平台账号订阅
  `iot/+/device/+/report`；`MQTT_SIGNAL_ENABLED=true` 时自动生效。
- 支持 `heartbeat / battery / position / alarm`；告警类型需存在于
  `ac_alarm_type`（内置 `fall`、`sos`）。
- 联调：`webrtcsim --report-interval 2s`，检查 `ac_device`、
  `ac_iot_device_position`、`ac_alarm_record`。
- 如果 `ac_alarm_record` 报主键冲突，说明开发库序列落后于手工种子数据：
  ```sql
  SELECT setval(pg_get_serial_sequence('ac_alarm_record','id'),
                (SELECT MAX(id) FROM ac_alarm_record));
  ```

**离线推送**（设备呼叫 App）：

1. 后台「第三方平台 → 个推」填写 AppID / AppKey / MasterSecret；
2. App 启动后 `POST /app/push-tokens` 上报个推 CID；
3. 设备 invite 且房间内无 role=app 的 WS 时，后端调用个推
   `/push/single/cid`，payload 含 `room_id/device_code/call_id`。
4. 未配置个推或没有 CID 时只在 backend 日志记录，不影响设备呼叫。

**App 通话**：

- `POST /app/av/devices/:id/call-ticket`（需设备已绑定当前用户）；
- App 连 `/app/av/ws`，信令 `invite/agree/reject/hangup`；
- 设备是 offer 方，App answer；TURN 凭据随 ticket 下发。

## 11. Kubernetes 清单（deploy/k8s）

> 适用版本：v0.2.0+。清单是**自包含的 kustomize 结构**，不依赖仓库外的文件，
> 可直接 `kubectl apply -k deploy/k8s`。

### 11.1 目录结构

```
deploy/k8s/
├── kustomization.yaml          # 入口（默认只启用推荐形态）
├── namespace.yaml              # Namespace: ai-camera
├── configmap.yaml              # 后端基线配置 config.yaml + 外部 DB 地址
├── secret.example.yaml         # 占位密钥（CHANGE_ME，禁止提交真实值）
├── redis.yaml                  # Redis Deployment + Service + PVC
├── zlm-statefulset.yaml        # ZLMediaKit StatefulSet + 2 个 Service + 录像 PVC
├── zlm/
│   ├── config.tmpl             # ZLM 配置模板（同步自 deploy/zlm/config.ini）
│   └── render-config.sh        # K8s 版渲染脚本（模板只读、输出到 emptyDir）
├── backend-deployment.yaml     # 后端 Deployment + uploads PVC
├── backend-service.yaml        # HTTP ClusterIP + SIP LoadBalancer
├── sipsvc-statefulset.yaml     # 可选：独立信令（默认不启用）
└── pipecat-deployment.yaml     # 可选：语音 Agent 控制面（默认不启用）
```

### 11.2 应用与前置条件

```bash
# 1. 先把 configmap.yaml 的 DATABASE_HOST / DATABASE_NAME / DATABASE_USER
#    与 secret.example.yaml 的占位密钥改掉（或用 External Secrets 注入）。
# 2. 一次性应用
kubectl apply -k deploy/k8s

# 3. 检查
kubectl -n ai-camera get pods -o wide
kubectl -n ai-camera get svc
kubectl -n ai-camera logs -f deploy/ai-camera-backend --tail=100
```

前置条件（清单**刻意不内置**）：

| 依赖 | 说明 |
|:---|:---|
| PostgreSQL | 生产建议云托管或独立 Patroni 集群；`DATABASE_HOST` 指向它。清单不内置 PG，避免把有状态数据库塞进应用命名空间。 |
| LoadBalancer | SIP 的 `5060/udp+tcp` 与 ZLM 的 `10000/udp+tcp` 必须让**设备可达**。无 LB 实现时把 Service 改成 `NodePort`，并把 `SIP_ADVERTISE_IP` / `MEDIA_PUBLIC_IP` 设为节点公网 IP。 |
| 媒体节点记录 | 清单不会写库。首次部署后必须更新 `ac_gb_media_server` 默认节点，见 11.4。 |

### 11.3 关键约束（写进清单注释，也在这里强调）

1. **内嵌 SIP → backend 固定 1 副本**（`replicas: 1` + `strategy: Recreate`）。
   SIP 事务、TCP 连接、INVITE 会话、设备源地址都在进程内存；多副本会导致
   「注册在 A、播放落到 B」的稳定 503。`Recreate` 保证滚动更新期间不会短暂
   出现两个 Pod 同时持有 SIP 状态。
2. **Service 必须暴露 `5060/udp` + `5060/tcp`**（`ai-camera-sip`，`externalTrafficPolicy: Local`）。
   用 `Cluster` 策略会 SNAT 掉设备真实源 IP，NAT 诊断和排障都会失真。
3. **若改独立 sipsvc**：`sipsvc-statefulset.yaml` 副本固定 1，且必须同时把 backend
   的 `GB28181_EMBEDDED` 改为 `false`、移除 backend 的 SIP Service。
   ⚠️ 跨进程命令通道（Redis RPC）**尚未实现**，此时 HTTP 播放/云台/回放会 503，
   只能用于协议层压测/独立调试。
4. **ZLM 单端口 10000**：只开 `10000/udp` + `10000/tcp`，**不需要** 30000-30500 端口段。
   平台不得调用 `openRtpServer`（详见 §9.3）。
5. **ZLM 配置由渲染脚本生成**：ConfigMap 卷只读，渲染结果写 `emptyDir:/opt/media/conf`；
   不要把 secret 直接写进 `config.tmpl`。
6. **密钥不进 ConfigMap**：数据库口令、`JWT_SECRET`、`GB28181_SIP_NONCE_SECRET`、
   `ZLM_SECRET`、`PIPECAT_TOKEN` 全部走 Secret + `config.go` 的 `envBindings`。
7. **`uploads` 用 RWO PVC**：replicas=1 时够用；扩容或迁移对象存储前不要改成 RWX
   假设（见 [02-监控与容灾.md](02-监控与容灾.md) §5.5）。

### 11.4 首次部署后：对齐媒体节点

清单不会写数据库，必须让 `ac_gb_media_server` 的默认节点指向集群内的 ZLM：

```sql
UPDATE ac_gb_media_server
   SET ip = 'ai-camera-zlm',          -- 集群内 Service 名
       http_port = 80,
       sdp_ip = '<MEDIA_PUBLIC_IP>',  -- 设备可达地址（与 ConfigMap 一致）
       hook_ip = 'ai-camera-backend', -- 平台回调地址（ZLM 侧环境变量已设置）
       secret = '<与 Secret 的 ZLM_SECRET 完全一致，≥32 字符>',
       online = false                 -- 启动后由 on_server_keepalive 置 true
 WHERE default_server = true;
```

三处 secret 必须一致：K8s Secret、`ac_gb_media_server.secret`、ZLM 渲染后的
`config.ini`。不一致的典型表现是 ZLM 日志显示回调成功、平台侧一条都没收到。


9. ZLM HTTP API 可达性与 secret 是否正确；
10. ZLM 节点在线标记与最近 hook 心跳。

## 13. 信令日志保留与清理

> 实现：`GbSipLogService.Cleanup` + `cmd/server` 内置 janitor。

`ac_gb_sip_log` 是追加写、无软删除的大表（每台设备每分钟一条心跳，点播期间还有
INVITE/ACK/BYE/INFO）。不做清理会拖慢分页查询并持续占用磁盘。

### 13.1 默认策略

| 项 | 值 | 说明 |
|:---|:---|:---|
| 保留天数 | **30 天** | 覆盖「上周还好、这周黑屏」类排障窗口 |
| 执行周期 | 每 24 小时 | 进程启动后首次延迟 10 分钟，避开启动期 AutoMigrate/设备重注册 |
| 单次超时 | 30 分钟 | 防止慢查询永久卡住 janitor |
| 单批行数 | 5000 | 每批独立事务，避免长事务锁表阻塞信令写入 |
| 删除方式 | **物理 DELETE** | 日志表没有 `deleted_at`，软删只会让表更大 |

### 13.2 配置

```bash
# 默认 30 天；非法值（非数字 / <=0）会回退到 30 并打印告警
SIP_LOG_RETENTION_DAYS=30
```

该变量只被 janitor 读取，**不进入 `config.Config`**：纯运维参数，没必要为它
扩展配置结构与模板。

### 13.3 手动清理（应急）

```sql
-- 分批执行，避免一条 SQL 锁表太久；重复执行直到影响行数为 0
DELETE FROM ac_gb_sip_log
 WHERE id IN (
   SELECT id FROM ac_gb_sip_log
    WHERE created_dt < now() - interval '30 days'
    ORDER BY created_dt ASC
    LIMIT 5000
 );
```

### 13.4 观测

- `aicamera_gb_sip_log_deleted_total`：janitor 累计删除行数（应每日增长）。
- `aicamera_gb_sip_log_dropped`：异步写队列丢弃数（应长期为 0；持续 >0 说明
  DB 写入跟不上信令速率）。
- 任务日志关键字：`信令日志清理完成` / `信令日志清理未完成`。

## 14. IOT MQTT broker（mochi-mqtt）

### 14.1 组件与端口

| 组件 | 镜像 | 端口 | profile |
|:--|:--|:--|:--|
| MQTT broker | 本地构建 `deploy/mochi-mqtt` | `1883/tcp`、`8083/tcp`（WebSocket） | `iot` |

```bash
docker compose --profile full --profile iot up -d --build
```

### 14.2 鉴权链路

```
设备/客户端 CONNECT
  → broker OnConnectAuthenticate
  → POST {backend}/rpc/mqtt/auth   (X-RPC-Token)
  → 后端查 ac_iot_service_group（启用 / type=webrtc / 含 MQTT 服务项）
  → allow / deny
PUBLISH/SUBSCRIBE
  → POST /rpc/mqtt/acl → 只允许 iot/<group_code>/**
```

- **两端必须配置同一个 `MQTT_RPC_TOKEN`**：broker 为空时拒绝启动；后端为空时拒绝所有鉴权。
- broker 与后端都是 **fail-closed**：后端不可达时连接被拒绝，不会放行。
- 账号来自「IOT 管理 → 服务管理 → WebRTC 服务组」，密码在组创建时自动生成，可在服务组页重置。

### 14.3 常见故障

| 现象 | 原因 | 处理 |
|:--|:--|:--|
| 所有连接被拒，broker 日志 `RPC 失败` | `BACKEND_RPC_URL` 错或后端未启动 | broker 容器内 `wget -qO- $BACKEND_RPC_URL/health` |
| 后端返回 503「未配置 MQTT_RPC_TOKEN」 | 后端环境变量缺失 | 注入后重启后端与 broker |
| 鉴权通过但发布被拒 | 话题不在 `iot/<group_code>/` 下 | 用服务组页显示的 `code` 作前缀 |
| 服务组密码忘了 | 组密码只显示一次 | 服务组页「重置凭据」，同步更新设备 |

## 15. TURN / STUN（coturn）

### 15.1 组件与端口

| 组件 | 镜像 | 端口 | profile |
|:--|:--|:--|:--|
| coturn | `coturn/coturn:4.6.3-alpine` | `3478/udp+tcp`、`49160-49200/udp`（中继） | `turn` |

```bash
docker compose --profile full --profile turn up -d
```

### 15.2 授权模型（重要）

**coturn 没有 HTTP 鉴权回调。** 唯一的外部授权方式是 TURN REST API：

1. 调用方请求后端 `POST /rpc/turn/credentials`（`X-RPC-Token`），带上 `subject`；
2. 后端做自己的授权判断，然后用共享密钥签发：
   - `username = "<过期时间戳>:<subject>"`
   - `password = Base64(HMAC-SHA1(secret, username))`
3. 客户端把这对凭据作为 ICE 的 `username`/`credential`；
4. coturn 用 `static-auth-secret` 验签并检查过期时间，**不发起任何网络回调**。

因此「自定义授权」的落点在**后端**（谁有权拿凭据），而不是 coturn。

### 15.3 必须一致的三处

| 位置 | 变量 | 说明 |
|:--|:--|:--|
| `.env` | `TURN_STATIC_AUTH_SECRET` | 后端签发与 coturn 验签共用 |
| coturn 容器 | `TURN_STATIC_AUTH_SECRET` | 由 compose 注入命令行 |
| 后端容器 | `TURN_STATIC_AUTH_SECRET` | 签发凭据时读取 |

另：
- `TURN_REALM` 必须与客户端一致，否则 coturn 回 401；
- `TURN_EXTERNAL_IP` 必须是客户端可达地址（NAT 后填映射地址），否则中继候选不可用；
- `TURN_URLS` 是返回给客户端的地址，**不能写 compose 服务名**（客户端不在 compose 网络里）；
- 中继端口段 `49160-49200` 在 compose 与 coturn 配置中必须一致。

### 15.4 验证

```bash
# 1) 签发凭据
curl -s -X POST http://localhost:8081/rpc/turn/credentials \
  -H "X-RPC-Token: $TURN_RPC_TOKEN" -H 'Content-Type: application/json' \
  -d '{"subject":"device-001","ttl":600}'

# 2) 用返回的账号做 TURN 分配（需安装 turnutils_uclient 或用 WebRTC 客户端）
```

### 15.5 常见故障

| 现象 | 原因 | 处理 |
|:--|:--|:--|
| 客户端 401 Unauthorized | realm 未配 / 密钥不一致 / 时钟偏差 | 核对三处密钥与 `TURN_REALM`；确保服务器时间同步 |
| 能分配但媒体不通 | `external-ip` 或中继端口未映射 | 检查 `TURN_EXTERNAL_IP` 与 `49160-49200/udp` |
| 签发接口 503 | 后端未配 `TURN_STATIC_AUTH_SECRET` | 注入后重启后端 |
| Docker 起不来 | 中继端口段太宽 | 保持 41 个端口以内，或改用 host 网络 |

### 14.4 两种鉴权后端（二选一）

| 方式 | broker | 后端配置 | 说明 |
|:--|:--|:--|:--|
| HTTP RPC | `deploy/mochi-mqtt`（本仓库） | `MQTT_RPC_TOKEN` | 有完整 ACL（`iot/<group>/**`） |
| gRPC RPC | 内部 fork `cloud/mochi-mqtt` | `MQTT_GRPC_ENABLED=true`、`MQTT_GRPC_LISTEN=:50051` | 与 fork 的 `rpc.address` 对接；fork 目前 ACL 恒 true |

### 14.5 MQTT 作为 WebRTC 信令

后端可启用信令 worker（默认关闭）：

```yaml
MQTT_SIGNAL_ENABLED: "true"
MQTT_BROKER_URL: tcp://mqtt:1883
MQTT_RPC_TOKEN: <与 broker 一致>
```

- worker 以内部账号 `__platform__` 连接 broker；
- 订阅 `iot/+/signal/backend`，把 offer 转给 ZLM WHEP，再发布 answer 到
  `iot/+/app/+/signal`；
- 失败会回 `{"type":"error"}`，App 不要只依赖超时。

## 15. 本地联调：宿主机后端 + 容器 MQTT/TURN

本地开发常见形态是 **Go 后端跑在宿主机（:8080）、PostgreSQL/Redis/ZLM/MQTT/TURN 跑在容器**。
此时 `.env` 由 Docker Compose 读取，**Go 进程不会自动加载 `.env`**，必须显式 `export`
（或 `set -a; source .env; set +a`）后再启动后端。

### 15.1 启动顺序

```bash
cd <仓库根>
# 1) 基础设施
docker compose up -d postgres redis

# 2) 宿主机后端（先启动一次完成 AutoMigrate，创建 turnusers_lt 等表）
cd backend
set -a; source ../.env; set +a
export DATABASE_HOST=127.0.0.1 DATABASE_PORT=5432 DATABASE_USER=aicamera
export DATABASE_PASSWORD="$POSTGRES_PASSWORD" DATABASE_DBNAME=ai_camera_dev
export REDIS_HOST=127.0.0.1 REDIS_PASSWORD="${REDIS_PASSWORD:-aicamera_redis}"
export MQTT_RPC_TOKEN MQTT_SIGNAL_ENABLED=true MQTT_BROKER_URL=tcp://127.0.0.1:1883
export TURN_STATIC_AUTH_SECRET TURN_RPC_TOKEN TURN_REALM TURN_EXTERNAL_IP TURN_URLS
go run ./cmd/server/main.go

# 3) 另一个终端：MQTT/TURN 容器
cd <仓库根>
docker compose --profile iot --profile turn up -d --build mqtt turn
```

> **不要**在宿主机形态下设置 `MQTT_GRPC_ENABLED=true`：本仓库 `deploy/mochi-mqtt`
> 是 HTTP RPC 鉴权（`/rpc/mqtt/auth`），gRPC 仅用于内部 fork。

### 15.2 宿主机形态必须覆盖的地址

| 变量 | 值 | 原因 |
|:--|:--|:--|
| `MQTT_BACKEND_RPC_URL` | `http://host.docker.internal:8080` | broker 在容器内，要回调宿主机后端；不能写 `backend:8080` |
| `MQTT_BROKER_URL` | `tcp://127.0.0.1:1883` | 宿主机后端连容器发布的 1883 |
| `TURN_EXTERNAL_IP` | 宿主机 LAN IP（如 `192.168.10.207`） | coturn 在 relayed candidate 中通告；不能是 127.0.0.1 |
| `TURN_URLS` | `stun:<LAN IP>:3478,turn:<LAN IP>:3478?...` | 返回给客户端，必须客户端可达 |

Linux 宿主上 `host.docker.internal` 默认不存在，`docker-compose.yml` 已为 mqtt 服务
补 `extra_hosts: host.docker.internal:host-gateway`。

### 15.3 健康检查

```bash
docker compose ps

docker logs --tail 100 ai-camera-turn

# MQTT 鉴权（内部账号）
```

### 15.4 已知坑

1. **mochi-mqtt v2.7.x 的 `Serve()` 启动监听后立即返回**。仓库 `deploy/mochi-mqtt/main.go`
   已补信号等待；若自行升级该依赖，必须保留这段，否则容器会以 0 反复重启。
2. **`turnusers_lt` 由后端 AutoMigrate 创建**。coturn 只 `depends_on postgres`，
   首次启动可能早于建表；先起后端再起 turn，或 `docker compose restart turn`。
3. **IOT 服务组地址**：`ac_iot_service` 的 `host/port` 种子为空，必须在
   「IOT 管理 → 服务组 → WebRTC 服务组」填入客户端可达的 MQTT/TURN 地址，
   再绑定产品；绑定后服务组变只读，顺序不能反。
4. **产品绑定才会生成凭据**：绑定后 `ac_iot_product_service` 有行，
   产品×TURN 凭据同步写入 `turnusers_lt`。
5. **`.env` 与 shell 环境不一致**：改了 `.env` 必须重启 Go 进程并确认已 export。
