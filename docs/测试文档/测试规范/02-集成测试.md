# 集成测试规范

> 版本: v0.1.0
> 最后更新: 2026-09-21

---

> **定位**：验证 2~5 个 Service 串联后的**跨模块数据一致性**与**状态流转正确性**。
> 单元测试保证单点正确，集成测试保证接线正确。
>
> **执行频率**：每次提交（与单元测试同批执行）。
>
> **运行时间**：全量 < 60s；单条链路 < 5s。
>
> **对标**：全部核心业务链路（12 条）100% 覆盖，每条链路的所有参与表在链路结束后状态自洽。

---

## 一、与单元测试的边界

```
┌────────────────────────────────────────────────────────────┐
│  单元测试                         集成测试                  │
│  ─────────                        ─────────                │
│  1 个 Service 方法                2~5 个 Service 串联       │
│  断言返回值 + 单表字段            断言多表数据一致性         │
│  不关心调用者                    覆盖真实业务操作顺序        │
│  失败 → 该 Service 有问题         失败 → 模块接线/契约有问题  │
└────────────────────────────────────────────────────────────┘

示例：
  单元：RegionService.Create  → 断言 ac_region 表字段正确
  集成：Create Region → Create Device(region_id) → Report Risk
        → 断言 ac_risk_record.region_id 与 ac_device.region_id 一致
```

> **注意**：集成测试同样使用 `testutil.WithTx(t, fn)`，多 Service 共享同一事务句柄
> （由 `bootstrap.SetDB(tx)` 覆盖），因此链路中任一步失败，整条链路的数据全部回滚。

## 三、重点链路详解

### 3.1 IT-01 AI 风险全生命周期

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ RegionService│──►│DeviceService │──►│RiskTypeService│
│  Create      │   │  Create      │   │  Create       │
│  厂区A        │   │  region_id   │   │  level=high   │
└──────────────┘   └──────────────┘   └──────────────┘
                                               │
                                               ▼
                    ┌──────────────────────────────────────┐
                    │ RiskService.Report (ApiKey)          │
                    │ risk_type_id + device_code           │
                    │ → status=pending, read=false         │
                    │   detect_accurate=""                 │
                    └──────────────────────────────────────┘
                                       │
              ┌────────────────────────┴────────────────────┐
              ▼                                             ▼
   ┌────────────────────┐                       ┌────────────────────┐
   │ 分支 A：检测准确=是 │                       │ 分支 B：检测准确=否 │
   │ UpdateAccurate(yes)│                       │ UpdateAccurate(no) │
   │ → read=true        │                       │ → read=true        │
   │ → status=pending   │                       │ → status=handled   │
   │ Handle(...)        │                       │ （误报，无需处理）  │
   │ → status=handled   │                       └────────────────────┘
   │ → handler/HandledDT│
   └────────────────────┘
              │                                             │
              └────────────────────────┬────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │ StatsService.Dashboard / RiskStats   │
                    │ 今日预警 +1、已处理 +1               │
                    └──────────────────────────────────────┘
```

**链路断言**：

| 步骤 | 断言的字段 | 期望值 |
|:---|:---|:---|
| `Report` | `risk_type_id`、`device_id`、`device_code`、`region_id`、`location` | 与设备一致（冗余字段回填） |
| `Report` | `status` / `read` / `detect_accurate` | `pending` / `false` / `""` |
| `Report` | `risk_level` | 等于 `RiskType.Level`（冗余） |
| `UpdateAccurate("yes")` | `read` / `read_dt` | `true` / 非空 |
| `UpdateAccurate("yes")` | `status` / `accurate_by` / `accurate_dt` | 仍为 `pending` / 操作人 / 非空 |
| `UpdateAccurate("no")` | `status` / `read` | `handled` / `true` |
| `Handle` | `handle_result`、`handle_image`、`handler`、`handled_dt`、`status` | 写入 / `handled` |
| `PendingCount` | 返回值 | 与 `Page(status=pending).Total` 一致 |
| `Dashboard` | `today_risk` / `today_handled` | 各 +1 |

### 3.2 IT-02 物联网卡更换

```
Device(IotCardID=null)
   │
   ├─ ① IotCardService.Create(card_no=C1, device_id=D)
   │        └─► ac_iot_card.device_id = D
   │
   ├─ ② DeviceService.Update(id=D, iot_card_id=C1)
   │        └─► ac_device.iot_card_id = C1
   │
   ├─ ③ IotCardService.Create(card_no=C2)
   │
   ├─ ④ IotCardService.ReplaceCard(device_id=D, new_card_id=C2, operator="admin")
   │        ├─► ac_iot_card_replace_log 新增 1 条
   │        │     old_iot_card_id=C1, new_iot_card_id=C2
   │        │     old_card_no=C1, new_card_no=C2
   │        │     device_code / region_id / location 冗余回填
   │        │     replace_dt 非空, operator="admin"
   │        ├─► ac_device.iot_card_id = C2
   │        ├─► ac_iot_card[C1].device_id = null（解绑）
   │        └─► ac_iot_card[C2].device_id = D（绑定）
   │
   └─ ⑤ PageReplaceLogs(device_id=D)
            └─► 返回 1 条，old_card_no=C1，new_card_no=C2
```

> **注意**：换卡是**追加型**操作，`ac_iot_card_replace_log` 不做修改与删除，
> 用于追溯某台设备历史使用过的全部卡片。

### 3.3 IT-03 巡检任务闭环

```
Web 端                                  App 端
──────                                  ──────
InspectService.CreateTask
  name / region_id / location
  inspector_id / content / plan_dt
  → status=published
  → ac_inspect_task.read=false
        │
        ▼
AppService.PageInspectTasks(userID=inspector)
  → 只返回 inspector_id = 自己 的任务
        │
        ▼
AppService.GetInspectTask(id)
  → 返回任务详情（Preload Region.Name）
        │
        ▼
AppService.FinishInspectTask(taskID, userID, req)
  ├─► 校验 userID == task.inspector_id（否则 403/error）
  ├─► ac_inspect_record 新增 1 条
  │     task_id / task_name（冗余快照）
  │     region_id / location（冗余快照）
  │     inspector_id / inspector（冗余快照）
  │     content（冗余快照）
  │     result / result_image / handled_dt
  │     status=finished
  ├─► ac_inspect_task.status = finished
  └─► ac_inspect_task.read = true
        │
        ▼
Web 端 InspectService.PageRecords
  → 可见刚生成的巡检记录
Web 端 InspectService.PageTasks(status=published)
  → 不再包含该任务
```

**越权拦截断言**：以 `userID != inspector_id` 调用 `FinishInspectTask` 必须返回 error，
且 `ac_inspect_record` 不新增记录、`ac_inspect_task.status` 保持 `published`。

### 3.7 IT-08 数据权限四级

预置数据：3 个部门（D1 生产、D2 质量、D3 仓储），每部门 2 条 `ac_region`，共 6 条。

| 角色 | `data_permission` | `cross_dept_ids` | `Page` 可见行数 | 说明 |
|:---|:---|:---|:---:|:---|
| 超管 | `all` | — | **6** | 不过滤 |
| 跨部门主管 | `cross_dept` | `D2` 对应 ID | **4** | D1 + D2 |
| 部门主管 | `dept` | — | **2** | 仅 D1 |
| 普通用户 | `personal` | — | **1** | D1 且 `created_by` = 本人 |
| 无部门用户 | `dept`/`personal` | — | **该用户创建的行数** | `dept_id` 为空 → 退化为 `created_by` 过滤 |
| `cross_dept` 且 `cross_dept_ids` 为空 | `cross_dept` | 空 | **该用户创建的行数** | 同上退化 |

> **注意**：`ApplyToQuery` 的 `personal` 分支在 `dept_id` 为空时退化为
> `created_by = 当前用户名`；非空时为 `dept_id = ? AND created_by = ?`。
> 二者行为不同，测试必须覆盖两条路径。

### 3.11 IT-13 设备告警全生命周期

与 IT-01 平行，差异点：

- 无 `detect_accurate` 维度（告警来自设备状态，非 AI 识别），`/web/alarms/:id/accurate` 不存在
- 参与表为 `ac_alarm_record` + `ac_alarm_type`
- `AlarmService.Report` 需写 `alarm_level`（冗余自 `AlarmType.Level`）与 `content`

**内置告警编码**：`offline`（离线）、`battery`（电量）、`traffic`（流量），由种子数据写入，
集成测试须验证三者可被 `AlarmTypeService.Options` 返回且能成功上报。
