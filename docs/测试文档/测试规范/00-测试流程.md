## 一、测试体系概览

AI Camera 采用五层测试体系，从函数级到用户级逐层收敛，上层失败时优先回退到下层定位。

```
┌──────────────────────────────────────────────────────────────┐
│  L5  端到端测试 (E2E)        Playwright + 真实后端 + 真实库     │
│      frontend/e2e/           覆盖页面跳转、Modal 交互、权限显隐 │
├──────────────────────────────────────────────────────────────┤
│  L4  回归测试                全量用例重跑 + 历史缺陷清单       │
│      docs/测试文档/测试规范/04 │触发条件：每次版本发布前         │
├──────────────────────────────────────────────────────────────┤
│  L3  接口测试                HTTP 层：认证/参数/权限/分页/软删  │
│      backend/tests/<domain>/  200 个端点的契约级验证            │
├──────────────────────────────────────────────────────────────┤
│  L2  集成测试                跨模块全链路（Service 层串联）     │
│      backend/tests/<domain>/  12 条核心业务链路                 │
├──────────────────────────────────────────────────────────────┤
│  L1  单元测试                Service 层方法级 + 字段级验证      │
│      backend/tests/<domain>/  24 个 Service / 195 个方法        │
└──────────────────────────────────────────────────────────────┘
        ▲ 依赖方向：L5 → L4 → L3 → L2 → L1（下层不依赖上层）
```

| 层级 | 目录 | 执行频率 | 单次耗时 | 门槛 |
|:---|:---|:---|:---:|:---|
| 单元测试 | `backend/tests/<domain>/` | 每次提交 | < 30s | 100% 通过 |
| 集成测试 | `backend/tests/<domain>/` | 每次提交 | < 60s | 100% 通过 |
| 接口测试 | `backend/tests/<domain>/` | 每日构建 | < 90s | 100% 通过 |
| 回归测试 | 全量重跑 | 版本发布前 | < 180s | 无 P0/P1 遗留 |
| 端到端测试 | `frontend/e2e/` | 版本发布前 | < 300s | 主链路 100% 通过 |

## 二、测试流程

### 2.1 运行方式

后端测试全部由 Go 原生 `go test` 驱动，测试代码位于 `backend/tests/<domain>/`，
测试工具位于 `backend/tests/testutil/`。

```bash
# 全量执行（必须显式指定测试库连接参数）
cd backend && TEST_DB_HOST=192.168.1.227 TEST_DB_PORT=5432 TEST_DB_USER=boticz TEST_DB_PASSWORD='<测试库密码>' TEST_DB_NAME=ai_camera_test go test ./tests/... -count=1 -timeout 180s

# 单模块执行
cd backend && TEST_DB_HOST=192.168.1.227 TEST_DB_PORT=5432 TEST_DB_USER=boticz TEST_DB_PASSWORD='<测试库密码>' TEST_DB_NAME=ai_camera_test go test ./tests/system/... -v

# 单个用例
cd backend && TEST_DB_HOST=192.168.1.227 TEST_DB_PORT=5432 TEST_DB_USER=boticz TEST_DB_PASSWORD='<测试库密码>' TEST_DB_NAME=ai_camera_test go test ./tests/basic/ -run TestRegionService_Create -v
```

前端测试：

```bash
cd frontend && npx vitest run          # 单元测试（MSW mock，无需后端）
cd frontend && npx playwright test     # 端到端测试（需要后端在 :8080）
```

移动端测试：

```bash
cd app && flutter test                 # Flutter 单元测试
cd app && flutter analyze              # 静态检查（要求 0 error 0 warning）
```

> **注意**：启动测试前必须停止本地正在运行的后端服务，避免端口冲突；
> 若测试用例通过 HTTP 访问后端（接口测试），需先以 `config-test.yaml` 启动服务。

### 2.2 测试数据

| 数据来源 | 命令 | 说明 |
|:---|:---|:---|
| 清空测试库 | `cd backend && go run ./tests/testutil/resetdb/main.go` | 删除全部业务数据，保留表结构 |
| 初始化种子数据 | `cd backend && go run ./tests/testutil/initdb/main.go` | 写入 admin 账号、内置角色、菜单树、告警类型等 |
| 单元测试自建数据 | 测试用例内部构造 | 每个用例自带前置数据，不依赖 seed |

> **注意**：修改测试用例后若出现「唯一索引冲突」或「种子数据与用例断言不一致」，
> 需先执行 `resetdb` 再执行 `initdb`，最后重跑测试。

### 2.3 测试数据隔离

每个测试用例通过 `testutil.WithTx(t, fn)` 包裹，在独立数据库事务中执行，结束后**无条件回滚**：

```go
func TestRegionService_Create(t *testing.T) {
    testutil.WithTx(t, func(tx *gorm.DB) {
        bootstrap.SetDB(tx)          // 事务句柄覆盖全局 DB
        svc := basic.NewRegionService()

        got, err := svc.Create(ctx, &request.CreateRegionReq{Name: "厂区A", Code: "R-A"})
        // ... 断言
    })
}
```

原理：`WithTx` 在 `*gorm.DB` 上开启事务，通过 `bootstrap.SetDB(tx)` 把事务句柄写入全局单例。
所有 Service / Repository 均通过 `bootstrap.DB()` 取库，因此拿到的都是同一个可回滚事务。

隔离收益：

- 用例之间无顺序依赖，可并行拆分、可单独重跑
- 失败用例不会污染后续用例
- 无需在每个用例后手写清理 SQL

### 2.4 自动迁移

`bootstrap.Init()` 在包导入时执行 `AutoMigrate()`，对 `internal/model/` 下全部模型做增量迁移
（新增表、新增列、列类型变更）。测试进程同样触发该逻辑，因此：

- 新增模型或新增字段后，**无需手工改测试库**，跑一次测试即自动补齐
- 初次建表由 `docs/开发文档/数据库设计/sql/ddl/*.sql` 完成，AutoMigrate 只做增量
- AutoMigrate 采用 fail-fast：任一模型迁移失败即中止，避免静默跳过导致表结构不一致

> **注意**：AutoMigrate 不会删除列、不会回滚类型变更。删除字段需手工执行 SQL。

## 三、测试模式对比

| 维度 | 单元测试 | 集成测试 | 接口测试 | 回归测试 | 端到端测试 |
|:---|:---|:---|:---|:---|:---|
| **测试对象** | 单个 Service 方法 | 2~5 个 Service 串联 | HTTP 端点 | 全部已有用例 | 完整用户操作 |
| **调用入口** | Service 方法直调 | Service 方法直调 | `httptest` / HTTP | 混合 | 浏览器 / App |
| **数据库** | 事务回滚 | 事务回滚 | 真实写入 + 清理 | 事务回滚 | 真实写入 |
| **是否需启动后端** | ❌ 不需要 | ❌ 不需要 | 🟡 建议启动 | ❌ 不需要 | ✅ 必须启动 |
| **校验重点** | 字段写入、返回值 | 状态流转、数据一致性 | 认证、参数、权限、分页 | 无回归缺陷 | 页面渲染、交互、显隐 |
| **典型用例量** | ~130 | ~25 | ~60 | 全量 | ~30 |
| **单次耗时** | < 30s | < 60s | < 90s | < 180s | < 300s |
| **执行频率** | 每次提交 | 每次提交 | 每日构建 | 版本发布前 | 版本发布前 |
| **失败定位成本** | 低 | 中 | 中 | 高 | 高 |

## 四、测试准则

1. **Service 层全覆盖**：`internal/service/` 下每个 Service 的每个导出方法都必须至少有 1 个单元测试，
   方法名与用例名一一对应（`RegionService.Create` → `TestRegionService_Create`）。
2. **必须验证字段更新**：所有单元测试必须验证**绝大多数字段**的写入与更新，
   在断言中显式列出字段名（如 `name`、`code`、`sequence`、`active`、`remark`、`created_by`），
   防止字段保存失效（DTO 字段未映射、GORM tag 拼写错误等）逃逸。
3. **事务隔离**：所有单元/集成测试必须使用 `testutil.WithTx(t, fn)`，禁止直接读写全局库。
4. **禁用 dev / prod 库**：测试只能连接 `ai_camera_test`（测试库 MCP `postgres_ai_camera_test`），
   **严禁**操作开发库 `ai_camera_dev`。
5. **自包含数据**：每个用例自行创建所需前置数据，不依赖其他用例的执行顺序与残留状态。
6. **状态流转必测**：涉及状态机的模块（风险 pending→handled、巡检 published→finished、
   升级计划 pending→canceled）必须验证合法流转成功、非法流转被拒。
7. **数据权限必测**：涉及 `ds *utils.DataScope` 参数的 Service 方法，必须覆盖
   `all` / `cross_dept` / `dept` / `personal` 四级的可见行数差异。
8. **改动同步**：修改前后端功能后，必须同步调整对应的单元测试、集成测试与端到端测试。
9. **E2E Modal 选择器**：Playwright 脚本必须使用 `e2e-xxx-modal` 类定位弹窗，
   **禁止**使用 `.ant-modal`、`.ant-modal-footer` 等通用选择器。
10. **用例文档同步**：新增 Service 方法或 API 端点时，同步更新 `docs/测试文档/测试用例/` 下对应文档。
