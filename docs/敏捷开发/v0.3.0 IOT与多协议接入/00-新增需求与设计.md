## 1.1 目前只有两个产品（业务基线）

**产品类型不作为平台字段**：配网方式、服务组、是否允许分享全部是产品自身的配置，
平台只校验取值合法，不做「类型 → 配置」的联动约束。

| 项 | 安防相机 | 适老化智能相机 |
|:--|:--|:--|
| 产品编码（种子） | `security_camera` | `elderly_camera` |
| `net_config_mode` | `qrcode`（无需配网） | `bluetooth`（NUS，见 §7.1） |
| 绑定 | **扫设备二维码**（`boticz.cn/qrDevice/...`） | 配网成功后由 App 绑定 |
| 服务组（产品上绑定） | `gb28181`（SIP / RTSP） | `webrtc`（WebRTC / MQTT / RTSP）+ `aichat`（WebSocket） |
| `allow_share` | `false` | `true` |
| 分享 | 不需要 | 配网后由 owner 生成**设备分享二维码**（一次性） |
| 媒体接入 | GB28181 推 PS/RTP 到 ZLM | WebRTC（MQTT 信令）+ AIChat |

种子数据预置这两个产品（不预置真实服务组地址）；服务组由管理员按实际部署录入后绑定。

## 2. IOT 管理数据模型

### 2.1 新增表（7 张 + coturn userdb）

| 表 | 作用 | 关键约束 |
|:--|:--|:--|
| `ac_iot_product` | 产品定义 | `code` 唯一；`auto_network`、`net_config_mode`、`allow_share` |
| `ac_iot_service_group` | 服务组（固定三条） | `code` 唯一；**不持有凭据**；不开放增删 |
| `ac_iot_service` | 服务（组内接入项） | `(group_id, code)` 唯一；协议白名单 |
| `ac_iot_product_service_group` | 产品 ↔ 服务组 | `(product_id, service_group_id)` 唯一 |
| `ac_iot_product_service` | 产品 ↔ 服务（含鉴权） | `(product_id, service_id)` 唯一；`username` 全局唯一 |
| `ac_iot_device_account` | 设备账号 | `username` / `share_token` 唯一；`role=owner/shared`；`platform_user_id` 关联平台用户 |
| `ac_iot_device_event` | 设备事件 | 追加写：ota / activate / account-create / secret-reset / unbind |
| `turnusers_lt` | coturn SQL userdb | `(realm, name)` 主键；`hmackey=MD5(username:realm:password)` |

### 2.2 `ac_device` 扩展

| 列 | 说明 |
|:--|:--|
| `product_id` | 所属产品 |
| `device_secret` | 设备接入密钥（OTA / 激活 / SIP 绑定校验） |
| `activated_at` | 激活时间 |

> **为什么设备复用 `ac_device`**：平台已有唯一的设备权威源，GB28181 白名单、
> 通道、报警、录像都挂在它上面。另建 IOT 设备表会产生两套主键与生命周期，
> 后续同步会变成长期负担。

### 2.3 服务组类型与协议白名单

服务组是**系统预置的三条固定数据**（编码 = `gb28181` / `webrtc` / `aichat`），
不开放新增/删除，编码与类型不可修改；类型由编码决定。

| 编码 | 允许服务协议 |
|:--|:--|
| `gb28181` | SIP、RTSP |
| `webrtc` | WebRTC、MQTT、RTSP、TURN |
| `aichat` | WebSocket |

**引用锁定**：服务组一旦被任一产品绑定，即进入只读状态——禁止编辑名称/描述、
修改服务与删除。设计原因：设备 OTA 正在使用该组的服务配置，后台改动会让
已联网设备拿到不一致配置。管理员必须先在产品页解除绑定。

**凭据**：产品选择服务组后，平台为组内每个服务生成独立的
`username` / `password`，存放在 `ac_iot_product_service`；组本身不持有凭据。

## 3. MQTT 接入

### 3.1 组件

- Broker：`deploy/mochi-mqtt`（基于公开 `mochi-mqtt/server` v2.7.9）
- 鉴权：broker 在 `OnConnectAuthenticate` / `OnACLCheck` 调用后端 RPC
- 协议：`POST /rpc/mqtt/auth`、`POST /rpc/mqtt/acl`（`X-RPC-Token`）

### 3.2 鉴权规则

- 用户名匹配 `ac_iot_product_service` 中启用的产品×服务凭据，且该服务为启用的
  MQTT 服务、所属服务组为启用的 `webrtc`、产品启用；
- 密码 constant-time 比较；
- ACL 限定 `iot/<group_code>/**`；
- **双层 fail-closed**：后端不可达 / token 缺失 / 非 2xx → broker 一律拒绝。

### 3.3 内部账号

- broker 与后端之间使用 `__platform__` + `MQTT_RPC_TOKEN`；
- 只允许订阅 `iot/+/signal/backend`、发布 `iot/+/app/+/signal`。

### 3.4 与内部 fork 的对接（gRPC）

内部 `cloud/mochi-mqtt` 已经内置 gRPC 鉴权钩子：

```proto
service IotMqttAuthService { rpc MqttAuth(MqttAuthRequest) returns (MqttAuthResponse); }
message MqttAuthRequest  { string username = 1; string password = 2; }
message MqttAuthResponse { int32 code = 1; string msg = 2; bool data = 3; }
```

后端提供同契约的 gRPC 服务（`internal/mqttrpc`）：

- `MQTT_GRPC_ENABLED=true` 时启动，默认监听 `:50051`（`MQTT_GRPC_LISTEN` 可覆盖）；
- broker 配置 `rpc.address: backend:50051`；
- `code=200 && data=true` 才放行。

> ⚠️ fork 的 `OnACLCheck` 目前直接返回 `true`，即**只鉴权、不隔离话题**。
> 本项目自带的 broker（HTTP 钩子）有完整 ACL；若使用 fork，需要在
> `hooks/auth/rpc.go` 里把 ACL 也改为 RPC 调用（后端已有 `CheckACL`）。

## 4. MQTT 信令（App ↔ WebRTC）

### 4.1 话题

| 方向 | 话题 |
|:--|:--|
| App → 后端 | `iot/<group_code>/signal/backend` |
| 后端 → App | `iot/<group_code>/app/<client_id>/signal` |

### 4.2 消息

```json
{"type":"offer","request_id":"uuid","client_id":"...","channel_id":123,"stream":"0BEBC201","sdp":"v=0..."}
{"type":"answer","request_id":"uuid","sdp":"v=0..."}
{"type":"error","request_id":"uuid","code":"...","message":"..."}
```

### 4.3 流程

```
App 调播放接口拿 stream
  → 连 MQTT（服务组凭据）
  → createOffer / setLocalDescription
  → publish offer
  → 后端 POST 到 ZLM /index/api/webrtc?app=rtp&stream=<stream>&type=play
  → 取 answer → publish 到 App 话题
  → App setRemoteDescription → onTrack 渲染
```

媒体仍由 App ↔ ZLM 直连；受限网络下用 TURN 中继。
MQTT 信令失败时，App 回退到原有 HTTP WHEP 模式。

## 5. TURN / STUN

### 5.1 关键事实

**coturn 没有 HTTP/RPC 鉴权回调。** 可用的外部授权方式只有：

1. TURN REST API（`static-auth-secret`）：短期、无状态；
2. SQL / Redis userdb：coturn 原生查询静态用户。

本项目按使用方拆成两套：

- **设备**：每个产品 × TURN 服务生成固定用户名/密码，存入
  `ac_iot_product_service`，并同步到 coturn SQL userdb（`turnusers_lt`，
  `hmackey=MD5(username:realm:password)`）；设备 OTA 下发该凭据。
- **App 播放**：`GET /app/rtc/ice-servers` 继续用 TURN REST 短期凭据
  （subject=用户 ID），避免把设备级静态账号暴露给 App。

### 5.2 接口

- 设备：`POST /iot/ota` → `service_groups[].services[]` 中 `protocol=TURN` 的项
  携带用户名/密码；
- App：`GET /app/rtc/ice-servers`（内部 `POST /rpc/turn/credentials`）→
  `{username,credential,ttl,expires_at,realm,urls}`。

### 5.3 部署约束

- `TURN_STATIC_AUTH_SECRET` 三处一致：`.env` / coturn / 后端；
- `TURN_REALM` 必须配置；
- `TURN_EXTERNAL_IP` 必须是客户端可达地址；
- `TURN_URLS` 不能写 compose 服务名。

## 6. 设备二维码与 SIP 绑定

### 6.1 二维码

为与参考 App（`neme-ai-app`）保持一致，二维码采用 **URL 格式**：

| 类型 | 格式 |
|:--|:--|
| 设备绑定码 | `https://boticz.cn/qrDevice/<产品编码>/<设备编码>` |
| 设备分享码 | `https://boticz.cn/deviceShareToken/<token>` |

- 扫码视为持有设备，App 调 `POST /app/iot/devices/bind-qr` 绑定到当前用户；
- 分享码调 `POST /app/iot/devices/claim`（一次性令牌）；
- App 同时兼容旧的 JSON 形式（`{"type":"device",...}` / `{"type":"device_share",...}`），
  仅作输入兼容，平台生成时不再使用。

### 6.2 SIP 携带设备编码与产品编码

GB28181 标准没有产品编码字段，平台约定在 **REGISTER** 与 **Keepalive MESSAGE** 上增加自定义头：

```
X-Device-Code: <业务设备编码>
X-Product-Code: <产品编码>
```

绑定规则：

0. **未同时携带 `X-Device-Code` 与 `X-Product-Code` 时不做任何产品绑定**：
   该设备按**独立 GB28181 设备**接入，只按 `gb_device_id` 走国标白名单；
   产品为可选项，OTA 对无产品设备返回空服务组。
1. REGISTER 先按国标编码查 `ac_device`；
2. 未命中时，若同时携带 `X-Device-Code` + `X-Product-Code`，且存在匹配的 IOT 设备与产品：
   - `gb_device_id` 为空 → 写入并置 `activated`，允许本次注册；
   - 已绑定同一编码 → 幂等；
   - 已绑定不同编码 / 产品不匹配 → **403 拒绝**（不允许静默改绑）；
3. 仍不命中 → 403（原有白名单语义）。

> 这保持了「SIP 设备必须是设备管理中已有的设备」这一核心约束，
> 同时允许设备在出厂信息与平台档案之间建立首次绑定。

## 7. App 添加设备

### 7.1 蓝牙配网

使用 Nordic UART Service：

| 用途 | UUID |
|:--|:--|
| Service | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| RX（写入） | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` |
| TX（通知） | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` |

JSON 帧（UTF-8 + `\n`）：

```json
{"cmd":"hello","product_code":"..."}         → {"status":"ok","device_code":"..."}
{"cmd":"wifi","ssid":"...","password":"..."}  → {"status":"ok"} / {"status":"error",...}
{"cmd":"bind","token":"..."}                  → {"status":"ok","device_code":"...","device_secret":"..."}
```

配网成功后 App 调 `POST /app/iot/devices/bind`。

### 7.2 扫一扫

- `device_share` → `POST /app/iot/devices/claim`
- `device` → `POST /app/iot/devices/bind-qr`
- 非本系统二维码、相机权限拒绝 → 明确中文提示

## 8. 服务鉴权信息复制

产品页面提供「复制鉴权信息」，内容为结构化 JSON：

```json
{
  "product": {"code":"...","name":"..."},
  "groups": [{
    "code":"webrtc","type":"webrtc",
    "services":[{"code":"mqtt","protocol":"MQTT","host":"...","port":1883,
                 "username":"...","password":"..."}]
  }],
  "mqtt": {"url":"mqtt://host:1883","topic_prefix":"iot/<group_code>"},
  "turn": {"urls":["..."],"realm":"..."}
}
```

- 明文密码只出现在 `GET /products/:id/credentials`，要求 `iot:product:update` 权限；
- 其余读接口继续返回 `****`；
- 前端提供「复制 JSON / 复制文本」两种格式。

## 9. 安全边界

| 项 | 取舍 | 缓解 |
|:--|:--|:--|
| 服务组密码明文入库 | 设备端必须拿到明文才能登录外部服务 | 组级凭据（影响面小）、高熵、可轮换、接口脱敏 |
| `device_secret` 明文入库 | 设备端需要比对 | 仅接口脱敏、可重置、每设备独立 |
| 分享令牌 | 单次可认领 | 认领后清空，可撤销 |
| 设备二维码 | 扫码即视为持有 | 二维码不含密钥；后台解绑接口 `POST /web/iot/devices/:id/unbind` 删除全部账号并清除激活状态 |
| SIP 自定义头 | 可被伪造 | 必须先通过产品+设备匹配；不匹配即 403 |

## 11. 未完成 / 风险

1. **真机依赖**：BLE 配网协议、设备端 MQTT/WebRTC 实现、SIP 自定义头均需固件配合，当前只能用模拟器与单测验证平台侧。
2. **内部仓库不可达**：`neme-ai-app` / `mochi-mqtt` 的 SSH 未授权，实现基于本项目约定与公开库；与内部 fork 的差异需对齐。
3. **SDK 兼容**：`flutter_blue_plus`、`mobile_scanner`、`mqtt_client` 需要真机权限与系统版本适配。
4. **TURN 中继端口**：compose 只开放 41 个端口，生产需按并发调整。
5. **产品服务凭据轮换**：按产品×服务轮换后，该产品下的设备需重新 OTA 才能拿到新凭据；
   当前无主动推送机制。TURN 账号会同步 coturn userdb。
6. **产品分享码无消费端**：`iot_product_share` JSON 目前只由平台生成/留存，App 未解析；设备码与分享码已有 App 消费端。
7. **设备 owner 并发唯一性**：应用层保证一台设备最多一个主账号，但缺少数据库部分唯一索引/行锁；高并发激活/认领理论上可能产生重复 owner，后续以迁移脚本补强。
8. **App 分享码展示**：分享页展示链接与复制，不渲染二维码图形（未引入 `qr_flutter`，沿用既定取舍）。
9. **列表 N+1**：IOT 三个列表按行补查服务组数/账号/服务项，数据量大时需由列表接口聚合字段。

## 12. 与参考 App（neme-ai-app）的差异

参考仓库已可访问（2026-10-24）。对比后确认的差异与取舍：

| 项 | 参考 App | 本项目 | 取舍 |
|:--|:--|:--|:--|
| 添加设备 | AP 配网 + 二维码（BLE 依赖被注释，见 pubspec） | BLE 配网 + 扫码；保留扫码 | 用户明确要求 BLE，按 Nordic UART 协议实现 |
| 设备二维码 | `boticz.cn/qrDevice/{product_name}/{device_id}` | 已对齐为 `https://boticz.cn/qrDevice/{product_code}/{device_code}` | 格式兼容，字段语义为产品编码/设备编码 |
| 分享二维码 | `boticz.cn/deviceShareToken/{token}` | 已对齐 | 一致 |
| MQTT 用途 | 远程控制指令（`LocalMqttClient.remoteControl`） | WebRTC SDP 信令（offer/answer） | 按用户「MQTT 作为信令」实现；两者可并存 |
| 媒体面 | LiveKit（`livekit_client`） | ZLM WHEP + TURN | 本项目媒体栈是 ZLM，未引入 LiveKit |
| 服务类型 | MQTT / WebRTC / RTSP / CloudStorage / Playback / LiveKit | gb28181 / webrtc / aichat + 协议项 | 按本项目需求定义；如需 LiveKit 可后续加协议项 |

> 若后续要求与参考 App 完全一致，需要引入 LiveKit 服务端与
> `ApplicationServiceTypes` 对齐；属于下一期范围，不在本次实现内。
