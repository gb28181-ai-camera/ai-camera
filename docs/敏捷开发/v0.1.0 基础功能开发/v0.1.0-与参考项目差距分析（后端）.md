## 1. 结论摘要

本次对照了 11 个维度（分层/中间件/鉴权/数据权限/响应 DTO/工具包/配置/迁移种子/测试/CI/可观测性），
**真实能力缺失 5 条**，其中 **P0 级 1 条**；另有 **6 条"看起来是差距、实际不是"**（参考项目自身是死代码或同样缺失），
以及 **13 条 ai-camera 反超参考项目**的地方。

最关键的 5 个差距与影响判断：

| 排序 | 差距 | 一句话影响 |
|---|---|---|
| 1 | **无任何定时任务框架** | `ac_device_upgrade_plan` 的 `plan_dt` **没有任何执行者**，定时升级永不生效（功能不可用，非体验问题） |
| 2 | **无序列号生成能力** | `ac_sequence` 表已建但全仓库零读写，业务单号无自动编号手段（能力缺失，长期易重号） |
| 3 | **无集中式数据权限测试** | 数据权限是安全属性，`ApplyToQuery` / 有效权限合并逻辑无针对性回归网（改动即裸奔） |
| 4 | **migrate 零 seed / 零 backfill** | GORM 新增带默认值的列**不回填存量行**，每次加列都要手工补 SQL 且无处记录（演进效率问题） |
| 5 | **上传落本机磁盘，无对象存储** | 单副本无碍，但 CI 是 `kubectl rollout restart`，**一旦扩到 >1 副本上传文件即时有时无**（扩副本即坏） |

需要特别指出：任务清单中怀疑的 **"事务中间件缺失""Recovery 中间件缺失""token 刷新/登录锁定/验证码/令牌黑名单缺失""cross_dept 语义遗漏""Redis 缺失"**，
经实地核对 **全部不是差距**——参考项目对应文件是死代码（3 行注释/无注册点）或同样缺失。详见 §2.2 与 §4。

## 3. ai-camera 做得更好的地方（13 条，逐条给证据）

### 3.1 安全 / 鉴权

1. **Casbin matcher 补齐了 `obj` / `act` 校验（参考项目存在真实越权漏洞）**
   - ai-camera `config/rbac_model.conf:19`：
     `m = keyMatch2(r.obj, p.obj) && r.act == p.act && (g(r.sub, p.sub) || g2(r.sub, p.sub) || g3(r.sub, p.sub))`
   - 参考项目 `config/rbac_model.conf:19`：
     `m = g(r.sub, p.sub) || g2(r.sub, p.sub) || g3(r.sub, p.sub)`
   - **影响判断**：参考项目的 matcher 完全没用到请求路径与方法——**只要用户拥有任意一个角色，访问任意路径、任意方法都会放行**，`AddPolicy(role, path, method)`（`pkg/perm/casbin.go:63-65`）写入的 p 策略形同虚设，接口级鉴权实质失效。ai-camera 另用 `keyMatch2` 顺带支持 `:id` 形式的路由参数（`config/rbac_model.conf:18` 注释）。

2. **JWT 里 `role_code` / 部门真填了值（参考项目恒为空 / 0）**
   - 参考项目 `internal/service/auth/auth_service.go:42`：`roleCode := ""`（硬编码空串），`:50`：`GenerateToken(..., roleCode, 0, dataPerm, ...)` 第 4 个实参（orgID）恒为字面量 `0` → JWT 的 `role_code` 与 `org_id` **永远是空/0**（`pkg/auth/jwt.go:11-20` 的 Claims 定义与 `internal/api/middleware/auth.go:64-65` 的写上下文全是空转）。
   - ai-camera `internal/service/system/auth_service.go:60-63` 用 `GetPrimaryRoleCode(ctx, user.ID)`（取有效角色中 sequence 最小者）填 `roleCode`，`:67-70,76` 用 `user.DeptID` 填 `deptID`。

3. **登录拒绝禁用账号 + 错误提示防账号枚举**
   - ai-camera `internal/service/system/auth_service.go:14-16`：统一 `errInvalidCredential`（不区分"用户不存在"与"密码错误"）；`:44-46`：`if user.Active != nil && !*user.Active { return 用户已被禁用 }`。
   - 参考项目 `internal/service/auth/auth_service.go:22-31`：无禁用校验（被禁用的账号仍能拿到有效 token），两种失败也未做统一的模糊化处理设计。

4. **Casbin 中间件的错误处理与响应体正确**
   - ai-camera `internal/api/middleware/auth.go:89-111`：`enforce` 返回 err → `utils.ServerError` 500；返回 `!ok` → `utils.Forbidden` 403；且先判 `username == ""` 短路返回 401。
   - 参考项目 `pkg/perm/casbin.go:42-58`：`if err != nil || !ok` 合并处理，**统一返回 403**（权限系统故障被伪装成"权限不足"，误导排查），并且**手写 `gin.H{...}` 绕过统一响应类型**——参考项目自己定义了 `utils.Forbidden`（`pkg/utils/response.go:66-71`）却**零使用**（`grep -c "utils.Forbidden(" internal/` = **0** 次；ai-camera = 1 次）。

### 3.2 工程健壮性

5. **统一查询串归一化中间件**
   - ai-camera `internal/api/middleware/normalize_query.go:24-60`：剔除"仅有空值"的查询参数（`allEmpty` 判定，`:41-52`），并在 `internal/api/router/router.go:24` 全局注册。它解决的问题在注释里写得很清楚（`:16-22`）：前端 Controller 对未填筛选项会发 `active=`，被绑成"非 nil 的 false"→ `WHERE active = false` → 用户/角色/岗位/通知列表**恒为 0 条**。
   - 参考项目无此中间件。

6. **全局操作日志（参考项目完全没有）**
   - ai-camera `internal/api/middleware/operation_log.go:22-77`：仅记 POST/PUT/DELETE/PATCH（`:25-29`），请求体截断至 4096B 防表膨胀（`:16`、`:36`），读体后 `NopCloser` 回写避免下游读到空 body（`:39`），模块名从路径推导（`:80-93`），审计写入失败不影响业务响应（`:74-75`）；挂在认证组 `internal/api/router/web.go:97`。
   - 参考项目**无全局操作日志**：`grep -rn "OperationLog" internal/` 仅命中 `pricelist_handler.go:224`、`purchase_handler.go:518-521` 等业务内日志，日志模型分散在各业务文件（`internal/model/pricelist.go:63`、`internal/model/purchase.go:166`）。
