# v0.1.0 需求覆盖度审计

> 版本: v0.1.0
> 审计日期: 2026-09-21
> 审计对象: AI摄像头操作手册（43-8101）全部功能点
> 审计方法: 以 `docs/需求文档/AI摄像头操作手册 - 43-8101.docx` 正文为唯一权威，逐条回到代码核对（backend/internal 路由+service+repository、frontend/src/admin/pages、app/lib/pages）；对可疑项额外通过运行中的测试后端（`http://localhost:8081`，admin/admin123）实地打接口验证。

## 1. 结论摘要

| 分类 | 数量 | 占比 |
|:---|---:|---:|
| ✅ 已实现 | 171 | 85.9% |
| ⚠️ 部分实现 | 17 | 8.5% |
| 🚧 占位/假实现 | 6 | 3.0% |
| ❌ 未实现 | 5 | 2.5% |
| **合计** | **199** | **100%** |

**一句话结论**：CRUD 与查询类功能覆盖度极高（所有菜单页面、所有增删改查、所有列表字段与搜索条件均已落地），但**「平台主动做事」的能力几乎全部缺失** —— 通知不发送、告警不产生、语音不下发、升级不下发、时间不同步、视频无流。这些缺口集中在「设备/人之间的消息与指令通路」，而非「页面与表单」。因此「86% 已实现」这个数字具有误导性：**被算作已实现的 171 项里，有相当一部分是"配置能存下来但没有任何消费者"的空转功能**（通知人、通知类型、报警频率、第三方凭据、`voice_played` 等）。

判定边界说明：手册功能点在「页面 + 接口 + 交互存在且行为与手册字面一致」时记为 ✅；即使其下游效果依赖尚未接入的外部系统（如第三方 SDK、流媒体网关），只要手册该条只描述到页面行为，就按 ✅ 计，并把下游缺口单独列在第 2、4 节，避免重复计数掩盖问题。

## 2. 关键缺口（P0/P1）

### P0-1 系统通知（ac_notification）从不产生 —— 写入方不存在

- **手册原文**（8.6.8 系统通知）：「在系统通知中可查看设备告警信息、风险通知信息和巡检通知信息……巡检消息通知会在指派的巡检人员账号中显示。当有未读消息时，图标上会有红点显示，已读后就会隐藏。」
- **现状**：表、模型、仓储、Service、Web 接口、移动端接口、前端页面**全部齐备**，但**全代码库没有任何一处调用 `NotificationService.Push`**。风险上报（`risk_service.go:253-255`）与告警上报（`alarm_service.go:206`）都用注释把责任推给一个**并不存在的定时任务**：

  ```go
  // 系统通知（ac_notification）由统计/定时任务扫描未读风险后统一生成，
  // 以避免风险切片与通知切片相互依赖。
  ```

- **证据**：
  - 写入能力定义在 `backend/internal/service/system/notification_service.go:82-101`（`Push`），调用方搜索 `grep -rn "\.Push(" --include=*.go` 结果为 0。
  - 全库无任何业务调度器：`grep -rni "cron|ticker|time.AfterFunc|scheduler" backend/internal backend/cmd backend/pkg` 仅命中 `pkg/perm/casbin.go:120`（Casbin 策略重载 ticker），无业务定时任务。
  - 实地验证：`GET /web/system/notifications` 返回 `{"total":0,"items":[]}`。
  - 前端页面注释与事实相反：`frontend/src/admin/pages/system/NotificationList.tsx:31` 写「通知由后端在告警、风险、巡检流程中写入（ac_notification）」，实际从未写入。
- **影响**：系统通知页永远为空；移动端 `未读通知` 待办恒为 0（`backend/internal/service/app/app_service.go:252,290`）；顶部红点永不出现；手册第 8.6.8 节 4 个功能点全部落空。同时导致 5.1/5.3 的「消息通知」列与手册语义脱节 —— 该列实际读的是**风险/告警记录自身**的 `read` 字段，而不是 `ac_notification`。
- **建议**：二选一并统一。方案 A（推荐，成本低）：在 `RiskService.Report` / `AlarmService.Report` / `InspectService.CreateTask` 中直接调用 `NotificationService.Push`，按告警/风险通知设置里的 `notify_user_ids` 展开接收人。方案 B：真正实现手册隐含的扫描任务并引入调度器。**必须同时决定 5.1/5.3「消息通知」列的数据源**，否则两套"已读"状态会长期并存。

### P0-2 通知推送整体不生效：通知人、通知类型、报警频率三项配置无任何消费者

- **手册原文**（8.2.1）：「可配置告警类型（离线告警、电量告警、流量告警）的通知人员、通知类型及报警频率等内容」；（8.2.2）：「可配置风险类型的通知人员、报警频率及通知类型等内容」。
- **现状**：`AlarmSetting` / `RiskNotifySetting` 两张表的读取仅出现在自身 CRUD 与「删除告警类型前的引用计数校验」。配置存得下、查得出、删得掉，**但没有任何代码读取它们去决定"通知谁、用什么方式、隔多久"**。
- **证据**：
  - `grep -rln "AlarmSetting\|RiskNotifySetting" --include=*.go backend/internal` 命中文件为 handler/router/migrate/dto/model/repository(自身)/basic 服务。其中唯一的跨模块引用是 `backend/internal/repository/alarm_type_repo.go:87-91` 的 `CountAlarmSettings`（仅做删除前引用校验）。
  - `NotifyFreq`（报警频率）字段在整个后端除 CRUD 外无任何读取点。
- **影响**：8.2.1、8.2.2 两节共 6 个「配置类」功能点表面上已实现，但配置**零效果**。配合 P0-1，用户配置了通知人员也不会有人收到任何消息。
- **建议**：与 P0-1 合并处理 —— 让 `Push` 的接收人集合来自这两张表，`notify_type` 决定站内/App 推/短信，`notify_freq` 做发送节流。

### P0-3 设备告警不会自动产生（离线/电量/流量三类告警无检测逻辑）

- **手册原文**（5.3 设备告警）：「设备告警中可查看设备的告警信息……」；（8.2.1）明确告警类型为「离线告警、电量告警、流量告警」。
- **现状**：`alarm_service.go` 只有 `Report` 一条写入路径，且必须由设备主动通过 API Key 调用 `POST /web/alarms/report`。心跳处理 `DeviceService.Heartbeat`（`backend/internal/service/device/device_service.go:344-412`）**只更新设备快照并追加一条 DeviceHistory，不判断电量低于阈值、不判断流量不足、不做心跳超时检测**。
- **证据**：
  - 全库 `model.AlarmRecord{` 字面量构造仅一处：`backend/internal/service/alarm/alarm_service.go:168`（即 `Report`）。
  - 无调度器（同 P0-1），因此「心跳超时 → 离线」这类必须由服务端时间驱动的判定在架构上无处安放。
  - `AlarmSetting.Threshold`（`backend/internal/model/notify.go:37`，注释「电量告警阈值(%)、流量告警阈值(MB)」）无任何读取点。
  - 实地验证：测试库里唯一的告警（`content: "设备心跳超时，已离线"`）来自 `docs/开发文档/数据库设计/sql/init/01-初始数据.sql` 的种子数据，而非运行期生成。
- **影响**：告警列表只会有种子数据与设备主动上报的数据；「离线告警」在原理上无法由平台产生。
- **建议**：引入一个最小调度器（如每 60s 扫描 `last_beat_dt` 超时设备 + 电量/流量阈值），复用 `AlarmService.Report` 的落库逻辑。

### P0-4 语音播报无下行通道：`voice_played` 是死字段

- **手册原文**（8.1.2 语音配置管理）：「语音配置管理中可配置风险类型的播报音频……点击试听，可试听该风险配置的音频」；日常操作流程隐含风险触发时设备现场播报。
- **现状**：语音配置只有 CRUD（`voice_config_service.go` 仅 `Page/Create/Update/Delete`，见 `backend/internal/api/handler/web/voice_config_handler.go:47,73,101,132`，无第五个方法）。风险记录上**已经预留了 `voice_played`（是否已语音播报）列却从未被读写**。
- **证据**：
  - `backend/internal/model/risk.go:58`：`VoicePlayed *bool \`gorm:"column:voice_played;default:false;comment:是否已语音播报"\``
  - `grep -rn "voice_played\|VoicePlayed" --include=*.go backend/internal` 仅命中该模型定义一处（其余命中都在生成物 `backend/docs/*_docs.go` 中）。
  - 全库无 MQTT / 设备下行 / 指令下发通道（见 P0-5 证据）。
  - 前端 `frontend/src/admin/pages/setting/VoiceConfigList.tsx:184-190` 的「试听」「下载文件」是浏览器 `<audio>` 与本页链接，属管理端自听，与设备播报无关。
- **影响**：手册的语音播报能力 = 一个"存音频文件"的表单。设备永远不会收到任何音频。
- **建议**：明确下行通道（MQTT topic 或设备轮询接口 `GET /device/voice-configs`），在下发成功后回写 `voice_played`。当前 `voice_played` 字段的存在会误导后续开发者以为该功能已通。

### P0-5 定时升级计划永远不会被执行

- **手册原文**（8.3.1）：「远程升级可对设备（固件和模型）进行现在升级或定时升级……若选择定时升级后，在升级计划中会有一条定时升级任务，可点击取消升级取消该任务。」
- **现状**：`UpgradeDevices` 的 `plan` 分支只写入 `status=pending` 的 `ac_device_upgrade_plan` 记录（`backend/internal/repository/firmware_repo.go:357`）；`cancel` 与 `batch-cancel` 会置为取消。**没有任何代码把到期的 pending 计划转成 done 并写入升级记录**（无调度器）。
- **证据**：
  - `grep -rn "UpgradePlanPending" --include=*.go backend/internal` 命中：定义（`model/upgrade.go:11`）、创建（`firmware_repo.go:357`）、单条取消（`firmware_repo.go:437`）、批量取消（`firmware_repo.go:461`）—— 没有任何"执行"路径。
  - "现在升级"路径 `FirmwareRepo.UpgradeNow`（`firmware_repo.go:259-320`）的真实行为是：写一条 `upgrade_type=now, status=done` 的记录 + 用 `tx.Model(&model.Device{}).Where(...).Updates(...)` 把 `firmware_ver`/`model_ver` 改成目标版本号。**没有任何字节下发给设备**（无下行通道，见下）。
- **影响**：定时升级 100% 不会发生，计划列表只增不减（除手动取消）；"现在升级"也只是数据库层面的版本号改写，设备端固件实际未变。测试库 `GET /web/upgrades/plans` 返回 `total:0` 属正常（无种子），但即便创建也永不变更状态。
- **建议**：实现计划执行器（扫描 `plan_dt <= now AND status = pending`），并先解决下行通道问题，否则执行器依然只能改数据库。

### P0-6 「同步时间」不向设备下发任何指令

- **手册原文**（8.1.1 设备管理）：「同步时间：点击同步时间，可同步设备与服务器时间。」
- **现状**：Service 实现就是一次数据库 UPDATE，把设备的 `last_beat_dt` 改成当前时间；Handler 顺带把服务器时间回显给前端。
- **证据**：
  - `backend/internal/service/device/device_service.go:323-329`：
    ```go
    // SyncTime 同步设备时间：把 last_beat_dt 置为当前时间。
    func (s *DeviceService) SyncTime(ctx context.Context, id int64) error {
        if _, err := s.Get(ctx, id); err != nil { return err }
        return s.repo.UpdateFields(ctx, id, map[string]interface{}{"last_beat_dt": time.Now()})
    }
    ```
  - 前端提示语强化了误导：`frontend/src/admin/pages/setting/DeviceList.tsx:205` → `时间同步成功，服务器时间：${res.data?.sync_time}`。
- **影响**：这是典型的"看着有其实没有"。`last_beat_dt` 被写成 now 还会**污染在线状态判定与历史采样**（心跳超时检测依赖该字段）。
- **建议**：至少改文案为「已记录服务器时间（待设备下次心跳生效）」；正解是走下行通道下发对时指令。

### P1-1 实时视频/录像：字段可用但无流、无播放内核、浏览器无法播 RTSP

- **手册原文**（2 实时监控）：「可单屏、4 宫格、9 宫格显示视频监控，需选择区域和摄像头后才会显示视频监控。」
- **现状**：前端**确实**渲染了真实 `<video src={device.stream_url}>`（不是占位组件），九宫格布局、区域/摄像头选择、离线与无信号分支都真实存在。问题在下游：
  1. `stream_url` 只能由管理员在设备表单手工填写（`DeviceList.tsx:489-491`，placeholder `rtsp://192.168.1.10/live`），设备心跳上报**不带** `stream_url`；
  2. 无流媒体网关做 RTSP→HLS/FLV 转封装，前端**没有 hls.js/flv.js 播放内核**，浏览器原生 `<video>` 无法播放 RTSP；
  3. 种子数据里 `stream_url` 为空串，开箱即用状态下每个窗口都显示「无信号」。
- **证据**：
  - `frontend/src/admin/pages/monitor/RealtimeMonitor.tsx:106-114`（真实 video 标签）与 `:116-120`（「设备无信号」分支）。
  - `frontend/src/admin/pages/risk/AiMonitor.tsx:192-200`（同样的 `<video src={streamUrl}>`）。
  - 写入点仅两处，且都来自管理端表单：`backend/internal/service/device/device_service.go:144`（Create）、`:232-234`（Update）。
  - 心跳上报字段不含流地址：`request.DeviceHeartbeatReq`（`backend/internal/dto/request/device.go`）。
  - 实地验证：`GET /web/devices` 返回 `"stream_url":""`。
  - 项目自身也承认：`docs/敏捷开发/v0.1.0 基础功能开发/待完成事项.md:29` 标注「播放的是**占位播放器**」——该描述不准确（已是真实 video 标签），但结论「未接入真实流」正确。
- **影响**：三个分屏档位、AI监控、设备监控、风险监控的「查看实时视频/实时监控」按钮全部**结构性可用但内容为空**。
- **建议**：接入流媒体网关并把转封装后的 HLS 地址由后端动态生成下发；同时补 `hls.js`，并让设备心跳上报 `stream_url`。

### P1-2 地理可视化不是地图

- **手册原文**（GIS查看）：「可在GIS地图中查看设备的相关位置，鼠标移至图标上可查看该设备的相关信息。」
- **现状**：**未引入任何地图库**。实现是 CSS 渐变网格底板 + 把经纬度线性归一化到 5%~95% 百分比坐标后绝对定位图标。页面右下角自己标注了「图标位置由设备经纬度归一化计算，非真实底图」。
- **证据**：
  - `frontend/src/admin/pages/device/GisMap.tsx:27-32` 注释：「不引入地图库 —— 用 CSS 网格底板 + 按经纬度归一化到百分比坐标的绝对定位图标呈现」。
  - `GisMap.tsx:143-146`：`backgroundImage: 'linear-gradient(...)'` 网格。
  - `GisMap.tsx:189-191`：「图标位置由设备经纬度归一化计算，非真实底图」。
  - `grep -rn "leaflet\|mapbox\|amap\|bmap\|openlayers\|cesium" frontend/package.json` 无结果。
- **影响**：悬停查看信息、点击「查看风险」跳转两个交互**是真实可用的**；但「GIS 地图」这一核心预期未达成 —— 图标位置与真实地理无关（相对坐标随数据集变化而漂移，不同区域筛选下同一设备位置会不同），无法作为 GIS 使用。
- **建议**：接 Leaflet + 高德/天地图底图（成本低），或明确降级需求为「设备分布示意图」并改文档措辞。

### P1-3 第三方平台（个推 / 腾讯云短信）只存配置，不调用 SDK

- **手册原文**：（8.5.1）「可配置个推账号。」（8.5.2）「可配置腾讯云短信。」
- **现状**：两项均为 `ac_thirdparty_config` 表中的键值对读写，含脱敏回显（前 4 位 + `****`）。**`go.mod` 中没有任何个推/腾讯云 SDK 依赖**，代码中无任何第三方 HTTP 调用。
- **证据**：
  - `backend/internal/service/setting/setting_service.go:224-272`（`GetGetui/UpdateGetui/GetSms/UpdateSms`，纯键值 upsert）。
  - 全量依赖清单 `backend/go.mod` 中仅有 gin/gorm/viper/jwt/casbin/zap 等基础库，无 `getui`、`tencentcloud-sdk-go`。
- **影响**：手册该两条字面只要求「可配置」，故按 ✅/⚠️ 边界记为部分实现；但结合 P0-1/P0-2，配置的凭据没有任何消费方，配置页实质是"凭据仓库"。
- **建议**：若产品预期是"配置后能收到 App 推送/短信"，则属未实现，需补 SDK 接入与发送队列。

### P1-5 升级管理缺少「升级计划/升级记录」的搜索交互

- **手册原文**（8.3.1）：「（升级计划）输入固件名称进行搜索。」「（升级记录）选择设备名称、设备编号、操作时间等条件进行搜索。」
- **现状**：`DeviceUpgradeList.tsx` 三个 Tab 中只有「可升级设备」Tab 有 `SearchBar`（`:321`），「升级计划」「升级记录」两个 Tab **没有搜索栏**。此外「可升级设备」的「当前固件」筛选是**前端本页过滤**（`firmwareFilter` 仅作用于 `devices`，注释写着"本页筛选"，`DeviceUpgradeList.tsx:157-159,347`），跨页时结果不完整。
- **证据**：`grep -n "SearchBar" frontend/src/admin/pages/upgrade/DeviceUpgradeList.tsx` 仅命中 `:321` 一处，位于 `devicesTab` 内。
- **影响**：设备量增长后升级计划/记录无法检索；固件筛选结果随分页漂移。
- **建议**：为 plans/records 补 SearchBar 并落到后端查询条件；把固件筛选下推到 `pageDevices`。

## 5. 建议的补齐优先级

### 第一梯队（P0，同一批解决，相互强耦合）

**核心判断：先把「消息与指令的下行通路」打通，否则后续所有功能都只能用"改数据库"冒充。**

1. **落地站内通知写入**（P0-1）—— 在 `RiskService.Report` / `AlarmService.Report` / `InspectService.CreateTask` 直接调 `NotificationService.Push`。**决策点**：5.1/5.3 的「消息通知」列是改为读 `ac_notification`，还是保留记录自身的 `read` 并删除"通知"语义？必须二选一，否则双份已读状态长期并存。
2. **让告警设置/风险通知设置生效**（P0-2）—— `Push` 的接收人集合来自 `AlarmSetting.notify_user_ids` / `RiskNotifySetting.notify_user_ids`，`notify_type` 决定通道，`notify_freq` 做节流。与 1 同批完成，成本极低（配置表已就绪）。
3. **引入最小业务调度器**（P0-3 / P0-5）—— **一个**调度器同时解决三件事：心跳超时→离线告警、电量/流量阈值告警、到期升级计划执行。这是当前架构最缺的一块，且是 3 个 P0 的共同前置。
4. **补设备下行通道**（P0-4 / P0-5 / P0-6）—— 选型建议二选一：MQTT（实时性好，适合对时/切模式/播报）或设备轮询接口 `GET /device/commands`（实现简单，适合升级/语音拉取）。打通后 `voice_played`、`SyncTime`、`UpgradeNow` 才有真实语义。在通道就绪前，**建议先修正前端误导文案**（"时间同步成功"、"已下发升级"），避免继续扩大"看着有其实没有"的面积。

### 第二梯队（P1，可持续投入）

5. **视频链路**（P1-1）—— 接入流媒体网关做 RTSP→HLS 转封装 + 前端补 `hls.js`；同时让设备心跳上报 `stream_url`，并由后端动态签发带时效签名的播放地址。此项工作量最大，建议单独立项。
6. **GIS 换真地图**（P1-2）—— Leaflet + 高德/天地图，半天可完成，收益直观；若产品接受降级，则应改需求文档措辞而非保留"GIS"之名。
7. **升级管理补搜索**（P1-5）+ **固件筛选下推后端**。
8. **第三方平台 SDK 接入**（P1-3）—— 取决于产品是否承诺"配置后能收到推送/短信"；若承诺则属未实现，需排期。
9. **操作日志导出改 xlsx**（P1-4）—— 引入 `excelize` 或改文档措辞，二选一即可，成本低。

### 第三梯队（文档与信任修复）

10. **清理代码中的"甩锅注释"**（`risk_service.go:253-255`、`alarm_service.go:206`）与前端不实注释（`NotificationList.tsx:31`）—— 这些注释会把下一个接手的人引向错误方向，是本次审计中成本最低、收益明确的一项。
