## 四、鉴权体系实现要点（四级权限叠加）

本项目鉴权与 boticz-mes 保持同一套方案，分四层叠加，任一层失效都会导致越权，因此实现时
对每一层都做了显式约束。

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  第 1 层：JWT 签发                                                            │
│  文件：pkg/auth/jwt.go   签发：internal/service/system/auth_service.go        │
│                                                                              │
│  claims = { user_id, username, role_code, dept_id, data_perm, company_id,    │
│             cross_dept_ids }                                                 │
│  算法：HS256；有效期：jwt.expire_hours（开发/测试环境 7200 小时）              │
└────────────────────────────────┬─────────────────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│  第 2 层：Auth 中间件（认证）                                                  │
│  文件：internal/api/middleware/auth.go  → AuthMiddleware.Handler()            │
│                                                                              │
│  ① 校验 Authorization: Bearer <token>（缺失/格式错误/无效分别返回不同 message） │
│  ② 写入 gin.Context：handler 通过 c.GetInt64("user_id") 读取                  │
│  ③ 写入 Go Context：model.WithUsername/WithDeptID/WithUserID                  │
│     → 驱动 BaseModel 的 BeforeCreate/BeforeUpdate 钩子自动填充审计字段与 dept_id │
└────────────────────────────────┬─────────────────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│  第 3 层：Casbin RBAC（鉴权）★ 本版本核心修正                                 │
│  文件：pkg/perm/casbin.go + config/rbac_model.conf                            │
│                                                                              │
│  p 策略来源：角色(role.code) → 菜单(ac_role_menu_rel) → 菜单API(ac_menu_api)    │
│             即 p = (roleCode, apiPath, method)                                │
│                                                                              │
│  三条角色继承链：                                                              │
│    g  ：用户登录名 → 角色编码（ac_user_role_rel 直接分配）                     │
│    g2 ：部门编码   → 角色编码（ac_dept_role_rel 部门继承）                     │
│    g3 ：岗位编码   → 角色编码（ac_post_role_rel 岗位继承）                     │
│                                                                              │
│  matcher（修正后）：                                                          │
│    keyMatch2(r.obj, p.obj) && r.act == p.act                                  │
│      && (g(r.sub, p.sub) || g2(r.sub, p.sub) || g3(r.sub, p.sub))            │
└────────────────────────────────┬─────────────────────────────────────────────┘
                                 ▼
┌──────────────────────────────────────────────────────────────────────────────┐
│  第 4 层：数据权限（行级过滤）                                                 │
│  文件：pkg/utils/data_scope.go  → NewDataScope(c).ApplyToQuery(q, "x.dept_id") │
│                                                                              │
│  all        → 不过滤（超级管理员）                                            │
│  cross_dept → dept_id IN (本部门 + cross_dept_ids)                            │
│  dept       → dept_id = 本部门                                                │
│  personal   → dept_id = 本部门 AND created_by = 当前用户                       │
│  （dept_id 为空时降级为 created_by 过滤）                                      │
│                                                                              │
│  dept_id 为空的表（ac_menu、ac_role 等）不做行级过滤                            │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 4.1 策略一致性（多副本部署）

| 机制 | 实现 | 作用 |
|:---|:---|:---|
| 授权变更即时生效 | `role_service.syncCasbinForRole(ctx, roleID)` 重建该角色的 `p`/`g`/`g2`/`g3` 并 `ReloadPolicy()` | 单副本立即生效 |
| 多副本最终一致 | `bootstrap` 中 `casbin.StartAutoReload(5 * time.Minute)` | 其他 Pod 在最长 5 分钟内同步 |
| 定时重载 | `config.yaml` 的 `casbin.auto_load_interval` 可调 | 权限生效时效与数据库压力的权衡 |
| 初始化降级 | Casbin 初始化失败时 `globalCasbin = nil`，路由使用放行中间件并打印显著告警 | 权限故障不阻塞服务启动，但会通过日志与健康检查暴露 |

### 4.2 菜单树双用途

菜单树（`ac_menu`）同时驱动两件事，二者必须保持一致：

| 用途 | 机制 | 前端读取 |
|:---|:---|:---|
| 侧边栏渲染 | `GET /web/profile/menus` 返回按角色过滤的菜单树（含祖先目录） | `DynamicIcon` + antd `Menu` |
| 按钮级权限 | 菜单的 `permission_code` 作为权限码下发 | `LoginData.permissions` → 前端按权限码控制按钮显隐 |

> **注意**：菜单的 `platform` 字段区分 `web` 与 `mobile`，Web 与 App 登录接口返回不同平台的菜单树。

## 五、与 boticz-mes 的差异与改进

v0.1.0 的后端架构、鉴权方案、响应类型规范、E2E 规范**主动对齐** boticz-mes 的成熟实践，
同时在若干处做了修正与改进。

### 5.1 核心改进：Casbin matcher 补齐接口与方法校验（修复鉴权漏洞）

这是本版本**最重要的一处修正**。

| 项 | boticz-mes 原方案 | AI Camera v0.1.0 |
|:---|:---|:---|
| matcher | `m = g(r.sub, p.sub) \|\| g2(r.sub, p.sub) \|\| g3(r.sub, p.sub)` | `m = keyMatch2(r.obj, p.obj) && r.act == p.act && (g(r.sub, p.sub) \|\| g2(r.sub, p.sub) \|\| g3(r.sub, p.sub))` |
| 判定输入 | 只使用 `r.sub`（用户）与 `p.sub`（角色） | 额外使用 `r.obj`（请求路径）与 `r.act`（请求方法） |
| 实际效果 | **只要用户拥有任意角色，且该角色在 `casbin_rule` 中登记过任意一条 `p` 策略，就会被放行到所有接口** | 鉴权粒度回到「角色 → 接口路径 + HTTP 方法」 |
| 风险表现 | 登录后「什么菜单都能点、什么接口都能调」；接口级鉴权形同虚设，只有菜单显隐在起作用（前端隐藏按钮 ≠ 后端拒绝请求） | 未授权接口返回 403「权限不足」 |

**漏洞成因**：Casbin 的 `policy_effect = some(where (p.eft == allow))` 在 matcher 只判断
角色成员关系时，等价于「存在一条 `p` 策略，其 `p.sub` 属于该用户」——而 `p` 策略的
`p.obj` / `p.act` 两个字段**完全没有参与匹配**。因此只要角色被授予过任何一个菜单（必然产生
至少一条 `p` 策略），该角色的所有用户就获得了全部接口的访问权。

**修复要点**：

1. `keyMatch2(r.obj, p.obj)` —— 用 `keyMatch2` 而非 `keyMatch`，以支持 `/web/devices/:id`
   形式的路径参数（例如 `p.obj = /web/devices/:id` 可匹配 `r.obj = /web/devices/42`）。
2. `r.act == p.act` —— 精确匹配 HTTP 方法，避免「有 GET 权限就能 DELETE」。
3. 中间件传递的是 Gin 的 `c.Request.URL.Path`（真实路径）与 `c.Request.Method`：

   ```go
   // internal/api/middleware/auth.go
   ok, err := enforce(username, c.Request.URL.Path, c.Request.Method)
   ```

4. 策略来源必须完整 —— `ac_menu_api` 表登记「菜单 → 接口路径 + 方法」，`syncCasbinForRole`
   由「角色 → 菜单 → 菜单 API」三级推导出全部 `p` 策略。缺失登记会导致**正常用户被误拒**。

**验证方式**（接口测试必测项，见测试计划 4.3 节）：

| 场景 | 期望 |
|:---|:---|
| 用户有角色 A（已授权 `/web/risks` GET），请求 `DELETE /web/risks/1` | 403「权限不足」 |
| 用户有角色 A，请求 `/web/system/users`（角色 A 未授权该菜单） | 403「权限不足」 |
| 用户有角色 A，请求 `/web/risks?page=1` | 200 |

> **注意**：该修正的连带要求是 `ac_menu_api` 的数据必须完整 —— 每新增一个端点，都要在
> 「菜单管理 → 菜单 API」中登记，否则**所有非超级管理员用户**都会被 403 拦下。
> 这是上线后最容易出现的「权限问题」，排查时先看 `ai_camera_casbin_deny_total` 指标
> 与 `ac_menu_api` 是否覆盖了该路径。

### 5.2 其他差异与改进

| 维度 | boticz-mes | AI Camera v0.1.0 | 改进理由 |
|:---|:---|:---|:---|
| **业务前缀** | `mes_` | `ac_` | 与项目命名空间一致，避免与 MES 表混用；同时便于备份脚本按前缀筛选表 |
| **设备上报鉴权** | 无独立设备上报通道 | 新增 `ApiKeyAuth`（`X-Api-Key` → SHA256 → `ac_api_key`），**独立于 Casbin 分组** | 设备无用户会话，且上报频率高（心跳默认 60s/台），不适合走 JWT 与 Casbin |
| **模型规模** | 12 个模型文件 / 82 张表 | 9 个模型文件 / 38 张表 | 业务面更窄，模型按领域归并（`device.go` 一个文件承载 6 张资源管理表） |
| **时序数据** | 无专门时序表 | `ac_device_history` 复合索引 `(device_id, sampled_dt)` | 设备历史记录需支撑近 3 日曲线与一周状态回放 |
| **数据权限列** | `company_id` | `dept_id` | 本项目按**部门**而非公司划分数据归属，更贴近「区域管理员 / 安全员 / 巡检员」的组织形态 |
| **迁移策略** | AutoMigrate 按表循环 | `AutoMigrate(38 models...)` **一次性 fail-fast** | 逐表循环会静默跳过失败的表，导致表结构漂移；一次性调用任一失败即中止 |
| **初次建表** | 纯 DDL 或纯 AutoMigrate | **DDL 脚本建表 + AutoMigrate 增量** | DDL 脚本可评审、可版本化；AutoMigrate 负责新增列与列类型变更 |
| **前端工程** | 管理后台单入口 + 独立官网 | **单工程双入口**（`index.html` base `/admin/` + `website.html` base `/`） | 官网与管理后台共享 `shared/utils`，减少重复依赖与构建配置 |
| **E2E Modal 选择器** | 曾使用通用 `.ant-modal` | **强制 `e2e-xxx-modal` class**，并在 CLAUDE.md 中固化清单 | 嵌套弹窗（表单 Modal 内开选择器 Modal）场景下通用选择器会匹配错层 |
| **响应类型** | `PageResp` 模糊类型有历史遗留 | 从第一天起**只用** `RPageXxx` / `RXxxList` / `RXxx` 三类 | 避免「同一端点有时分页有时不分页」的契约破坏 |
| **文档前置** | 边写边补文档 | 先冻结 `00-接口契约.md`（200 条路由 + 四层签名）再实现代码 | 四层命名逐字对齐契约，router 可一次性装配成功 |

### 5.3 从 boticz-mes 继承的实践

| 实践 | 落地位置 |
|:---|:---|
| 分层架构 Handler → Service → Repository → Model | `internal/` 四层，**Handler 不得直接调用 Repository** |
| `Bootstrap` 在 `init()` 中自动装配 | `internal/bootstrap/main.go`（含 `SetXxx()` 测试注入点） |
| `BaseModel` 软删除 + 审计字段 | `internal/model/base.go`（含 Context 驱动的自动填充钩子） |
| 统一 `{code, message, data}` 响应 | `pkg/utils/response.go` |
| 类型化分页响应 | `internal/dto/response/`，21 个文件 |
| 关联表查询必须展示名称字段 | Repository 层统一 `Preload`（`risk_type.name`、`device.name`、`region.name`） |
| Swagger 驱动前端代码生成 | `gen-swagger.sh` → `api-gen.sh` → `generated/`（**禁止手写 API 请求**） |
| 测试事务隔离 `WithTx` | `backend/tests/testutil/testutil.go` |
| 冒烟测试串行 + `99-` 收尾 | `frontend/e2e/smoke/`（`--workers=1`） |
| 静态路由先于 `:id` 注册 | `web.go` 中 `/devices/modes`、`/devices/iot-cards` 等置于 `/:id` 之前 |

## 八、结论

v0.1.0 完成了「从 0 到 1」的平台搭建：**38 张表、209 个端点、48 个页面、四级鉴权体系、
50 份设计文档**全部交付，四个可运行产物（后端 / 管理后台 / 官网 / 移动端）齐备，
业务闭环（设备上报 → 风险复核 → 处理归档）与操作手册的日常操作流程逐步对应。

本版本最具价值的产出不是代码量，而是两件事：

1. **先冻结契约再实现** —— `00-接口契约.md` 先行锁定 200 条路由与四层方法签名，
   使 170 个 Go 文件的分层命名能够一次性装配成功，避免了「接口对不上、反复返工」。
2. **修掉了一处真实的鉴权漏洞** —— Casbin matcher 补齐 `keyMatch2(r.obj, p.obj) && r.act == p.act`，
   把「只校验角色成员」的接口级放行改回「角色 → 接口 + 方法」的真实鉴权。

同时必须承认：**测试是本版本最大的短板**。规范与用例清单齐备，但自动化用例实现不足，
当前交付可信度主要建立在契约约束与代码评审之上。补齐测试用例已列为 v0.2.0 的 P0 事项。
