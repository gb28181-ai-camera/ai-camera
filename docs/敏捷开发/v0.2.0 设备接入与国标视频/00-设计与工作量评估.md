## 1. 背景与目标

### 1.1 现状：v0.1.0 的能力边界

v0.1.0 交付的是一个**纯管理平台**，视频能力完全空缺：

| 维度 | v0.1.0 实际状态 | 证据 |
|:--|:--|:--|
| 流媒体 | 仓库内**零** SIP/GB28181/RTSP/RTP/ZLMediaKit 代码与依赖 | `backend/go.mod` 无任何流媒体库 |
| 实时监控 | HTML5 `<video src={stream_url}>` 占位播放器 | `frontend/src/admin/pages/monitor/RealtimeMonitor.tsx:106-119` |
| 流地址 | `ac_device.stream_url` 是管理员手填字符串，设备心跳不上报该字段 | `internal/model/device.go:54` |
| 设备接入 | 管理员手工 CRUD 建档 + 按数字 ID 上报心跳，无注册/激活概念 | `DeviceService.Create` 写死 `Status: offline` |
| 设备身份 | `device_code`（业务编号，如 `CAM_001`）是唯一身份 | `internal/model/device.go:23` |
| 通道 | **完全没有通道概念** | `ac_device` 无相关字段与表 |
| AI 识别 | 设备端推理，平台只接收结果 | `POST /web/risks/report`（ApiKey） |

`docs/敏捷开发/CHANGE_LOG.md` 已将「视频流为占位播放器」列为已知限制，归入 v0.2.0。

**基线数据**（2026-10-15 实测）：211 条路由（web 190 + app 20 + health 1）、41 张 `ac_` 表、`internal/model` 1107 行。

### 1.2 需求

1. **设备管理增强**：支持设备注册、激活等全生命周期管理。
2. **GB28181 视频平台**：实现 WVP-Pro 的全部功能（核心是 SIP 协议服务）。**SIP 设备必须是设备管理中已存在的设备，未登记的设备拒绝接入。**
3. **音视频与语音**：ZLMediaKit 承担推流与转协议，Pipecat 接入语音 Agent。
4. **移动端**：App 能查看设备实时画面、回放、控制云台，并接收 AI 监测事件。

### 1.3 范围决策

| # | 决策 | 理由 |
|:--|:--|:--|
| 1 | GB28181 信令 **Go 自研**，不旁挂 WVP-Pro 进程 | 单一技术栈、单体部署、白名单可直查 `ac_device` |
| 2 | 功能范围 = **WVP-Pro 全量平替** | 含国标级联、JT/T 1078 车载、云端录像、录像计划、推拉流代理、分组/区域、移动位置 |
| 3 | 前端 **全部在 React 后台重建**（不复用 WVP 的 Vue2 UI） | 统一体验、统一鉴权与权限体系 |
| 4 | Pipecat 语音 Agent **本期落地 MVP** | 打通「设备音频 → STT → LLM → TTS → 回推对讲」 |
| 5 | 协议版本只承诺 **GB28181-2016** | 真机绝大多数是 2016；WVP 亦无 2022 专门处理 |

### 1.4 明确不在范围内

- **GB28181-2022 平替**：只对向后兼容的 2022 设备尽力而为，不作为验收项。
- **平台侧 AI 推理**：AI 识别仍在设备端，平台只做模型文件版本管理与结果接收（沿用 v0.1.0 边界）。
- **视频转码集群**：仅使用 ZLMediaKit 自带的 ffmpeg 能力，不自建转码调度。

## 2. 关键技术结论

本章六条结论**经代码核实**，是全部后续设计的依据。若其中任一条被推翻，架构需重新评审。

### 2.1 结论一：ZLM 独占 RTP 与 PS，Go 侧不碰媒体包 ★最重要

> ⚠️ **本结论的适用范围已在评审后收窄。** 原文写作「WVP 的 Java 代码里没有任何 socket」，经复核**不成立**：
> `DatagramSocket` / `MulticastSocket` 确为零命中，但 `ServerSocket` **非零** ——
> `jt1078/codec/netty/TcpServer.java:17,59` 是一个货真价实的 netty TCP 服务器
> （`ServerBootstrap` + `bind(port).sync()`，配 `DelimiterBasedFrameDecoder(0x7e)` + JT808 编解码）。
> 因此本结论**只适用于 GB28181 媒体路径**；**JT/T 1078（模块 J）恰好相反，需要 Go 侧自建 TCP 服务器**。

在 **GB28181 媒体路径**上，WVP 不接收 RTP —— 所谓「开 RTP 端口」实际是 REST 调用：

```
RtpServerServiceImpl.java:294-340  openCommonRTPServer()
  → mediaServerService.createRTPServer(...)
  → ZLMMediaNodeServerService.createRTPServer(...)
  → ZLMServerFactory
  → ZLM REST: /index/api/openRtpServer        ← 返回值只是一个端口号
```

连 TCP-ACTIVE（直觉上应「由我们主动连设备」）也是委托：

```
PlayServiceImpl.java:626-655  tcpActiveHandler()
  → mediaServerService.connectRtpServer(...)
  → ZLM REST: /index/api/connectRtpServer     ← ZLM 去拨号
```

`vmanager/ps/PsController.java` **不是** PS 解复用器，而是第三方 PS 服务对接 API。

**结论（限 GB28181 媒体路径）**：ZLM 直接接收裸 PS-over-RTP，内部解复用为 ES 轨（H.264/H.265/G.711A/AAC）。因此：

- ❌ **不写 Go PS 解复用器** —— 手写 PS 解复用是数周级的正确性泥潭
- ❌ **不写 Go RTP 接收路径**
- ✅ Go 侧只做 SSRC 分配、RTP server 生命周期编排、TCP-ACTIVE 分支转发

**收益**：省约 13 人天，且避开一个永久正确性债。**这是本项目最重要的架构不变量。**

### 2.2 结论二：流名是 SSRC 的十六进制

`RtpServerServiceImpl.java:76-155`：多端口模式（WVP 默认 `media.rtp.enable: true`）下：

```java
app    = "rtp"                              // MediaStreamUtil.RTP_APP
stream = String.format("%08x", ssrc).toUpperCase()
```

`{deviceId}_{channelId}` 形式**只是鉴权映射键**（`streamReplace`），仅单端口模式作为兜底流名。

**若按 `deviceId_channelId` 推导 `app/stream`，将导致 `on_publish` 鉴权、`getMediaList`、`closeRtpServer` 全部打空** —— 表现为「INVITE 成功但没有画面且无法收流」。

### 2.3 结论三：Redis 是净新增依赖

`backend/go.mod` 无 Redis 客户端；`config/config.go` 的 `RedisConfig` 注释为「预留：验证码、令牌黑名单、实时推送」，是**占位符，未接入任何业务**。

**须引入 `github.com/redis/go-redis/v9` 并新建 `pkg/redis`。** 所有「状态放 Redis」的设计都是净新增工作量，不是配置开关。

### 2.4 结论四：SIP 一期固定单节点、独立可执行

> ⚠️ **本条的论据在评审后被推翻，结论保留但理由重写。**
> 原文用「多副本会让 Digest nonce 缓存分裂 → 无限 401 循环」论证，**该论据不成立**：
> WVP 的服务端 Digest 是**完全无状态**的 —— `DigestServerAuthenticationHelper.generateNonce()`
> 只是「时间戳 + 随机数」做 MD5，不入库、不入缓存；`doAuthenticatePlainTextPassword()`
> 只用客户端回带的 nonce 重算摘要比对，**没有任何 nonce 存在性/过期校验**。
> 因此 pod A 发的挑战，pod B 完全能校验，「无限 401 循环」在 WVP 上不会发生。
> 而且 WVP 明确支持多信令节点（`service/redisMsg/` 下 24 个 `RedisRpc*` 类 + `wvp_device.server_id` 路由）。
>
> 「nonce 缓存 ~5s 过期」是 **`emiago/diago` 的 `DigestAuthServer.Expire`** 的特性（默认 5 秒），
> 不是 sipgo 的，也不是 GB28181 的 —— 见 §6.1 的选型更正。

**真正的理由**是这三条：

1. **TCP 连接与 SIP 事务/会话状态是节点本地的。** 设备用 TCP 注册后，后续 MESSAGE/INVITE 走同一条连接；
   跨节点无法复用（UDP 虽无连接，但 INVITE 会话状态仍在单进程内存里）。
2. **设备注册后绑定节点**：`wvp_device.server_id` + `host_address` + `expires`，
   后续所有下行指令必须路由回该节点。
3. **一期没有跨节点命令路由。** 要做就得引入 WVP 那套 `RedisRpc*`（24 个类），
   而一期只有**单向**需求（API 副本 → sipsvc 取播放地址、下发云台），不值得先建双向集群。

**结论**：`cmd/sipsvc` 独立进程，**一期**副本数固定 1，`hostNetwork` 或专用 LB 暴露 UDP/TCP 5060。
**这不是"必须"而是"一期选择"** —— 架构上预留多节点扩展（见 P 模块的「API → sipsvc 请求-响应通道」），
日后要扩容时，真正要解决的是上面第 1、2 条，而不是 nonce。

### 2.5 结论五：PTZ 走 MESSAGE，回放控制走 INFO

| 场景 | 载体 | 内容 |
|:--|:--|:--|
| 云台控制 | 带外 `MESSAGE` | MANSCDP `<Control><PTZCmd>…</PTZCmd><DeviceID>…</DeviceID></Control>` |
| 录像控制 | 带外 `MESSAGE` | MANSCDP `<Control>` 内的 `<RecordCmd>` |
| 回放暂停/恢复/拖动/倍速 | **带内 `INFO`** | MANSRTSP（`PLAY RTSP/1.0` / `PAUSE` / `Scale` / `Range`） |

**搞反是典型的一周级 bug** —— 表现为「按了没反应但也不报错」。

### 2.6 结论六：设备名是 GB2312

中文设备名/通道名以 **GB2312 字节**进入 XML body。WVP 的处理：注册时写默认值
`device.setCharset("GB2312")`（`RegisterRequestProcessor.java:206` 新建、`:216` 已有但为空时兜底 ——
**不是原文写的 :186，那行是"密码错误回 403"的日志**），解码在 `XmlUtil.java:202-217`
（`getRootElement` 硬编码 `"gb2312"`，带 charset 的重载在 null 时同样回落 `gb2312`，再 `reader.setEncoding()`）。**按设备可配。**

**Go 侧的失败模式要区分两种**（原文笼统说"产生乱码"是不准确的）：

| 报文情况 | Go `encoding/xml` 的行为 |
|:--|:--|
| 声明 `encoding="GB2312"` 且 `Decoder.CharsetReader == nil` | **直接返回错误** `xml: encoding "GB2312" declared but Decoder.CharsetReader is nil` —— 不是乱码 |
| 声明为 UTF-8、或无 XML 声明 | **静默乱码**，并落库污染数据 |

> 这个区别很实际：第一种在真机上很常见，表现为「**设备注册上来了，但目录一条都没有**」，
> 而不是「名字是乱码」。按「乱码」预期写兜底会漏掉这条路径。

**结论**：必须同时处理两条路径 —— 注入 `Decoder.CharsetReader`（按设备的 `charset` 列做
`simplifiedchinese.GB18030` 转码）**并且**在转码失败时显式记日志、拒绝该报文，不要静默吞掉。
这是 **XML body 层的职责，不是 SIP 栈的事**。

### 3.2 进程拓扑

| 进程 | 职责 | 副本 | 扩缩容 |
|:--|:--|:--:|:--|
| `cmd/server` | HTTP API（现有 + 新增国标管理接口） | 3–5 | HPA |
| `cmd/sipsvc` | SIP 信令 + 媒体编排 | **1** | 不可水平扩展 |
| ZLMediaKit | 媒体收流/解复用/转协议/录像 | 1+ | 可多节点（`ac_gb_media_server` 管理） |
| Pipecat | 语音 Agent 管线 | 1+ | 可按并发扩展 |

**仍是单体**：同一 Go module、同一套 `internal/model|repository|service`、同一数据库、同一份 Casbin 配置。不引入 RPC、不引入消息队列 —— 与 `docs/敏捷开发/v0.1.0 基础功能开发/v0.1.0-与参考项目差距分析（后端）.md:54`「ai-camera 是单体，没有外部服务要对接」的定位一致。

**命名说明**：第二个可执行文件命名为 `cmd/sipsvc` 而非 `cmd/media` —— 媒体在 ZLM 里，叫 `media` 会误导后续维护者。

**Go 侧不需要 RTP 端口段**（结论一）：`openRtpServer(port=0)` 让 ZLM 从自身配置的 `rtp.port-range` 里选取。

**开发期便利**：`gb28181.embedded: true` 时 `cmd/server` 内嵌启动同一组 goroutine，一条命令完成端到端联调。

### 3.3 配置新增

`config/config.go` 新增三组（`Config` 结构体追加字段）：

```go
type GB28181Config struct {
    Enabled        bool     // 总开关
    Embedded       bool     // 是否内嵌到 cmd/server（开发期 / 单容器部署）
    SIPIP          string   // 监听地址（多网卡关键）
    SIPPort        int      // 5060
    SIPDomain      string   // 十位域，如 3402000000
    SIPID          string   // 20 位平台国标 ID
    Transport      []string // ["udp","tcp"]
    RegisterExpire int      // 注册有效期（秒）
    HeartbeatCount int      // 心跳超时倍数
    SIPNATSIP      string   // 对外通告的 SDP IP（NAT 场景）
}

type MediaServerConfig struct {
    ID         string // mediaServerId
    IP         string // ZLM API 地址
    HTTPPort   int
    Secret     string // ZLM API 密钥（敏感）
    HookIP     string // ZLM 回调本服务的地址
    SDPIP      string // SDP 中通告的 IP
    StreamIP   string // 流地址对外 IP
    RTPPortRange string // 30000-30500
}

type VoiceAgentConfig struct {
    Endpoint string // Pipecat 控制面地址
    Token    string // 共享 token（敏感）

}
```

**配置来源**：YAML 为基线，**支持环境变量覆盖**（`config.go` 的 `envBindings`）。这是容器化部署不把密钥写进镜像的前提。已支持 `DATABASE_*`、`REDIS_*`、`JWT_SECRET`、`SERVER_PORT` 等，v0.2.0 需补 `GB28181_*`、`ZLM_*`、`PIPECAT_*`。

### 3.4 部署形态（开源版：Docker Compose）

开源版本以 **Docker Compose 一键部署**为交付形态，仓库根 `docker-compose.yml` 已落地。

| 服务 | profile | 副本 | 说明 |
|:--|:--|:--:|:--|
| `postgres` | 无（始终启动） | 1 | PostgreSQL 16 + **PostGIS** + **pgvector** |
| `redis` | 无（始终启动） | 1 | 注册表与跨节点状态 |
| `backend` | `full` | 1–N | `cmd/server`，HTTP API |
| `frontend` | `full` | 1–N | nginx 托管管理后台 + 官网，并反代 `/web` `/app` |
| `zlm` | `gb28181` | 1+ | ZLMediaKit |
| `sipsvc` | `gb28181` | **1（固定）** | GB28181 信令 |
| `pipecat` | `voice` | 1+ | 语音 Agent |

**两种用法**（不加 `--profile` 即只起基础设施，供本地开发）：

```bash
# 本地开发：只起 postgres + redis，应用在宿主机跑
cp .env.example .env && docker compose up -d
cd backend && go run ./cmd/server/main.go

# 完整部署
docker compose --profile full up -d --build
```

**`sipsvc` 与 `backend` 的关系**：同属一个 Go module、**同一个镜像**，只是两个入口 ——
`backend/Dockerfile` 一次构建产出 `/app/ai-camera-api` 与 `/app/ai-camera-sipsvc`，compose 用 `command` 区分：

```yaml
backend: { image: ai-camera-backend:latest, command: ["/app/ai-camera-api"] }
sipsvc:  { image: ai-camera-backend:latest, command: ["/app/ai-camera-sipsvc"] }
```

**为什么分成两个服务**：扩缩容诉求相反 —— `backend` 希望水平扩展，`sipsvc` 必须固定单副本（§2.4）。
若接受后端整体单副本，可改用 `gb28181.embedded: true`，SIP 随 API 进程一起启动，**一个容器即可**。

**本地数据库**：`deploy/postgres/` 的镜像在 PostgreSQL 16 上装了 PostGIS 与 pgvector ——
没有一个官方镜像同时提供两者（`postgis/postgis` 无 pgvector，`pgvector/pgvector` 无 PostGIS），
故以 postgis 为基底从 PGDG 源补装。两个库 `ai_camera_dev` / `ai_camera_test` 首次启动时自动创建。

## 4. 设备接入与白名单（需求核心）

需求 1「设备注册、激活」与需求 2「SIP 设备必须是设备管理里有的设备」是同一问题的两面，用一条主线解决：

> **`ac_device` 是唯一的设备权威数据源。** 管理员建档时平台生成 20 位国标 ID 与 SIP 密码；设备用这组凭证首次 REGISTER 成功即为「激活」。信令层收到 REGISTER 时直查 `ac_device`：**查不到即回 403 Forbidden**。

### 4.1 数据模型变更

**`ac_device` 追加 13 列**：

| 列名 | 类型 | 说明 |
|:--|:--|:--|
| `gb_device_id` | VARCHAR(20) **UNIQUE** | 20 位国标编码，SIP `From` 头携带的即是它 |
| `sip_password` | VARCHAR(100) | 每设备独立 Digest 密码（敏感，API 返回时脱敏） |
| `sip_realm` | VARCHAR(50) | 鉴权域，默认取 `gb28181.sip_domain` |
| `sip_transport` | VARCHAR(10) | `UDP` / `TCP` |
| `stream_mode` | VARCHAR(20) | `UDP` / `TCP-PASSIVE` / `TCP-ACTIVE` |
| `charset` | VARCHAR(20) | `GB2312` / `UTF-8`（结论六） |
| `register_status` | VARCHAR(20) | `pending` / `activated` / `rejected` |
| `register_dt` | TIMESTAMPTZ | 首次注册成功时间 |
| `sip_expires` | TIMESTAMPTZ | 注册过期时间 |
| `media_server_id` | VARCHAR(50) | 绑定媒体节点，`auto` 为自动选择 |
| `channel_count` | BIGINT | 通道数（冗余，列表展示用） |
| `local_ip` | VARCHAR(50) | 设备级源 IP 覆盖（多网卡场景） |
| `sdp_ip` | VARCHAR(50) | 设备级 SDP IP 覆盖（NAT 场景） |

> ⚠️ **ID 空间必须分开**。现有 `device_code`（`size:100`，唯一索引）是业务编号（如 `CAM_001`），被 `POST /web/devices/:id/heartbeat` 使用；国标 20 位编码是**另一个命名空间**。**不得复用 `device_code`**。
>
> `device_code` 含非数字字符的设备，其 `gb_device_id` 为空 → SIP 层一律 403。

**新增 `ac_gb_channel`（国标通道）**：GB28181 是「1 设备 + N 通道」，且**云台与点播都作用在通道上**，现有模型完全没有这个概念。字段见 §5 与 DDL 脚本。

### 4.2 注册与激活状态机

```
                    ┌──────────────────────────────────────┐
                    │ 管理员在「设备管理」新增设备           │
                    │  → 平台生成 gb_device_id + sip_password│
                    │  → register_status = 'pending'        │
                    └──────────────────┬───────────────────┘
                                       │ 凭证经二维码/配置文件下发现场
                                       ▼
                    ┌──────────────────────────────────────┐
                    │ 设备上电，发 SIP REGISTER             │
                    └──────────────────┬───────────────────┘
                                       │
                        ┌──────────────┴──────────────┐
                        │ 查 ac_device.gb_device_id    │
                        └──────┬────────────────┬──────┘
                       命中    │                │  未命中
                               ▼                ▼
              ┌────────────────────────┐  ┌─────────────────────────┐
              │ Digest 鉴权（401→重发） │  │ 403 Forbidden           │
              └───────┬────────┬───────┘  │ + 写 ac_gb_sip_log      │
              通过    │        │ 失败     │ （★ 需求 2 的落点）      │
                      ▼        ▼          └─────────────────────────┘
        ┌──────────────────┐  ┌──────────────────┐
        │ 200 OK           │  │ 403 Forbidden    │
        │ register_status  │  │ 记 rejected      │
        │   → 'activated'  │  └──────────────────┘
        │ register_dt = now│
        │ status → online  │
        └────────┬─────────┘
                 │ Keepalive 周期心跳续期
                 ▼
   ┌────────────────────────────────────────────────┐
   │ 心跳超时（heart_beat_interval × count）        │
   │ 或 sip_expires 到期未续注册                     │
   │  → status = 'offline'，写 ac_device_history    │
   └────────────────────────────────────────────────┘
```

### 4.3 白名单校验时序

```
设备                     cmd/sipsvc                      PostgreSQL
 │                            │                              │
 │── REGISTER (无凭证) ──────▶ │                              │
 │                            │── SELECT ... FROM ac_device ─▶│
 │                            │   WHERE gb_device_id=?        │
 │                            │◀── 命中 / 未命中 ─────────────│
 │                            │                              │
 │   [未命中] ◀── 403 Forbidden │  + INSERT ac_gb_sip_log     │
 │                            │                              │
 │   [命中]   ◀── 401 + WWW-Authenticate: Digest (nonce)      │
 │                            │                              │
 │── REGISTER (含 Digest) ───▶ │                              │
 │                            │  校验 MD5 摘要                │
 │                            │  + 写 registry（Redis）       │
 │                            │  + UPDATE ac_device           │
 │                            │    SET register_status='activated' │
 │   ◀────── 200 OK ───────── │    , status='online'         │
 │                            │                              │
```

**与 WVP 的差异**：WVP 靠「清空全局 `sip.password`」达成同一效果。本项目**做成显式查库**，不设公共密码开关 —— 语义更清晰，且天然满足多租户/数据权限。

### 4.4 MESSAGE / SUBSCRIBE 的入向校验（评审补充 —— 原文档缺失，存在绕过）

> ⚠️ 原文只定义了 REGISTER 的白名单，**MESSAGE 侧一条校验都没有**。这是需求 2 的一个真实绕过：
> 任何能到达 5060 的主机，只要冒用已注册设备的 `From: <sip:34020000001320000001@…>`，
> 就能维持心跳、**注入伪造目录（污染 `ac_gb_channel`）**、伪造报警。
> 而 MESSAGE 里的 Catalog 是**会创建数据**的，不是只读操作。

对照 WVP 的做法（`MessageRequestProcessor.java:82-97`），入向 MESSAGE 必须过三道：

| # | 校验 | 不通过的处理 |
|:--|:--|:--|
| 1 | `From` 的用户部分必须存在于 `ac_device.gb_device_id` 或 `ac_gb_platform.server_gb_id` | 回 404 `device xxx not found` |
| 2 | **报文源 IP:Port 必须等于该设备注册时绑定的地址**（WVP 用 `device.getHostAddress()` 比对） | 丢弃 + 记 `ac_gb_sip_log`（`result='rejected'`） |
| 3 | Catalog 中每个 `<DeviceID>` 必须落在该设备的**域前缀内** | 跳过该条目并记日志，不整体拒绝 |

第 2 条是消歧的关键：设备与上级平台可能用同一个 `deviceId` 语义空间，
WVP 正是靠源地址在两者间切换（`if (device.getHostAddress().equals(hostAddress+":"+remotePort)) parentPlatform = null; else device = null;`）。

**必做测试**：模拟器加 `--spoof-message` 场景（冒用已注册设备 ID 发目录），断言平台拒绝且未产生 `ac_gb_channel` 脏数据。见 §13.3.2。

**复用已有的 `ac_region`，不引入 `wvp_common_region`。** `ac_gb_channel.region_id` 指向 `ac_region`，避免出现两套并行的区域体系。`ac_gb_group`（业务分组树）是国标特有概念，无对应现有表，需新建。

### 5.2 权限数据

每个新页面与按钮需同步补三张表的数据（见 `CLAUDE.md`「按钮权限码规范」）：
`ac_menu`（`type='menu'` 页面行 + `type='button'` 按钮行，权限码形如 `gb:device:list`、`gb:channel:ptz`）、
`ac_menu_api`（菜单绑定的接口，Casbin `p` 策略的唯一来源）、`ac_role_menu_rel`（授权角色）。

**权限码必须真实存在于 `ac_menu` 且已授权**，否则前端的 `permCodes.includes()` 会对超管也静默失效。

## 6. GB28181 信令层设计

### 6.1 SIP 栈选型

> ⚠️ **本节经评审更正。原文声称「sipgo 内置服务端 Digest 原语（`NewDigestServer` / `AuthorizeRequest`）」——
> 这是把 `emiago/diago` 的能力记到了 `sipgo` 头上。**
>
> 实测（`go get` 拉取后 `go doc` 核对）：
> - `sipgo v1.6.0` 的 `DigestAuth` **只是一个 `struct { Username, Password string }`，无任何方法**；
>   `NewDigestServer` / `AuthorizeRequest` / `AuthorizeDialog` / `DigestAuthServer` 在 sipgo 中**均不存在**。
> - 这些 API 全部属于 `github.com/emiago/diago`：`type DigestAuthServer` + `func NewDigestServer() *DigestAuthServer`
>   + `AuthorizeRequest` / `AuthorizeDialog` / `Close`。
> - diago 的 `DigestAuthServer.Expire` **默认 `5 * time.Second`**（源码 `digest_auth.go:29`）——
>   这正是原文 §6.2 #4 与 R11 所写的「sipgo 的 nonce 缓存 ~5s」，进一步印证了来源搞混。
>
> 另一个旁证：diago 拉入了 `gopkg.in/hraban/opus.v2` 等音频编解码依赖，是**完整 VoIP 框架**
> （含 RTP/RTCP/packetizer/DTMF），与原文否决 gosip 的理由（「完整框架会对抗」）属同一类。

**选 `github.com/emiago/sipgo`**（+ `sipgo/sip`），**服务端 Digest 自研**。

| 候选 | 评估 |
|:--|:--|
| **`emiago/sipgo`** ✅ | 轻量 SIP 事务/会话层：`NewServer`/`NewClient`/`NewDialogServer`/`NewDialogClient`/`DialogServerCache` 均实测存在。**服务端 Digest 需自研**（见 §6.2）。维护活跃 |
| `emiago/diago` | 提供现成的 `DigestAuthServer`，但它是**完整 VoIP 框架**（RTP/RTCP/packetizer/DTMF/opus），会与 GB28181 非标准的 INVITE/INFO/BYE 模式对抗；且 License 为 **MPL-2.0**（sipgo 是 BSD-2）。**不选，但作为服务端 Digest 的实现参考** |
| `ghettovoice/gosip` | 自带 UA/事务框架；其 `sip/auth.go` 似含 `AuthorizeRequest`/`Authorizer` 接口，**是否为库能力未能确证**（网络受限），故不作为否决理由；维护节奏仍是扣分项 |
| 裸 UDP + 自研解析 | 需自行实现 RFC 3261 事务层（Timer A/B/E/F/K、Via branch 匹配），**3–5 周纯风险、零产品价值**。否决 |
| Fork JAIN-SIP 语义 | 交付路径无 Maven、JVM 非本栈。否决 |

**自研服务端 Digest 的规模**：GB28181 只需 RFC 2617 MD5（含 `qop=auth` 的 nc/cnonce 校验），
约 150–250 行 —— 远低于「引入一个完整 VoIP 框架」的代价。建议**直接参考 diago 的
`digest_auth.go` 实现**（读懂后自行实现，不引依赖），并把 nonce 做成**无状态**
（`HMAC(secret, deviceId|epoch)`）或干脆随机 —— 对齐 WVP 的做法，免去缓存与单节点约束。

### 6.2 sipgo 不提供、必须自建的四项

| # | 缺口 | 说明 | 优先级 |
|:--|:--|:--|:--:|
| **1** | **多网卡源 IP 选择** | WVP 按设备绑定本地 IP 发送（`SipLayer.getLocalIp`）。需每个本地 IP 一个 listener + 「从哪个 IP 收到就从哪个 IP 回」的路由规则 | **一期最大未知数，先做 spike** |
| 2 | RFC 3581 `rport`/`received` 重写 | WVP 手写实现（`gb28181/utils/SipUtils.java:176-205`）。需决定设备权威地址取 Via 还是报文源地址 | 高 |
| 3 | UDP MESSAGE 分片与目录重组 | 目录响应按 `SumNum` 跨多条 MESSAGE，需按 `(deviceId, SN)` 重组 + 超时；出向 MESSAGE 需保持小包 | 高 |
| 4 | nonce 策略 | **原文此处写错**：那不是 sipgo 的特性，而是 `emiago/diago` 的 `DigestAuthServer.Expire`（默认 5s）。既然服务端 Digest 自研（见下条），nonce 建议做成**无状态**（随机或 `HMAC(secret, deviceId\|epoch)`），对齐 WVP 的无状态实现，天然免去缓存与单节点约束 | 中 |
| **5** | **服务端 Digest 鉴权**（评审新增，原文漏列） | sipgo 的 `DigestAuth` 只是 `{Username, Password}` 空结构体，**无服务端能力**。401 挑战生成 + RFC 2617 MD5 摘要校验（含 `qop=auth` 的 nc/cnonce）**必须自研**，约 150–250 行；参考 diago 的 `digest_auth.go`（读懂后自行实现，不引依赖） | **高** |

**GB2312 转码**（结论六）在 XML body 层用 `golang.org/x/text/encoding/simplifiedchinese` 处理，与 SIP 栈解耦。

### 6.3 MANSCDP 报文清单

约 **25 种**（对照 `transmit/event/request/impl/message/{query,response,notify,control}/cmd/`；WVP 的 `XmlUtil.java` 730 行）：

| 方向 | 报文 |
|:--|:--|
| **接收**（设备→平台） | Keepalive、Catalog（响应）、DeviceInfo（响应）、DeviceStatus（响应）、Alarm（主动）、MobilePosition（主动）、RecordInfo（响应）、ConfigDownload（响应）、PresetQuery（响应）、MediaStatus（主动） |
| **发送**（平台→设备） | Catalog（查询）、DeviceInfo（查询）、DeviceStatus（查询）、DeviceControl（PTZ/录像/报警复位/重启/校时）、RecordInfo（查询）、ConfigDownload（查询）、PresetQuery（查询）、Subscribe/Notify（目录、报警、位置订阅） |

**订阅机制**：`SUBSCRIBE`/`NOTIFY`（RFC 3265）用于目录变更、报警、移动位置的持续推送，是「移动位置」「国标报警」两条业务线的数据来源。订阅状态落 `ac_gb_subscribe`。

### 6.4 SSRC 分配

平台侧分配，经 SDP `y=` 字段通告：

```
SSRC = "0" + domainPart + %04d(index)
         │     │             │
         │     │             └─ 10,000 位 BitSet 中的槽位（线性探测）
         │     └─ sipDomain[3:8]，5 位
         └─ 0 = 实时点播，1 = 回放
```

**进程内单写者，不放 Redis** —— SSRC 分配是单写者问题，分布式只会引入竞态。分配结果**发布**到 Redis 供 API 副本读取。

BitSet 的重建**不是只在启动时做一次**：WVP 是**每 5 秒周期重建**（`SSRCFactory.java:53`
`scheduler.scheduleAtFixedRate(this::rebuild, 5, 5, TimeUnit.SECONDS)`），
以免多实例或重启后 SSRC 冲突窗口被拉长。注意 `rebuild` 与 `allocate` 的锁竞争
（WVP 为每个媒体节点一把锁 `lockMap`），Go 侧需等价加锁。

`userSetting.ssrcRandom` 开启时退化为「前缀 + 4 位随机数」，不做簿记。

```
  │                  │                 │◀──── 200 OK (设备自己的 SDP) ─────│
  │                  │      ⑤ ACK      │               │                 │
  │                  │      ⑥ SSRC 协商：设备 y= 与平台不同且 ssrc_check 开启
  │                  │         → updateRtpServerSSRC(app,stream,newSsrc)
  │                  │                 │──────────────▶│                 │
  │                  │                 │               │◀══ RTP/PS 推流 ══│
  │                  │                 │               │                 │
  │                  │                 │◀─ on_publish（鉴权失败 → 拒绝）
  │                  │                 │◀─ on_stream_changed
  │                  │                 │◀─ on_media_arrival（★ WVP **内部**事件，非 ZLM 回调）
  │                  │                 │               │                 │
  │◀─ 返回 {webrtc, flv, app, stream} ─│               │                 │
  │─ WebRTC/WHEP 播放 ────────────────────────────────▶│                 │
```

**停止**：BYE（平台发起）→ ZLM `closeRtpServer` + `closeStreams` → 清 Redis 注册项。

### 7.2 传输模式（「能注册但黑屏」的主要来源）

| 模式 | 谁连谁 | SDP 标志 | ZLM `tcp_mode` | 说明 |
|:--|:--|:--|:--:|:--|
| **UDP** | 设备 → `sdpIp:rtpPort` | `m=video {port} RTP/AVP 96 98 97 99` | `0` | 默认推荐 |
| **TCP-PASSIVE** | **设备主动连** ZLM | `m=video {port} TCP/RTP/AVP …` + `a=setup:passive` + `a=connection:new` | `1` | WVP 默认（NAT 友好） |
| **TCP-ACTIVE** | **ZLM 主动连设备** | 平台从设备 200 OK 的 SDP 读 `c=`/`m=` | `2` | 走 `connectRtpServer` |

⚠️ 真机兼容性差异大：部分设备忽略 `a=setup:passive` 仍主动连；有的发 `$` 分帧 RTP、有的发裸 RTP；有的连上就挂起。**模拟器必须同时覆盖分帧与不分帧两种变体**，并保留按设备「强制 UDP」的逃生开关。

### 7.3 流命名与鉴权

- `app` 恒为 `rtp`，`stream` 为 `%08X(ssrc)`（结论二）
- `{deviceId}_{channelId}` → `(app, stream, callId)` 的映射存 Redis，供 `on_publish` / `on_play` 鉴权查表
- **`on_publish` 鉴权失败必须返回「失败语义」**。ZLM 两种都支持：HTTP 非 200，**或** HTTP 200 + JSON `{"code": -1}`。

> ⚠️ **更正**：原文写「必须返回 401（而非 200）」。实测 WVP 用的是后者 ——
> `ZLMHttpHookListener.java:103-130` 返回 `HookResultForOnPublish.Fail()`（HTTP 状态码仍是 200，JSON `code != 0`）。
> 两种都能真正阻断，但「（而非 200）」的措辞会让人误以为 WVP 是用 HTTP 200 放行，联调时会踩坑。

**ZLM 真实回调端点共 10 个**（`ZLMHttpHookListener.java`，**其中没有 `on_media_arrival`**）：
`on_server_keepalive`、`on_server_started`、`on_publish`、`on_play`、`on_stream_changed`、
`on_stream_none_reader`、`on_stream_not_found`、`on_send_rtp_stopped`、`on_rtp_server_timeout`、`on_record_mp4`。

> `on_media_arrival` 是 **WVP 的内部 Hook 类型**（`RtpServerServiceImpl.openCommonRTPServer` 里
> `Hook.getInstance(HookType.on_media_arrival, ...)`，由 `on_stream_changed`/`on_publish` 派生的
> `MediaArrivalEvent` 触发），**不是 ZLM 回调**。在 ZLM 的 hook 配置里配不出来 —— 别去找它。

### 7.4 播放协议选型

| 协议 | 延迟 | 用途 | 前端库 |
|:--|:--|:--|:--|
| **WebRTC / WHEP** | 200–500ms | **主**：选中窗格、云台操作、语音对讲 | 原生 `RTCPeerConnection`（ZLM `/index/api/webrtc?app=rtp&stream={hexSsrc}&type=play`） |
| HTTP-FLV | 1–3s | **兜底**：视频墙铺格子 | `mpegts.js`（`flv.js` 已停止维护） |

## 8. 语音 Agent 设计（Pipecat）

### 8.1 链路

```
会话启动 → internal/gb28181/play 对设备发 Talk/Broadcast INVITE
  → ZLM 收设备音频（PCMA/G.711A）
  → Pipecat 从 ZLM 拉音频 → VAD → STT → LLM → TTS
  → 输出 PCM 编 G.711A
  → ZLM startSendRtp 回推设备喇叭
```

**已知延迟构成**：设备→ZLM 收流 → Pipecat 拉流 → VAD 判停（通常 300–700ms）→ STT → LLM 首 token → TTS 首包 → 编码回推 → ZLM 发包。PCMA↔PCM 转换与可能的 ffmpeg 转码都要计入回路预算。**这是「对讲感觉迟钝」的主要来源，需在选择 VAD 判停阈值时权衡。**

### 8.2 动态 STT/LLM/TTS 配置

**结论：可以动态配置，且本项目已有现成承载结构。**

`ac_thirdparty_config`（`internal/model/notify.go:63-79`）本就是「键值 + `Secret` 脱敏标记 + `Category` 分类」的配置表，注释写明设计意图是「以键值形式存储，避免为每组固定配置各建一张窄表」。`internal/service/setting/setting_service.go` 已有全套原语（行号经评审更正）：

| 已有函数 | 位置 | 作用 |
|:--|:--|:--|
| `loadThirdParty(ctx, category)` | `:282` | 读出 `键→值` 与 `键→是否敏感` 两个映射 |
| `saveThirdParty(ctx, category, items)` | `:297` | 逐键 upsert；**空值与脱敏串跳过**，不会用 `****` 覆盖真密钥 |
| `maskIfSecret(code, value, rowSecret)` | `:311` | 敏感键返回脱敏串 |
| `repo.UpsertThirdPartyConfig(...)` | `setting_repo.go:182` | 底层 upsert |

**因此只加一个新 `Category = 'voice_agent'`，零新表、零新 CRUD 框架**，密钥「只写不读」直接复用。

#### 动态性的三个层次

| 层次 | 能力 | 本期 |
|:--|:--|:--:|
| **1. 配置动态** | 后台改 provider/模型/音色/系统提示词 → 存库 → 下发 Pipecat → **下一个会话生效**，不重启任何服务 | ✅ |
| **2. 会话热重建** | 进行中会话不中途换 provider（换 TTS 会断音），但可 `/session/stop` + `/session/start` 秒级重建 Pipeline | ✅ |
| **3. 免改代码加 provider** | provider 清单存 `ac_voice_provider` 字典表，前端下拉与**动态表单由 `param_schema` 渲染**；Pipecat 侧 `factory.py` 加一个映射项即可 | ✅ |

#### 配置键（`Category = 'voice_agent'`）

```
stt_provider / stt_model / stt_endpoint / stt_api_key(secret) / stt_language
llm_provider / llm_model / llm_endpoint / llm_api_key(secret) / llm_system_prompt
llm_temperature / llm_max_tokens
tts_provider / tts_voice / tts_endpoint / tts_api_key(secret) / tts_speed
vad_provider / vad_params
barge_in / session_idle_timeout / max_session_sec
```

#### 接口

```
GET  /web/settings/voice-agent            读配置（敏感键脱敏）
PUT  /web/settings/voice-agent            存配置
GET  /web/settings/voice-agent/providers  读 provider 字典（驱动前端动态表单）
POST /web/settings/voice-agent/test       provider 连通性测试
POST /web/settings/voice-agent/apply      推给 Pipecat 控制面并使其生效
```

#### Pipecat 侧控制面

Pipecat 是**库**不是服务，需在 Docker 内包一层薄控制面：

```
deploy/pipecat/
├── main.py         FastAPI：/health /config /session/start /session/stop /test
├── factory.py      provider 字符串 → Service 类的映射表
├── pipeline.py     VAD → STT → LLM → TTS 装配
├── transport.py    ZLM 音频接入（PCMA → PCM）与回推
└── requirements.txt
```

`param_schema` / `extra_params` 透传为各 Service 的构造 kwargs —— 这是「不改后端代码改配置」的落点。

#### 默认配置（零外部密钥）

`stt_provider=local_whisper`（faster-whisper 本地）、`llm_provider=anthropic`（`claude-sonnet-5-5`）、`tts_provider=edge_tts`（本地免费）。云端 provider 由后台切换。

#### 安全

- 密钥只写不读：复用 `maskIfSecret` + `saveThirdParty` 的脱敏串跳过逻辑
- Pipecat 控制面**只在 docker 内网暴露**，与 backend 之间用共享 token 校验
- `POST /test` 需 `voice:agent:test` 权限码，防止低权用户探测密钥有效性

**存量设备如何处理**（现有 `CAM_001` 等设备的 `gb_device_id` 为空）：

- 若某设备的 `device_code` 本身已是数字且客户希望直接复用为国标 ID，提供一次性导入脚本（显式操作），不做隐式转换。

## 12. 模拟器设计（`tools/gbsim`）

既是需求交付物，也是全项目的 E2E 夹具与回归门禁。

### 12.1 能力

| 能力 | 说明 |
|:--|:--|
| SIP UA | REGISTER（收到 401 后带 Digest 重发）、`Expires` 处理、周期 Keepalive |
| MANSCDP | 目录响应（**按 `SumNum` 分片**）、设备信息、设备状态、录像查询；**GB2312 编码** |
| 媒体 | 对 INVITE 回格式正确的 SDP（含 `y=`、`c=`、`m=`）；**PS 打包器**（Annex-B NAL + PTS → PES/PS，约 300 行） |
| 传输 | **UDP / TCP-PASSIVE / TCP-ACTIVE 三模**；TCP 模式主动连出并做 `$` 分帧 |
| 控制 | 应答 PTZ、快照、录像控制；回放应答 MANSRTSP |
| 异常注入 | **可故意回一个不同的 `y=`** 以覆盖 SSRC 校正路径 |
| AI 联动 | 定时/触发调用 `POST /web/risks/report`（X-Api-Key）上报风险并上传图片 |

### 12.2 CLI

```bash
go run ./tools/gbsim \
  --device-id 34020000001320000001 \
  --sip-server 127.0.0.1:5060 \
  --sip-domain 3402000000 \
  --password '<设备 SIP 密码>' \
  --channels 2 \
  --mode tcp-passive \
  --stream-file testdata/sample.h264 \
  --risk-interval 30s
```

### 12.3 关键前置依赖

⚠️ **本机无 ffmpeg**，需在仓库内置一个 H.264 Annex-B 样本（`tools/gbsim/testdata/sample.h264`，约 200KB，在有 ffmpeg 的机器上生成一次后提交）。**PS 打包器是无法回避的真实工作量。**

### 12.4 先做模拟器的战略价值

`d:\work2026\wvp-GB28181-pro` 自带 `docker/` compose（WVP + MySQL/Redis + ZLM），可独立运行。因此：

> **自研 SIP 服务一行代码都没写时，就能先把模拟器搭出来，对着一个已知正确的平台接线。** 模拟器一旦在 WVP-Pro 上跑通，它就成了一把可信的尺子 —— 后面自研 SIP 服务对着它调，错误只可能在我们这边，调试空间立刻收敛一半。

这同时降低「工作量低估」「无真机可测」「无本地工具链」三条风险。

### 13.2 后端单元与协议测试

- **执行约定**：`testutil.WithTx` 提供事务级隔离；**必须 `-p 1` 串行** —— 所有包共用同一个物理库
  `ai_camera_test`，不加时 A 包的数量断言会被 B 包的并发写入干扰（v0.1.0 实测 `tests/upgrade` 随机失败）。
- **协议往返测试**：MANSCDP / SDP / MANSRTSP / GBCode 各自「编码 → 解码 → 比对」。
  **必须包含一条真实 GB2312 中文通道名的样本** —— 这是结论六最容易静默出错的地方。
- **字段验证**：所有后端单测必须验证绝大多数字段的更新（沿用项目既有要求），防止字段保存失效。
- **白名单专项**：用**未建档**的国标 ID 起 gbsim，断言收到 SIP **403** 且 `ac_gb_sip_log` 有拒绝记录。**这是需求 2 的验收点。**

### 13.3 模拟设备集中调试（本项目的调试主线）

`gbsim` 不止是「一个假设备」，而是一套**可控、可复现、可批量的调试台**。GB28181 问题的难点几乎全在
「真机行为不可控、现场无法复现」，调试台的价值就在于把它变成可控变量。

#### 13.3.1 多设备并发

单个 `gbsim` 进程支持由一份清单描述 N 台相机，而非只模拟一台：

```yaml
# tools/gbsim/scenarios/mixed-10.yaml
devices:
  - gb_id: "34020000001320000001"  name: "东门球机"    channels: 1
    mode: tcp-passive  codec: h264  charset: GB2312
  - gb_id: "34020000001320000002"  name: "仓库枪机"    channels: 4
    mode: udp          codec: h265  charset: UTF-8
  # ... 可扩展到数十台，用于容量与并发验证
```

用途：批量注册、目录并发同步、媒体节点负载选择、`ac_device.channel_count` 汇总正确性、
「几十路同时点播」时 ZLM 与 SSRC 池的表现。

#### 13.3.2 场景注入（把现场故障变成可复现用例）

| 场景 | 注入方式 | 预期平台行为 |
|:--|:--|:--|
| 未建档设备 | 用不在 `ac_device` 的国标 ID | **403**，`ac_gb_sip_log` 记录拒绝 |
| 密码错误 | `--password` 传错值 | 401 挑战 → 带错凭证 → **403** |
| 中文名乱码 | `charset: GB2312` + 中文通道名 | 落库为正确中文，非乱码（结论六） |
| H.265 码流 | `codec: h265` | WebRTC 路径降级到 FLV/HLS，不静默黑屏（R7） |
| SSRC 不符 | `--force-ssrc-mismatch` | 平台经 `updateRtpServerSSRC` 校正后仍出流 |
| 裸 RTP（不分帧） | `--tcp-unframed` | TCP-PASSIVE 下仍可收流（R2） |
| 注册后立即断连 | `--die-after-register 3s` | 心跳超时后置 `offline`，写 `ac_device_history` |
| 心跳停发 | `--stop-keepalive-after 60s` | `sip_expires` 到期置 `offline` |
| 大目录 | `--channels 200` | 跨多条 MESSAGE 的 `SumNum` 分片被正确重组（R9） |
| ABNF 畸形报文 | `--malformed <kind>` | 平台不 panic，记日志并拒绝（**验证 R1 的隔离性**） |

#### 13.3.3 日志关联：一次调试怎么把链路串起来

三方日志按**两个关联键**对齐，是排障的核心手法：

| 日志源 | 位置 | 关联键 |
|:--|:--|:--|
| SIP 报文 | `ac_gb_sip_log`（含 `content` 全文） | **Call-ID** |
| ZLM 回调 | `internal/gb28181/hook` 的日志 | **app + stream（即 SSRC 十六进制）** |
| 应用链路 | `cmd/server` / `cmd/sipsvc` 常规日志 | 请求 ID / 设备国标 ID |

排障配方（以「点播黑屏」为例）：
1. 由设备国标 ID 查 `ac_gb_sip_log`，确认 INVITE 出去了、设备回了 200 OK；
2. 取 INVITE 的 `y=` 得到 SSRC，换算成 `%08X` 查 ZLM `getMediaList` —— 流是否存在；
3. 流不存在 → 看 `openRtpServer` 是否成功、设备侧是否真的在推（gbsim 会打印发送字节数）；
4. 流存在但浏览器黑屏 → 查 `on_publish` 是否被鉴权拦掉（**必须返 401 才会阻断**）、编码是否 H.265。

#### 13.3.4 调试台交付物

- `tools/gbsim/scenarios/*.yaml` —— 上述场景的清单文件，纳入版本库，可复现
- `scripts/debug-stack.sh` —— 一键起 `postgres + redis + zlm + sipsvc + backend + gbsim`，
  并打印各服务的日志文件路径与关联键查法
- `gbsim` 交互模式（`--interactive`）—— 手工触发注册/断连/上报报警，配合 Web 端点击云台时**观察设备侧收到什么**

### 13.5 App 端到端测试（Patrol）

**现状**：App 无任何 E2E 框架（v0.1.0 差距文档的 F11）。基线是好的 ——
`flutter analyze` 零问题、`app/android` 与 `app/ios` 工程完整（§9.1），因此可直接搭。

**选型 Patrol**：Flutter 生态里唯一能同时驱动 Flutter 层与**原生层**（权限弹窗、系统对话框）的框架。
本项目必须用到原生层能力 —— 语音对讲会弹麦克风权限、播放要处理系统级中断。

**覆盖场景**：

| 用例 | 备注 |
|:--|:--|
| 登录 → 设备列表 → 在线状态 | 基础链路 |
| 实时播放：**断言首帧渲染** | 不能只断言「页面没崩」，黑屏也算失败 |
| 云台：单指拖动 / 方向键 / 预置位 | 与视频层手势不冲突 |
| 回放：时间轴拖动、倍速 | |
| AI 事件列表与详情 | 通道维度 |
| 麦克风权限弹窗 → 对讲 | **必须驱动原生弹窗，这是选 Patrol 的主因** |

**关键限制（必须写进验收条件）**：
- **WebRTC 渲染类断言在模拟器上不可靠** —— Android 模拟器的硬件解码器行为与真机差异大，
  iOS 模拟器不支持部分编码。**媒体相关用例一律真机执行**，CI 只跑非媒体用例。
- iOS 需要 macOS runner，一期可只做 Android CI + iOS 手工。
- 与 Web E2E 共用同一套后端与调试台（同一个 `gbsim` 场景清单）。

### 13.6 真机兼容性验收（一期硬门槛）

模拟器只能做回归夹具，**不能替代真机**。一期结束前必须：

1. 接入 **≥1 台真实 GB28181 相机**，完成 §16 验收标准的 1–7 项；
2. **Web 与 App 各验一遍**；
3. 若真机是 H.265 或非 GB2312 编码，额外记录其在降级路径上的表现；
4. 把真机的实际报文（脱敏后）沉淀为 `protocol/` 的测试样本与 `gbsim/scenarios/` 的新场景 ——
   **一次真机联调的产出要能被后续回归复用**，否则每次都得重来。

## 附录 B：术语表

| 术语 | 说明 |
|:--|:--|
| **GB28181** | 中国国家标准《公共安全视频监控联网系统信息传输、交换、控制技术要求》 |
| **MANSCDP** | 国标信令 XML 协议，定义 Catalog/DeviceInfo/Alarm 等报文 |
| **MANSRTSP** | 国标回放控制协议，基于 RTSP 语义，走 SIP `INFO` |
| **PS / PS 流** | Program Stream（MPEG-2 系统层），国标规定的媒体封装格式 |
| **SSRC** | 同步源标识，国标中标识一路媒体流，经 SDP `y=` 字段通告 |
| **国标 ID** | 20 位编码，前 10 位为域（行政区划 + 行业），后 10 位为设备/通道序号 |
| **NVR** | 网络硬盘录像机；在 GB28181 中作为「1 设备 + N 通道」的设备形态 |
| **ZLM** | ZLMediaKit，流媒体服务器，负责收流、解复用、转协议与录像 |
| **WVP** | wvp-GB28181-pro，本项目的功能对标与协议参考实现 |
| **GB2312 / GB18030** | 中文编码；国标设备默认使用 GB2312，Go 侧统一按 GB18030 超集处理 |
| **WHEP** | WebRTC-HTTP Egress Protocol，ZLM 提供的低延迟播放入口 |

#### 第一轮评审修订要点

**事实性错误（4 条，均已改正）**：

| # | 原文 | 核实结果 |
|:--|:--|:--|
| 1 | §6.1「sipgo 内置服务端 Digest（`NewDigestServer`/`AuthorizeRequest`）」 | **张冠李戴** —— 这些 API 属 `emiago/diago`。实测 `go doc`：sipgo 的 `DigestAuth` 只是 `{Username, Password}` 空结构体，服务端能力**必须自研** |
| 2 | §2.1「WVP 库里没有任何 socket（`ServerSocket` 零命中）」 | `ServerSocket` **非零命中** —— `jt1078/codec/netty/TcpServer.java` 是真的 netty TCP 服务器。结论已收窄为「**GB28181 媒体路径**上 ZLM 独占」 |
| 3 | §2.4 用「Digest nonce 缓存分裂」论证「SIP 必须单节点」 | 论据**不成立** —— WVP 的 `generateNonce()` 无缓存、无过期校验，服务端 Digest 完全无状态。结论保留（改为 TCP/会话状态与 `server_id` 绑定三条理由），措辞从「必须」改为「一期选择」。**错误论据已同步从 `docker-compose.yml` 移除** |
| 4 | §5「18 张表覆盖 WVP 的 22 张」 | **漏了 `wvp_platform_group` / `wvp_platform_region`** —— 二者在 `PlatformChannelMapper`/`PlatformMapper` 中被大量使用，缺了则「按分组/按区域推送目录」做不出来。已补表 → **20 张** |
| 5 | §2.6「默认 GB2312（`RegisterRequestProcessor.java:186`）」 | 行号错（应为 `:206`/`:216`）；且「Go 直接 Unmarshal 产生乱码」不准 —— 声明非 UTF-8 时会**直接报错**，静默乱码只发生在无声明或声明 UTF-8 时。两种失败模式已分别说明 |
| 6 | §7.1 把 `on_media_arrival` 与 ZLM 回调并列 | 它是 **WVP 内部事件**，不在 ZLM 的 10 个回调之列。已标注并补全真实回调清单 |
| 7 | §7.3「`on_publish` 必须返 401 而非 200」 | WVP 用 HTTP 200 + JSON `code=-1`。两种都有效，但措辞误导 |
| 8 | §14.2 引用了不存在的表 `ac_notify` / `ac_alarm` | 实际是 `ac_notification` / `ac_alarm_record` |
